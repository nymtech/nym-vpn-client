# Account Specification

> Generated by openlore on 2026-06-25

## Purpose

Manages VPN account authentication and lifecycle: storing credentials (mnemonic or Privy signature), forgetting accounts, tracking account state, exposing account summaries and subscription status, and generating localized account links and PIN-protected autologin deeplinks. All account-mutating operations are gated on the tunnel being disconnected and are delegated to `nym-vpnd` over gRPC.

## Requirements

### Requirement: Add Account With Mnemonic

The backend SHALL accept a mnemonic passphrase via the `add_account` command to register or authenticate a decentralised account, only when the VPN tunnel is in the `Disconnected` state.

#### Scenario: Store account from disconnected state
- **GIVEN** the tunnel is `Disconnected`
- **WHEN** `add_account` is invoked with a mnemonic
- **THEN** `vpnd.store_account(Vpn { mnemonic })` is called and account state is updated

#### Scenario: Reject add while connected
- **GIVEN** the tunnel is in the `Connected` state
- **WHEN** `add_account` is invoked
- **THEN** an error of the form "cannot add account from state Connected" is returned

### Requirement: Add Account With Signature

The backend SHALL accept a Privy signature via the `add_account` command to register a Privy-linked account, only when the tunnel is `Disconnected`.

#### Scenario: Store Privy account
- **GIVEN** the tunnel is `Disconnected`
- **WHEN** `add_account` is invoked with a signature
- **THEN** `vpnd.store_account(Privy { mnemonic: signature })` is called

### Requirement: Forget Account

The backend SHALL remove all account-related data (device identity, credentials, gateway registrations) via the `forget_account` command, only when the tunnel is `Disconnected`.

#### Scenario: Forget account when disconnected
- **GIVEN** the tunnel is `Disconnected` and an account exists
- **WHEN** `forget_account` is invoked
- **THEN** `vpnd.forget_account()` is called

#### Scenario: Reject forget when not disconnected
- **GIVEN** the tunnel is not `Disconnected`
- **WHEN** `forget_account` is invoked
- **THEN** an internal error is returned and no data is removed

### Requirement: Account State Tracking

The system SHALL track and expose the current account state via the `AccountState` enum, mapping daemon controller states to values such as Ready, LoggedOut, Syncing, Offline, BandwidthExceeded, NoSubscription, MaxDeviceReached, and Error.

#### Scenario: Ready to connect
- **GIVEN** the daemon reports a ready-to-connect controller state
- **WHEN** `get_account_state` is invoked
- **THEN** `AccountState::Ready` is returned

#### Scenario: Device limit reached
- **GIVEN** the daemon reports a max-devices-reached condition
- **WHEN** the account state transitions
- **THEN** the account state becomes `MaxDeviceReached`

### Requirement: Account Storage Query

The system SHALL report whether an account is stored and expose account identity queries.

#### Scenario: Account stored check
- **GIVEN** an account is stored locally
- **WHEN** `is_account_stored` is invoked
- **THEN** it returns `true`

### Requirement: Autologin Deeplink

The backend SHALL generate a PIN-protected autologin deeplink via the `get_autologin_deeplink` command, returning both a URL and a PIN code for the autologin flow after web signup.

#### Scenario: Generate autologin deeplink
- **GIVEN** the user initiates autologin after web signup
- **WHEN** `get_autologin_deeplink` is invoked
- **THEN** a response containing a URL and a PIN code is returned and surfaced in the PIN-code dialog

### Requirement: Account Links

The backend SHALL provide localized account links (sign-up, sign-in, account portal) via the `account_links` command using the requested locale.

#### Scenario: Locale-specific links
- **GIVEN** the frontend requests links for a given locale
- **WHEN** `account_links` is invoked with that locale
- **THEN** sign-up, sign-in, and account portal URLs for that locale are returned

### Requirement: Account Summary And Subscription

The system SHALL expose account details including traffic usage, subscription status, authentication methods, and fair-usage data via the `get_account_summary` command.

#### Scenario: Retrieve account summary
- **GIVEN** an authenticated account
- **WHEN** `get_account_summary` is invoked
- **THEN** a summary containing traffic used/limit, subscription status, and auth methods is returned
