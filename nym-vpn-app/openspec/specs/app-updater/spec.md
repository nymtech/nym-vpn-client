# App Updater Specification

## Purpose

Provides cross-platform application update checking and installation through the Tauri updater plugin, with progress reporting during download. On Linux, additionally watches for out-of-band binary replacement (e.g. by a package manager) and notifies the frontend when a restart is needed.

## Requirements

### Requirement: Check For Updates

The backend SHALL gate update checking behind the `UPDATER_ENABLED` flag, query the configured (or default) update endpoint via the `fetch_update` command, and return update metadata while caching the pending update.

#### Scenario: Updater disabled
- **GIVEN** `UPDATER_ENABLED` is false
- **WHEN** `fetch_update` is invoked
- **THEN** an "updater is disabled" error is returned immediately

#### Scenario: Update available
- **GIVEN** the update endpoint offers a newer version
- **WHEN** `fetch_update` is invoked
- **THEN** update metadata (new version and current version) is returned and the pending update is cached in state

### Requirement: Download And Install Update

The backend SHALL require a previously fetched pending update, then download and install it via the `install_update` command while emitting progress events.

#### Scenario: Install with progress events
- **GIVEN** a pending update exists
- **WHEN** `install_update` is invoked
- **THEN** the event channel receives a Started event, then Progress events as chunks arrive, then a Finished event

#### Scenario: Install without a pending update
- **GIVEN** no pending update has been fetched
- **WHEN** `install_update` is invoked
- **THEN** a "no update available" error is returned

### Requirement: Detect Linux Binary Replacement

On Linux, the backend SHALL spawn a watcher that detects when the running binary is replaced on disk and SHALL emit an update-pending event exactly once.

#### Scenario: Replacement detected at startup
- **GIVEN** the binary was replaced before the watcher started
- **WHEN** the watcher checks the running binary during initialization
- **THEN** it detects the inode mismatch, emits the update-pending event once, and stops

#### Scenario: Replacement detected while running
- **GIVEN** the watcher is monitoring the binary's parent directory
- **WHEN** the binary file is modified or replaced
- **THEN** an inode comparison is performed and, on mismatch, the update-pending event is emitted

### Requirement: Resolve Running Binary Path

On Linux, the backend SHALL resolve the running binary path from `/proc/self/exe`, stripping any trailing " (deleted)" suffix.

#### Scenario: Strip deleted suffix
- **GIVEN** the running binary's `/proc/self/exe` link is marked deleted
- **WHEN** the self path is resolved
- **THEN** the trailing " (deleted)" suffix is stripped from the returned path

### Requirement: Graceful Shutdown Before Restart

The backend SHALL delay briefly before the app exits for an update so the UI can render its final state.

#### Scenario: Delay before exit
- **GIVEN** installation finishes
- **WHEN** the before-exit callback runs
- **THEN** the process waits briefly before exiting so the completion state is visible
