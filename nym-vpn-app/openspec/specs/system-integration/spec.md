## Purpose

Manages desktop OS integration and the app shell: the system tray (native on Windows/macOS, StatusNotifierItem on Linux), window management (main + error windows), deep-link handling, CLI argument parsing, the embedded sled key-value store, TOML config and filesystem path organization, system-info detection, single-instance enforcement, autostart, and window-state persistence.

## Requirements

### Requirement: Embedded Key-Value Store

The application SHALL use an embedded sled database under the app data directory, with typed keys for UI preferences, cached gateway lists, cached identities, custom split-tunnel apps, and feature flags, and SHALL seed defaults on first run.

#### Scenario: Seed defaults on startup
- **GIVEN** the app starts and the network-stats key is unset
- **WHEN** the database defaults are initialized
- **THEN** the network-stats key is set to its default value

#### Scenario: Redact large cached values in logs
- **GIVEN** the frontend reads a key that holds a cached gateway list
- **WHEN** the read is logged
- **THEN** the log redacts the value to avoid logging large data

### Requirement: Config File Management

The application SHALL read and write a TOML config file under the app config directory and fall back to an empty config if it is malformed.

#### Scenario: Fallback on malformed config
- **GIVEN** the config file is malformed
- **WHEN** the app reads it at startup
- **THEN** it logs a fallback message, uses an empty default config, and clears the file

### Requirement: Filesystem Path Organization

The application SHALL organize persistent data into platform-specific config, data, and log directories, resolved at startup.

#### Scenario: Resolve config directory
- **GIVEN** the app initializes
- **WHEN** it resolves the config directory
- **THEN** it verifies the directory exists and logs the resolved path

### Requirement: System Tray Icon Management

The application SHALL update the tray icon to reflect VPN tunnel state using platform-specific backends, debouncing rapid updates.

#### Scenario: Icon reflects connected state
- **GIVEN** the tunnel transitions to Connected
- **WHEN** the tray backend handles the state change
- **THEN** the tray icon is updated to the connected icon

#### Scenario: Debounce rapid changes
- **GIVEN** the tunnel state changes several times in quick succession
- **WHEN** the tray icon update is requested repeatedly within the debounce window
- **THEN** pending update tasks are superseded so only the latest icon is applied

### Requirement: System Tray Menu Operations

The application SHALL provide tray menu items (show/hide, status, mode, entry, quit) whose text is driven by frontend commands, and SHALL toggle entry-item visibility based on entry-node selection.

#### Scenario: Show/hide from tray
- **GIVEN** the user clicks the show/hide tray item
- **WHEN** the menu event is handled
- **THEN** main window visibility is toggled

#### Scenario: Hide entry item
- **GIVEN** entry-node mode is disabled
- **WHEN** the frontend updates entry-item visibility to false
- **THEN** the entry menu item is removed or hidden

### Requirement: Single Instance Enforcement

The application SHALL allow only one running instance; a second launch SHALL focus the existing instance's main window.

#### Scenario: Second launch focuses existing window
- **GIVEN** an instance is already running
- **WHEN** a second instance is launched
- **THEN** the running instance's main window is shown, unminimized, and focused

### Requirement: Deep Link Handling

The application SHALL register and handle the `nymvpn://` deep-link scheme, supporting deep-link kinds for Privy, account linking, autologin, and account creation.

#### Scenario: Register scheme at launch
- **GIVEN** the app launches on a desktop platform
- **WHEN** the setup hook runs
- **THEN** the `nymvpn://` scheme handler is registered

### Requirement: CLI Argument Parsing

The application SHALL parse CLI arguments including build-info, log-file, log-level, nosplash, clean-local-files, and trailing deep-link arguments, and SHALL act on them before launching the UI where appropriate.

#### Scenario: Print build info and exit
- **GIVEN** the app is started with the build-info flag
- **WHEN** arguments are parsed
- **THEN** build metadata is printed instead of launching the UI

#### Scenario: Clean local files and exit
- **GIVEN** the app is started with the clean-local-files flag
- **WHEN** arguments are parsed
- **THEN** the app deletes all local files and exits without starting

### Requirement: Main Window Management

The application SHALL create and manage a main window with configurable visibility and size, applying a background color synchronized with the saved theme preference, and SHALL support skipping the splash screen.

#### Scenario: Apply saved theme background
- **GIVEN** the saved theme preference is dark
- **WHEN** the main window background color is set
- **THEN** the dark background color is applied to the webview

#### Scenario: Skip splash
- **GIVEN** the app starts with the nosplash flag or env var
- **WHEN** the main window is created
- **THEN** the splash screen is skipped

### Requirement: Error Window Display

The application SHALL display a dedicated error window on startup failure (e.g. database lock or open error) and exit the app when that window is closed.

#### Scenario: Database locked at startup
- **GIVEN** the database fails to open because it is locked
- **WHEN** startup error handling runs
- **THEN** an error window is created describing the failure

#### Scenario: Closing the error window exits
- **GIVEN** the error window is shown
- **WHEN** the user closes it
- **THEN** the application exits

### Requirement: Window State Persistence

The application SHALL persist and restore window position (and size, except where platform constraints apply) across restarts, excluding the error window.

#### Scenario: Restore window dimensions
- **GIVEN** the user resized the main window and exited
- **WHEN** the app launches again
- **THEN** the previous window dimensions are restored

### Requirement: System Information Detection

The application SHALL detect OS information (version, kernel, architecture, and on Linux the display server and GPU type) and apply platform-specific workarounds.

#### Scenario: NVIDIA workaround on Linux
- **GIVEN** the app starts on Linux with an NVIDIA GPU
- **WHEN** GPU detection identifies NVIDIA
- **THEN** the WebKit DMABUF renderer is disabled via the corresponding environment variable
