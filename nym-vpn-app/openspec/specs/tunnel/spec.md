# Tunnel Specification

> Generated by openlore on 2026-06-25

## Purpose

Manages the VPN tunnel control lifecycle: connecting, disconnecting, monitoring state transitions, selecting the VPN mode, configuring domain fronting, and managing per-application split tunneling. The Tauri backend translates frontend IPC commands into gRPC calls to `nym-vpnd` and broadcasts tunnel state changes back to the frontend via Tauri events.

## Requirements

### Requirement: Connect Transition

The client SHALL transition the tunnel from `Disconnected` to `Connecting` immediately when the `connect` command is invoked, before issuing any daemon RPC, and SHALL reject the command from any other state.

#### Scenario: Connect from disconnected state
- **GIVEN** the tunnel is in `TunnelState::Disconnected`
- **WHEN** the `connect` command is invoked
- **THEN** app state immediately becomes `TunnelState::Connecting(ConnectingState::default())` and a `tunnel-state` event is emitted before the daemon RPC

#### Scenario: Connect rejected from non-disconnected state
- **GIVEN** the tunnel is in any non-`Disconnected` state
- **WHEN** the `connect` command is invoked
- **THEN** the command returns an error of the form "cannot connect from state {state}"

### Requirement: Connection Progress Reporting

The tunnel SHALL report fine-grained connection progress phases (resolving API addresses, awaiting account readiness, refreshing gateways, selecting gateways, registering with gateways, connecting tunnel) as the daemon emits them.

#### Scenario: Progress phase update during connecting
- **GIVEN** the tunnel is in `Connecting` state
- **WHEN** the daemon sends a `TunnelEvent::NewState(Connecting{ ... })` with an updated progress phase
- **THEN** the frontend tunnel state is updated via the `tunnel-state` event reflecting the new progress phase

### Requirement: Disconnect Transition

The client SHALL transition the tunnel to `Disconnecting` when the `disconnect` command is invoked from a connected or connecting state, and SHALL reject the command when already disconnected or disconnecting.

#### Scenario: Disconnect from connected state
- **GIVEN** the tunnel is `Connected` or `Connecting`
- **WHEN** the `disconnect` command is invoked
- **THEN** the tunnel state becomes `TunnelState::Disconnecting` and the `vpn_disconnect` RPC is invoked

#### Scenario: Disconnect rejected when not connected
- **GIVEN** the tunnel is `Disconnected` or `Disconnecting`
- **WHEN** the `disconnect` command is invoked
- **THEN** the command returns an error and no RPC is issued

### Requirement: VPN Mode Selection

The client SHALL support two VPN modes — Mixnet (5-hop) and Wireguard 2-hop — selectable via the `set_vpn_mode` command, mapping the mode to the daemon's `set_two_hop` RPC.

#### Scenario: Selecting Wireguard 2-hop mode
- **GIVEN** the frontend requests `VpnMode::Wg`
- **WHEN** the `set_vpn_mode` command runs
- **THEN** the daemon RPC `set_two_hop(true)` is invoked

#### Scenario: Selecting Mixnet mode
- **GIVEN** the frontend requests `VpnMode::Mixnet`
- **WHEN** the `set_vpn_mode` command runs
- **THEN** the daemon RPC `set_two_hop(false)` is invoked

### Requirement: Fronting Mode Configuration

The client SHALL support three domain fronting modes — `Off`, `OnRetry`, and `Always` — configurable via the `set_fronting_mode` command and forwarded to the daemon.

#### Scenario: Disabling domain fronting
- **GIVEN** the user selects fronting mode `Off`
- **WHEN** the `set_fronting_mode(FrontingMode::Off)` command runs
- **THEN** the daemon RPC `set_fronting_mode(Off)` is sent

### Requirement: Tunnel Error Reporting

The tunnel SHALL surface detailed error reasons to the frontend, including (among others) `InvalidEntryGwId`, `MaxDevicesReached`, `InactiveSubscription`, `BandwidthExceeded`, and firewall/DNS/routing failures, by mapping daemon `ErrorStateReason` variants to frontend `TunnelError` variants.

#### Scenario: Invalid entry gateway identity
- **GIVEN** the daemon emits `ErrorStateReason::InvalidEntryGatewayIdentity`
- **WHEN** the error is mapped for the frontend
- **THEN** a `TunnelError::InvalidEntryGwId` is emitted to the UI

### Requirement: Split Tunnel Management

The client SHALL manage per-application VPN bypass (split tunneling), supporting adding and removing apps and producing an app list that merges apps imported from daemon config with discovered installed apps.

#### Scenario: Adding an app to split tunnel
- **GIVEN** the platform supports split tunneling
- **WHEN** the `add_app_to_split_tunnel` command is invoked with an app path
- **THEN** the daemon receives the split-tunnel RPC and the app is excluded from the VPN

#### Scenario: Listing split-tunnel apps
- **GIVEN** the daemon holds a split-tunnel config containing app entries
- **WHEN** the frontend requests the app list
- **THEN** apps imported from the daemon config are merged with discovered installed apps

### Requirement: Tunnel State Broadcast

The client SHALL stream tunnel state changes from the daemon event stream to the frontend via the tunnel-state Tauri event, and the frontend store SHALL update its tunnel state accordingly.

#### Scenario: Connected state propagated to store
- **GIVEN** the daemon event stream reports a new `Connected` state
- **WHEN** the frontend receives the `tunnel-state` event
- **THEN** the Zustand store updates to the connected tunnel state and clears transient progress messages
