# Diagnostics & Logging Specification

> Generated by openlore on 2026-06-25

## Purpose

Collects diagnostic telemetry (DNS, HTTP/API, gateway connectivity, hybrid transport), manages application logging with file rotation, integrates optional Sentry error reporting gated by a DSN environment variable, and toggles network bandwidth/latency statistics. Diagnostic reports can be exported to JSON for user support.

## Requirements

### Requirement: Collect Diagnostic Data

The backend SHALL run diagnostics via the `run_diagnostic` command, accepting parameters that may skip DNS, HTTP, or hybrid-transport tests, and SHALL return a report of the executed tests.

#### Scenario: Skip DNS tests
- **GIVEN** the user initiates a diagnostic with DNS tests skipped
- **WHEN** `run_diagnostic` runs
- **THEN** the daemon performs HTTP, gateway, and hybrid-transport tests and omits DNS tests

#### Scenario: Diagnostic against a specific gateway
- **GIVEN** a gateway is specified in the diagnostic parameters
- **WHEN** `run_diagnostic` runs
- **THEN** the tests use the specified gateway

### Requirement: Export Diagnostic Report

The backend SHALL serialize a diagnostic report to JSON and write it to a user-selected path via a file save dialog.

#### Scenario: Save report to file
- **GIVEN** a completed diagnostic report
- **WHEN** the share-diagnostic command runs
- **THEN** the user is shown a save dialog and the report is written as prettified JSON, or the action is cancelled without error

### Requirement: Configure Sentry Reporting

The backend SHALL gate Sentry initialization behind the `APP_SENTRY_DSN` environment variable, persist the user's monitoring preference, and require an app restart for changes to take effect.

#### Scenario: Sentry disabled without DSN
- **GIVEN** `APP_SENTRY_DSN` is empty
- **WHEN** Sentry initialization runs
- **THEN** no Sentry client is created and a warning is logged, and the app continues without error reporting

#### Scenario: Enable Sentry persists preference
- **GIVEN** the user enables Sentry
- **WHEN** the enable-Sentry command completes
- **THEN** the monitoring preference is persisted, a restart-required message is logged, and the daemon is told to enable its reporting

### Requirement: Manage Sentry Lifecycle

The backend SHALL close the Sentry client with a graceful shutdown timeout when disabled and keep the daemon-side reporting state in sync.

#### Scenario: Disable Sentry
- **GIVEN** Sentry is active
- **WHEN** the disable-Sentry command runs
- **THEN** the Sentry client is closed gracefully, the daemon disables its reporting, and the preference is persisted as disabled

### Requirement: Frontend Logging

The backend SHALL accept log messages from the frontend via the `log_js` command with an optional level, routing them to the tracing logger.

#### Scenario: Log a debug message from JS
- **GIVEN** the frontend sends a message with the Debug level
- **WHEN** `log_js` executes
- **THEN** the message is logged at the Debug level

### Requirement: Application Logging Setup

The backend SHALL configure the tracing subscriber with an environment filter (default Info), rotate the previous log file on startup, and optionally write to a log file when enabled.

#### Scenario: File logging with rotation
- **GIVEN** the app starts with file logging enabled
- **WHEN** logging is set up
- **THEN** the previous log file is rotated to an `.old` file and a new log file is created in the log directory

### Requirement: Network Statistics Toggle

The backend SHALL toggle network statistics collection via enable/disable commands, forwarding to the daemon and persisting the toggle in the embedded database.

#### Scenario: Enable network stats
- **GIVEN** the user toggles network stats on
- **WHEN** the enable-netstats command runs
- **THEN** the daemon begins collecting bandwidth/latency stats and the enabled flag is persisted
