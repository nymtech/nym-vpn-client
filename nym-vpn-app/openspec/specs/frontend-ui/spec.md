## Purpose

The React 19 + TypeScript frontend: application composition, routing, screen hierarchy, the Zustand + React Context state architecture, theming, and multi-locale internationalization with RTL support. The UI communicates with the Tauri backend via `invoke()` commands and listens to Tauri events for state updates.

## Requirements

### Requirement: Provider Composition

The application root SHALL compose context providers in a fixed order so that shared state is initialized before any route renders.

#### Scenario: State ready before routing
- **GIVEN** the app initializes
- **WHEN** the root component renders
- **THEN** the main state provider is mounted before the router provider so state is ready when routes render

### Requirement: Route Gating By Auth State

The startup gate SHALL route the user based on account and daemon state, ensuring unauthenticated screens precede authenticated access.

#### Scenario: No account routes to onboarding
- **GIVEN** the user has no stored account
- **WHEN** the app loads and the daemon is reachable
- **THEN** the startup gate navigates to the onboarding route

#### Scenario: Daemon down handled downstream
- **GIVEN** the daemon status is down or auth-denied
- **WHEN** the startup gate evaluates routing
- **THEN** it navigates to the root route so daemon status is handled downstream

### Requirement: Multi-Stage App Initialization

App initialization SHALL run in two batches: a first batch that unblocks the UI and a background second batch for non-critical state.

#### Scenario: First batch unblocks UI
- **GIVEN** the daemon status transitions to up
- **WHEN** the main state provider detects the change
- **THEN** the first initialization batch and gateway fetch run in parallel and signal initialization done to unblock the splash

#### Scenario: Second batch loads in background
- **GIVEN** the first batch has completed
- **WHEN** the provider re-renders
- **THEN** the second batch fetches non-critical data without blocking render

### Requirement: Zustand Store Slices

The Zustand store SHALL compose distinct slices (main, gateways, SOCKS5) and selectors SHALL return only the relevant slice to limit re-renders.

#### Scenario: Main state selector
- **GIVEN** a component reads main state
- **WHEN** the selector fires
- **THEN** it returns only the main slice properties using a shallow comparison to avoid unnecessary re-renders

### Requirement: Theme Persistence And Application

Theme state SHALL be read on startup, stored in the Zustand store, and applied by toggling the dark class on the root element, with the preference persisted to the key-value store.

#### Scenario: Apply dark theme
- **GIVEN** the resolved theme is dark
- **WHEN** the theme setter renders
- **THEN** it adds the dark class to the root element and dark-variant styles activate

### Requirement: Internationalization And Locale Loading

The frontend SHALL support multiple active locales, lazy-loading locale resources on demand while bundling English at build time, and SHALL detect the system locale when no preference is stored.

#### Scenario: Lazy-load a locale
- **GIVEN** the user selects a non-English language
- **WHEN** the language is set
- **THEN** that locale's resources are dynamically imported and registered, and the date library locale is updated

#### Scenario: System locale fallback
- **GIVEN** no stored language preference and an unsupported system locale
- **WHEN** locale detection runs
- **THEN** the app falls back to English

### Requirement: RTL Support

Right-to-left languages SHALL set the document direction and language attributes, and RTL-aware components SHALL adjust their layout accordingly.

#### Scenario: Apply RTL direction
- **GIVEN** the user selects a right-to-left language
- **WHEN** the language loads
- **THEN** the document direction attribute is set to RTL and RTL-aware components invert their layout

### Requirement: Language Persistence

The selected language SHALL be persisted to the key-value store and re-applied on restart before routes render.

#### Scenario: Persist and restore language
- **GIVEN** the user selects a language
- **WHEN** the selection completes
- **THEN** the preference is stored and, on the next launch, loaded and applied before routing

### Requirement: Technical Opt-In Gate

The technical opt-in screen SHALL be shown before the home screen until the user has seen it, with the seen state persisted to the key-value store.

#### Scenario: Show opt-in once
- **GIVEN** a fresh installation where the opt-in has not been seen
- **WHEN** the user navigates
- **THEN** the technical opt-in screen is shown before home, and once seen the flag is persisted and the screen is bypassed

### Requirement: Layout And Error Boundaries

The main layout SHALL conditionally render the top bar (`TopBar`), the daemon indicator (`DaemonDot`), and notifications (`ToastList`) based on the `noTopBar`, `noDaemonDot`, and `noNotifications` props, and routes SHALL define an error element to catch render-time exceptions.

#### Scenario: Onboarding hides top bar, daemon indicator, and notifications
- **GIVEN** the user is on the onboarding route
- **WHEN** the layout renders with `noTopBar`, `noDaemonDot`, and `noNotifications` set
- **THEN** the `TopBar`, `DaemonDot`, and `ToastList` are not rendered

#### Scenario: Route error boundary
- **GIVEN** a settings sub-route component throws during render
- **WHEN** the router catches the exception
- **THEN** the nearest error element renders the error
