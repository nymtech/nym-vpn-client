## Purpose

Describes the structural composition of the application: the two-process model, the Tauri IPC layer, the gRPC client to `nym-vpnd`, shared backend state, the frontend Zustand + Context state architecture, and the Rust→TypeScript type-generation workflow.

## Requirements

### Requirement: Layered Process Model

The system SHALL consist of two cooperating processes — the Tauri app (UI + control) and the external `nym-vpnd` daemon — with the Tauri backend acting as the sole gRPC client to the daemon.

#### Scenario: Backend brokers daemon access
- **GIVEN** the frontend needs VPN functionality
- **WHEN** it issues a Tauri command
- **THEN** the Rust backend translates the command into a daemon gRPC call rather than the frontend talking to the daemon directly

### Requirement: Command And Event IPC Layer

The backend SHALL organize IPC handlers into per-domain command modules and SHALL push asynchronous updates to the frontend via named Tauri events.

#### Scenario: Per-domain command modules
- **GIVEN** the backend exposes IPC handlers
- **WHEN** a new domain operation is added
- **THEN** it is placed in the corresponding command module and registered in the command registry

#### Scenario: Event-driven state updates
- **GIVEN** the daemon emits a state change on its event stream
- **WHEN** the backend receives it
- **THEN** the backend emits a corresponding Tauri event the frontend listens to

### Requirement: Shared Backend State

The backend SHALL maintain shared application state (daemon status, tunnel state, pending update, etc.) behind synchronized access so commands and the daemon event stream observe a consistent view.

#### Scenario: Consistent state across handlers
- **GIVEN** multiple command handlers and the event stream access app state
- **WHEN** state is read or mutated
- **THEN** access is synchronized through the shared state guard

### Requirement: Frontend State Architecture

The frontend SHALL manage application state in a Zustand store composed of slices, surfaced to React via Context providers composed at the app root.

#### Scenario: Slice-based store with context access
- **GIVEN** the frontend needs shared state
- **WHEN** a component reads it
- **THEN** it reads from the relevant Zustand slice exposed through a context provider

### Requirement: Type Generation Workflow

The system SHALL generate TypeScript IPC types from Rust structs annotated for export, and the generated file SHALL not be hand-edited.

#### Scenario: Regenerate after Rust type change
- **GIVEN** a Rust IPC type is modified
- **WHEN** type generation is run
- **THEN** the generated TypeScript types file is updated to match

### Requirement: Platform Abstraction

The system SHALL abstract platform-specific implementations (tray backend, app discovery, update detection) behind common interfaces or platform-gated code paths.

#### Scenario: Tray backend selection
- **GIVEN** the app runs on a given platform
- **WHEN** the tray is initialized
- **THEN** the platform-appropriate tray backend is selected behind a common tray interface
