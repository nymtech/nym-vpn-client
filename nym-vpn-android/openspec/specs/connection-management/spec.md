## Purpose

Provides the app-level orchestration layer above the low-level VPN engine. It binds to the Android VPN service, exposes an aggregated `TunnelManagerState` as a `StateFlow` for the UI, reduces low-level `VpnServiceEvent`s into that state, assembles VPN configuration before connecting, and manages identity state (mnemonic stored, device/account IDs, account state).

## Requirements

### Requirement: Service Binding

The backend manager MUST establish and maintain a binding to the Android VPN service, caching the service API for subsequent calls and serializing concurrent bind attempts.

#### Scenario: Bind on initialize
- **GIVEN** the app launches
- **WHEN** the backend manager initializes
- **THEN** it binds to the VPN service and caches the service API instance

#### Scenario: Serialize concurrent binds
- **GIVEN** multiple callers request the API before the service is bound
- **WHEN** they await the API concurrently
- **THEN** only one bind is launched and the others await the same in-progress result

### Requirement: Reactive State Exposure

The backend manager MUST expose tunnel connection state and account summary as reactive flows for UI subscribers.

#### Scenario: State propagates to UI
- **GIVEN** a singleton backend manager with an application-scoped state flow
- **WHEN** the tunnel manager state is updated
- **THEN** the change propagates through the state flow to all UI observers

### Requirement: Tunnel Startup Orchestration

Starting the tunnel MUST assemble the VPN configuration, apply split-tunnel restricted apps, initialize the core backend, and issue the connect command.

#### Scenario: Connect with restricted apps
- **GIVEN** split-tunnel exclusions are configured
- **WHEN** the tunnel start runs
- **THEN** the excluded packages are applied, the init request is built, the core is initialized, and connect is issued

#### Scenario: Relax gateway independence on reconnect
- **GIVEN** a reconnect requests relaxed gateway independence
- **WHEN** the start runs with that flag
- **THEN** gateway independence is disabled to allow matching entry/exit until the next full reconnect

### Requirement: Event Reduction

The event reducer MUST reduce low-level VPN service events into aggregated tunnel manager state mutations.

#### Scenario: Reduce up state
- **GIVEN** a state-changed event reporting the tunnel is up
- **WHEN** the reducer handles it
- **THEN** the state is set to up and the restarting flag is cleared

### Requirement: Connection Info Tracking

The backend manager MUST track entry/exit gateways, tunnel address, and connection timing in connection info, preserving the original connect time across reconnects.

#### Scenario: Capture established connection
- **GIVEN** an establish-connection event with entry and exit gateways
- **WHEN** the reducer processes it
- **THEN** the connection info is populated from the event data

### Requirement: Mixnet Status Aggregation

The backend manager MUST aggregate per-address-family (IPv4/IPv6) connection milestones into a mixnet connection state.

#### Scenario: IPv4 connected milestone
- **GIVEN** a mixnet connection event indicating IPv4 connected
- **WHEN** the reducer applies it
- **THEN** the mixnet connection state reflects the IPv4 connected milestone

### Requirement: Error Handling And Recovery

The backend manager MUST handle fatal errors, competing-VPN detection, and permission failures with state mutation and appropriate foreground/background user notification.

#### Scenario: Fatal error clears connection
- **GIVEN** a fatal-error event
- **WHEN** the reducer processes it
- **THEN** the tunnel state becomes down, connection sub-states are cleared, and the quick-settings tile is updated

#### Scenario: Permission required notification
- **GIVEN** a tunnel start returns permission-required while the app is backgrounded
- **WHEN** the result is handled
- **THEN** a permission notification is shown (or an in-app message when foregrounded)

### Requirement: Identity State Management

The backend manager MUST manage mnemonic storage, device identity, and account identity, synchronizing identity fields in state after changes.

#### Scenario: Refresh after storing mnemonic
- **GIVEN** a mnemonic is stored
- **WHEN** the store completes
- **THEN** identity state is refreshed (mnemonic-stored, device id, account id, account state)

### Requirement: Configuration Synchronization

The VPN config repository MUST expose the current core VPN config and apply updates through the VPN service API.

#### Scenario: Apply config updates
- **GIVEN** a list of config updates
- **WHEN** they are applied through the API
- **THEN** the config flow is refreshed with the updated config on success
