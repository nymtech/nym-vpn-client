## Purpose

Describes the structural composition of the Android client: the multi-module Gradle layout, Hilt dependency injection, the MVVM + repository + DataStore data flow, the bound `VpnService` backed by the Rust core, the reactive state pipeline (Flow/StateFlow) from repositories to Compose, and the build-flavor abstraction.

## Requirements

### Requirement: Modular Gradle Layout

The system SHALL separate concerns across Gradle modules — UI/app shell in `app`, the VPN engine in `core`, network monitoring in `connectivity`, billing in `billing`, and log capture in `logcatter`.

#### Scenario: Place engine code in core
- **GIVEN** low-level VPN engine functionality
- **WHEN** it is implemented
- **THEN** it resides in the `core` module rather than the app module

### Requirement: Dependency Injection

The system SHALL use Hilt to provide singletons (managers, repositories, services, dispatchers) via modules, injected into Android components and view models.

#### Scenario: Inject a manager
- **GIVEN** a component needs a manager or repository
- **WHEN** it is constructed
- **THEN** Hilt provides the dependency from a DI module

### Requirement: MVVM With Repositories And DataStore

The system SHALL follow an MVVM pattern where view models expose UI state and depend on repositories that persist via DataStore Preferences.

#### Scenario: Persist via repository
- **GIVEN** a view model changes a setting
- **WHEN** the change is saved
- **THEN** it is written through a repository to DataStore and observed back via a flow

### Requirement: Bound VPN Service

The system SHALL run the VPN through a bound Android `VpnService` backed by the Rust core, with the app layer communicating via a service API obtained through binding.

#### Scenario: Communicate via service API
- **GIVEN** the app needs to control the tunnel
- **WHEN** it issues a command
- **THEN** it calls the bound VPN service API rather than the core directly

### Requirement: Reactive State Pipeline

The system SHALL expose state as Kotlin Flows/StateFlows combined into UI state for Jetpack Compose, so UI updates reactively to backend, settings, config, and gateway changes.

#### Scenario: Combine into UI state
- **GIVEN** multiple state sources (backend, settings, config, gateways)
- **WHEN** any source updates
- **THEN** they are combined into a unified UI state emitted to Compose

### Requirement: Build Flavor Abstraction

The system SHALL abstract flavor-specific behavior (notably billing) behind interfaces with per-flavor implementations selected at build time.

#### Scenario: Flavor-specific billing implementation
- **GIVEN** a build flavor
- **WHEN** the billing dependency is resolved
- **THEN** the flavor's implementation (Google Play or F-Droid stub) is provided
