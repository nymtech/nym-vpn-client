## Purpose

The `core` Gradle module wraps the Nym Rust core (via uniffi bindings) behind an Android `VpnService`. It manages the tunnel lifecycle, translates Rust tunnel events into coarse tunnel states, configures the Android TUN interface (routes, DNS, split tunneling), persists VPN configuration, and bridges network connectivity changes to the Rust layer.

## Requirements

### Requirement: Tunnel State Lifecycle

The tunnel SHALL transition through discrete `Tunnel.State` values (Down → InitializingClient → EstablishingConnection → Up) when connecting and collapse to Down/Error/Offline on disconnect or error, driven by Rust `TunnelEvent` messages.

#### Scenario: Successful connect
- **GIVEN** an initialized VPN service in the Down state
- **WHEN** the core controller connects the tunnel
- **THEN** it sends the connect command, publishes InitializingClient, and publishes Up once the Rust core reports connected

#### Scenario: Competing VPN takeover
- **GIVEN** an active tunnel in the Up state
- **WHEN** the network callback detects another VPN app taking over
- **THEN** a competing-VPN event is emitted and the tunnel is torn down

### Requirement: Tunnel Mode Configuration

The tunnel SHALL support five-hop and two-hop mixnet modes via `Tunnel.Mode`, applying the selected mode to the Rust core and reconnecting when it changes on a running tunnel.

#### Scenario: Switch mode with reconnect
- **GIVEN** a running tunnel in two-hop mode
- **WHEN** the mode is changed to five-hop
- **THEN** the new mode is persisted, sent to the core, and the tunnel reconnects with the new hop count

### Requirement: Gateway Selection

Entry and exit points SHALL be selectable as Random, Gateway identity, Country, or Region, tracked by the controller and applied to the Rust core via set-entry-point/set-exit-point commands.

#### Scenario: Country-based exit
- **GIVEN** the user selects a specific country for the exit point
- **WHEN** the exit-point update is applied
- **THEN** the selection is persisted and the corresponding country exit point is set on the core

### Requirement: Connect/Disconnect Initiation

Connect, disconnect, and reconnect operations MUST serialize on the core mutex, verify VPN permission (returning a permission-required result when missing), ensure core initialization, and cleanly tear down the TUN interface and foreground notification on disconnect.

#### Scenario: Permission required at connect
- **GIVEN** VPN permission has not been granted
- **WHEN** a connect is attempted
- **THEN** the platform VPN prepare returns an intent and a permission-required result is returned

#### Scenario: Graceful disconnect
- **GIVEN** a connected tunnel
- **WHEN** disconnect runs
- **THEN** the disconnect command is sent, the TUN interface is closed, the foreground notification is cancelled, and the state becomes Down

### Requirement: Configuration Persistence

VPN configuration (entry/exit, mode, DNS, LAN bypass, restricted apps, network environment, debug flags) SHALL be persisted and applied to the Rust core via a diff-based mechanism that sends only changed fields.

#### Scenario: Diff-based batch update
- **GIVEN** a batch of config patches
- **WHEN** the updates are applied
- **THEN** they are folded into one snapshot, persisted, and only the changed fields are pushed to the core

### Requirement: Network Environment

The tunnel SHALL support mainnet, canary, and sandbox environments, initializing the corresponding Nym environment and falling back to mainnet on initialization error.

#### Scenario: Fallback on environment error
- **GIVEN** a non-mainnet environment fails to initialize
- **WHEN** environment creation throws
- **THEN** the error is logged and a mainnet fallback environment is used

### Requirement: Tunnel Event Handling

Rust tunnel events SHALL be dispatched via the status listener, mapped to coarse tunnel states, and re-emitted as service events to subscribers.

#### Scenario: Error state with reason
- **GIVEN** the Rust core reports an error state with a reason
- **WHEN** the tunnel event is handled
- **THEN** a fatal-error service event carrying the reason is emitted and the error state is published

### Requirement: Android VPN Service Integration

The VPN service SHALL act as the Android TUN provider and tunnel status listener, support binding for IPC, and detect always-on/auto-start to connect without UI.

#### Scenario: Always-on auto-connect
- **GIVEN** the service is started by the system in always-on mode
- **WHEN** the start command is handled
- **THEN** the service promotes to foreground, ensures readiness, and connects if currently down

### Requirement: TUN Interface Configuration

The TUN interface SHALL be configured with addresses, DNS, routes, and MTU, applying split-tunnel disallowed apps and LAN bypass before the file descriptor is handed to the Rust core.

#### Scenario: Restricted apps excluded
- **GIVEN** a config with restricted apps
- **WHEN** the tunnel interface is configured
- **THEN** each restricted app is added as a disallowed application and excluded from the tunnel

### Requirement: Connectivity Monitoring

The connectivity bridge SHALL aggregate platform network status changes and forward them to the Rust connectivity observers.

#### Scenario: Network change forwarded
- **GIVEN** registered Rust connectivity observers
- **WHEN** the network transitions from connected to disconnected
- **THEN** each observer is notified of the network change
