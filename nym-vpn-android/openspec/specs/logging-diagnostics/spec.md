# Logging & Diagnostics Specification

## Purpose

Captures, buffers, persists, and exports device logs from multiple sources (app, tunnel/core-vpn, and the libnymvpn library), with a Timber file-logging fallback when logcat is unavailable. Provides log viewing/filtering/export and a backend-driven diagnostic report in the settings UI.

## Requirements

### Requirement: Logcat Message Parsing

The system SHALL parse logcat threadtime-format lines into structured messages (time, pid, tid, level, tag, message).

#### Scenario: Parse a log line
- **GIVEN** a raw logcat threadtime line
- **WHEN** it is parsed
- **THEN** a structured message with pid, tid, level, tag, and message text is produced

### Requirement: Log Type Classification

The system SHALL classify logs into core (libnymvpn), tunnel (core-backend/core-vpn), and app categories by tag.

#### Scenario: Classify library log
- **GIVEN** a log tag belonging to the library
- **WHEN** it is classified
- **THEN** it is categorized as a core log

### Requirement: Buffered Log Streams

The system SHALL maintain replay-buffered streams per category with oldest-dropping overflow, emitting parsed messages to subscribers.

#### Scenario: Emit to app stream
- **GIVEN** a parsed line classified as an app log
- **WHEN** it is read
- **THEN** it is emitted on the app log stream for subscribers

### Requirement: Logcat Stream Reading

The system SHALL read the process's logcat output line-by-line, merge multi-line entries such as stack traces, and flush pending logs to file.

#### Scenario: Merge continuation lines
- **GIVEN** a parsed log followed by a continuation line
- **WHEN** the continuation is detected
- **THEN** it is merged into the pending message before emission

### Requirement: Logcat Fallback

The system SHALL activate a Timber file-logging fallback when logcat is blocked or yields no output.

#### Scenario: Fall back on blocked logcat
- **GIVEN** logcat is blocked or returns no lines
- **WHEN** the reader detects this
- **THEN** a Timber file tree is planted to capture logs to file

### Requirement: Log File Rotation And Retention

The system SHALL rotate log files when they reach a maximum size and enforce a maximum folder size by deleting the oldest files.

#### Scenario: Rotate on size limit
- **GIVEN** a log file approaching the size limit
- **WHEN** new log data would exceed it
- **THEN** a new file is created and writing continues into it

#### Scenario: Enforce folder cap
- **GIVEN** the log folder exceeds its maximum size
- **WHEN** a new file is needed
- **THEN** the oldest files are deleted until the folder is under the cap

### Requirement: Log Export

The system SHALL zip log files organized by category for export and share them via a content URI (or scoped storage on newer Android).

#### Scenario: Share zipped logs
- **GIVEN** the user requests log export
- **WHEN** the logs are zipped
- **THEN** a categorized zip is produced and shared via a share intent

### Requirement: Log Deletion

The system SHALL delete all logs by resetting the buffered stream caches, deleting log files, and clearing logcat.

#### Scenario: Delete all logs
- **GIVEN** the user requests deletion
- **WHEN** the delete runs
- **THEN** the buffered caches are reset, files are deleted, and logcat is cleared

### Requirement: Diagnostic Report Generation

The system SHALL generate a diagnostic report from the backend and surface loading/result/error state to the UI.

#### Scenario: Run diagnostics
- **GIVEN** the user runs diagnostics
- **WHEN** the backend returns a report
- **THEN** the report is stored in UI state, or an error is surfaced on failure

### Requirement: Timber Tree Configuration

The system SHALL filter logs by minimum priority per Timber tree and suppress debug logging in release builds.

#### Scenario: Filter below threshold
- **GIVEN** a debug tree with a minimum priority
- **WHEN** a lower-priority log is evaluated
- **THEN** it is reported as not loggable
