# Account & Billing Specification

> Generated by openlore on 2026-06-26
> Source files: `billing/.../net/nymtech/billing/*` (and `model/`, `src/general/`, `src/fdroid/` flavors), `app/.../manager/billing/{BillingManager,NymBillingManager}.kt`, `app/.../ui/screens/account/{info,passphrase,generating,payment,plan}/*`, `app/.../ui/screens/auth/AuthViewModel.kt`, `app/.../manager/backend/{BackendManager,ServiceBackedBackendManager}.kt`

## Purpose

Manages the VPN account lifecycle — credential creation/import via mnemonic passphrase, account registration, and account summary/subscription state — and Google Play in-app subscription billing. Billing is abstracted by build flavor: a Google Play implementation for general builds and a stub for F-Droid builds.

## Requirements

### Requirement: Mnemonic Credential Storage

The system SHALL store a user's mnemonic passphrase credential through the backend manager and expose whether a mnemonic is stored.

#### Scenario: Import valid mnemonic
- **GIVEN** the user submits a valid recovery-phrase mnemonic
- **WHEN** the auth view model handles the submission
- **THEN** the mnemonic is stored via the backend, the account is refreshed, and a save-to-password-manager event is emitted

#### Scenario: Reject invalid mnemonic
- **GIVEN** the user submits an invalid mnemonic
- **WHEN** the submission is handled
- **THEN** an invalid-recovery-phrase error is set in UI state

### Requirement: Account Creation And Registration

The system SHALL support creating a new account or logging in with an existing mnemonic, and SHALL register an account with an optional purchase token.

#### Scenario: Create account flow
- **GIVEN** the generating screen runs in create-account mode
- **WHEN** initialization completes
- **THEN** a new account is created, identity IDs are populated, and the user is routed to plan selection or onward

#### Scenario: Register after purchase
- **GIVEN** a Google Play subscription purchase reaches the purchased state
- **WHEN** the payment view model handles it
- **THEN** the account is registered with the purchase token and a payment-success event is emitted

### Requirement: Billing Initialization

The system SHALL initialize the billing client (connect and query existing purchases) only when billing is available for the build.

#### Scenario: Initialize when available
- **GIVEN** the build supports Google Play billing
- **WHEN** the billing manager is initialized
- **THEN** the billing client connects and active subscription status can be queried

### Requirement: Subscription Product Retrieval

The system SHALL query subscription products from Google Play and expose product id, name, price, and free-trial days.

#### Scenario: Fetch subscription products
- **GIVEN** the plan-selection screen is shown
- **WHEN** subscription products are fetched
- **THEN** the available products with prices and free-trial information are exposed for display

### Requirement: Purchase Flow Execution

The system SHALL launch the Google Play purchase flow for a selected product, associating the purchase with the user's account id.

#### Scenario: Launch purchase
- **GIVEN** a selected product and a non-null user id
- **WHEN** the purchase flow is started
- **THEN** the billing flow is launched with the user id set as the obfuscated account id

### Requirement: Purchase State Tracking

The system SHALL emit purchase-state transitions and handle already-owned and user-canceled outcomes distinctly.

#### Scenario: Already owned
- **GIVEN** a purchase attempt for an item already owned
- **WHEN** the billing result indicates already-owned
- **THEN** a subscription-owned event is emitted

### Requirement: Purchase Acknowledgment

The system SHALL acknowledge purchased, unacknowledged subscriptions.

#### Scenario: Acknowledge a new purchase
- **GIVEN** a purchase in the purchased state that is not yet acknowledged
- **WHEN** purchases are refreshed
- **THEN** the purchase is acknowledged with the billing client

### Requirement: Active Subscription Verification

The system SHALL determine whether an active subscription exists by querying purchased subscriptions matching known product ids.

#### Scenario: Verify at login
- **GIVEN** the user logs in
- **WHEN** active subscription status is queried
- **THEN** it returns true only if a purchased subscription matching a known product id exists

### Requirement: Account Summary And State

The system SHALL retrieve and expose account state and summary, refreshing it on account-state-changed backend events.

#### Scenario: Refresh on account change
- **GIVEN** the backend emits an account-state-changed event
- **WHEN** the manager observes it
- **THEN** the account summary is refreshed and exposed to the UI

### Requirement: Flavor-Based Billing Abstraction

The system SHALL provide billing via build flavor — a Google Play implementation for general builds and a no-op stub for F-Droid builds.

#### Scenario: F-Droid stub
- **GIVEN** the F-Droid flavor
- **WHEN** billing availability is checked
- **THEN** billing reports unavailable and billing methods are no-ops
