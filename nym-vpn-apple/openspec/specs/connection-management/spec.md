# Connection Management Specification

> Generated by openlore on 2026-06-26
> Source files: `Services/Sources/Services/ConnectionManager/*`, `Services/Sources/Services/Tunnels/*`, `Services/Sources/Services/TunnelMixnet/Config/MixnetConfig.swift`, `ServicesMutual/Sources/TunnelStatus/*`, `ServicesMutual/Sources/ConnectionTypes/*`

## Purpose

Manages the VPN tunnel lifecycle — initiating and terminating connections, maintaining connection state from user initiation through the platform-specific backend, and reporting tunnel status with metadata. Handles two tunnel types — mixnet 5-hop (entry/exit gateway pair) and WireGuard 2-hop (single VPN gateway) — with entry/exit selection wired into the tunnel configuration. The implementation diverges at the platform boundary: iOS uses a NetworkExtension `NETunnelProviderManager`/`NETunnelProviderSession`, while macOS drives a gRPC daemon.

## Requirements

### Requirement: Tunnel Status Publication

The `ConnectionManager` SHALL publish observable tunnel status transitions via Combine as a `TunnelStatus` enum, covering connected, connecting, disconnected, disconnecting, error, reasserting, restarting, offline, offlineReconnect, and unknown.

#### Scenario: Transition to connecting
- **GIVEN** a tunnel in the disconnected state
- **WHEN** the tunnel begins connecting
- **THEN** the published tunnel status transitions to `.connecting` and status is monitored

#### Scenario: Transition to connected
- **GIVEN** a tunnel in the connecting state
- **WHEN** the connection succeeds
- **THEN** the published tunnel status becomes `.connected` and the retry attempt is cleared

### Requirement: Connect/Disconnect Toggle

The `ConnectionManager` SHALL provide a `connectDisconnect()` method that toggles the tunnel based on current status, with distinct iOS (NetworkExtension) and macOS (gRPC) implementations.

#### Scenario: Disconnect an active tunnel (iOS)
- **GIVEN** an active tunnel in a connected/connecting/error-like status
- **WHEN** `connectDisconnect()` is called
- **THEN** on-demand is disabled, the configuration is saved, and the tunnel is disconnected

#### Scenario: Connect from disconnected (macOS)
- **GIVEN** the tunnel status is disconnected or disconnecting
- **WHEN** `connectDisconnect()` is called
- **THEN** the tunnel start path invokes the gRPC manager connect

### Requirement: Entry/Exit Gateway Selection

The `ConnectionManager` SHALL allow selecting entry and exit gateways via `setEntryGateway(_:)` and `setExitGateway(_:)`, persisting them to `ConnectionStorage` and propagating changes to the backend (a tunnel provider message on iOS, a gRPC call on macOS).

#### Scenario: Change entry gateway
- **GIVEN** an entry gateway is currently selected
- **WHEN** a new entry gateway is set
- **THEN** the entry selection updates, is persisted, and a set-entry-point message is sent to the active tunnel

### Requirement: Mixnet vs WireGuard Mode

The `ConnectionManager` SHALL distinguish mixnet 5-hop from WireGuard 2-hop, controlled by `setTwoHop(_:)` and reflected in the connection type and the generated config.

#### Scenario: Enable two-hop
- **GIVEN** the connection type is mixnet 5-hop
- **WHEN** `setTwoHop(true)` is called
- **THEN** the connection type becomes WireGuard, the two-hop flag is set, and the next connection uses two-hop

### Requirement: Connecting State Reporting

The `ConnectionManager` SHALL expose fine-grained handshake progress via a `TunnelConnectingState` enum, covering resolving API addresses, awaiting account readiness, refreshing gateways, selecting gateways, registering with gateways, and connecting the tunnel.

#### Scenario: Report gateway selection phase
- **GIVEN** the tunnel is connecting
- **WHEN** the backend reports a selecting-gateways phase
- **THEN** the connecting-state property is updated and published for the UI

### Requirement: Configuration Generation

The `ConnectionManager` SHALL generate a configuration object encapsulating entry/exit selection, tunnel type, and feature settings (QUIC, ad-blocking, custom DNS, mixnet tuning), apply it on connect, and persist setting changes.

#### Scenario: Build config on connect
- **GIVEN** the user initiates a connection
- **WHEN** the config is generated
- **THEN** it includes the entry gateway, exit router, two-hop flag, and feature settings, and is passed to the tunnels manager

#### Scenario: Live setting update without reconnect
- **GIVEN** a connected tunnel
- **WHEN** a feature setting such as ad-blocking is changed
- **THEN** a corresponding tunnel provider message updates the running extension without reconnecting

### Requirement: Retry And Error Tracking

The `ConnectionManager` SHALL publish connection retry state and the last encountered error, sourced from the tunnel or gRPC manager.

#### Scenario: Surface retry attempts
- **GIVEN** the tunnel is connecting with retry logic
- **WHEN** the backend reports an increased retry attempt
- **THEN** the published retry-attempt value is updated for display

### Requirement: Gateway Independence Consent

The `ConnectionManager` SHALL handle relaxed gateway-independence consent via `acceptRelaxedGatewayIndependence()`, disabling the independence requirement and re-initiating the connection when a "needs relaxed independence criteria" error is encountered.

#### Scenario: Accept relaxed criteria
- **GIVEN** the tunnel is in an error state requiring relaxed independence criteria
- **WHEN** the relaxed-independence consent is accepted
- **THEN** the backend independence requirement is disabled and the connection is restarted

### Requirement: Connection Metadata

The `ConnectionManager` SHALL expose real-time connection metadata (`ConnectionInfoData`) including the actual entry/exit gateway IDs chosen by the backend and the active tunnel type.

#### Scenario: Report selected gateways
- **GIVEN** an active connected tunnel
- **WHEN** connection info data is decoded from the backend
- **THEN** the metadata exposes the entry/exit gateway IDs and tunnel type for the UI
