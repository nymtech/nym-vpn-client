# Account & Credentials Specification

> Generated by openlore on 2026-06-26

## Purpose

Manages account registration, secure credential storage, authentication, subscription state, and device/account identity. Supports login via mnemonic, account creation, biometric authentication, and in-app purchases with subscription tracking. Account summary refresh is policy-gated with caching and platform-specific polling.

## Requirements

### Requirement: Credential Storage

The system SHALL store account mnemonics securely via the account storage backend with environment-specific scoping.

#### Scenario: Store mnemonic on account creation
- **GIVEN** a user registers with a mnemonic
- **WHEN** account creation runs
- **THEN** the mnemonic is stored and a stored-mnemonic check subsequently returns true

#### Scenario: Persist across restart
- **GIVEN** a mnemonic was stored
- **WHEN** the app restarts and reads the stored mnemonic
- **THEN** the persisted mnemonic is returned

### Requirement: Mnemonic Login

The system SHALL accept a mnemonic credential and log in, retrying when the account store is temporarily busy.

#### Scenario: Login with valid mnemonic
- **GIVEN** a valid mnemonic is imported
- **WHEN** the credential is added
- **THEN** the mnemonic is wrapped as a VPN credential and passed to the account storage backend

#### Scenario: Retry on busy store
- **GIVEN** the account store is temporarily busy
- **WHEN** login is attempted
- **THEN** the operation retries with backoff before failing

### Requirement: Account Token Management

The system SHALL manage access tokens per environment, persisting the token after registration keyed by the current environment.

#### Scenario: Persist token after registration
- **GIVEN** registration completes with an account token
- **WHEN** registration finishes
- **THEN** the token is persisted keyed by the current environment

### Requirement: Biometric Authentication

The system SHALL detect available biometric type and authenticate the user via the platform local-authentication policy.

#### Scenario: Detect biometric type
- **GIVEN** a device with Face ID
- **WHEN** available-biometric detection runs
- **THEN** it reports Face ID as available

#### Scenario: Authenticate with biometrics
- **GIVEN** the user triggers biometric authentication
- **WHEN** the authentication policy is evaluated
- **THEN** it resolves to success or throws an authentication error

### Requirement: Subscription State Tracking

The system SHALL maintain an account summary (active flag, valid-until date, subscription status, traffic limits) and publish it, syncing to local settings.

#### Scenario: Active subscription
- **GIVEN** the backend returns an active account summary
- **WHEN** the summary is assigned
- **THEN** it is published and synced to local settings, and the account reads as active

#### Scenario: Expiry fallback
- **GIVEN** the active flag is false
- **WHEN** active status is evaluated
- **THEN** it falls back to comparing the valid-until date against the current date

### Requirement: In-App Purchase Processing

The system SHALL process StoreKit purchases, verify and finish transactions, and track auto-renewal status.

#### Scenario: Successful verified purchase
- **GIVEN** a purchase is initiated with a product and account token
- **WHEN** the purchase returns a verified success
- **THEN** the transaction is finished and a success outcome is returned

### Requirement: Account Summary Refresh Policy

The system SHALL refresh the account summary conditionally — forcing a network refresh when inactive, skipping when the cache is fresh and active — with platform-specific poll delays.

#### Scenario: Force refresh when inactive
- **GIVEN** a forced refresh is requested
- **WHEN** the refresh policy is evaluated
- **THEN** a network fetch always executes

#### Scenario: Skip refresh when fresh
- **GIVEN** the account is active and the cache is within its freshness window
- **WHEN** a non-forced refresh is requested
- **THEN** the cached summary is used and the network fetch is skipped

### Requirement: Device And Account Identity

The system SHALL query and publish device identity and account identity from the platform backend.

#### Scenario: Populate identities
- **GIVEN** a credential import or successful registration
- **WHEN** identity updates run
- **THEN** the device identifier and account identifier are populated from the backend
