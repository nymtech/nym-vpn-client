# Presentation UI Specification

> Generated by openlore on 2026-06-26

## Purpose

The SwiftUI presentation layer for the iOS/iPadOS/macOS client: a semantic design system (color tokens, typography, spacing), a reusable component library spanning two generations (legacy "25" and modern "26"), screen composition (home/connection flow, onboarding, settings hierarchy), appearance switching (dark/light/automatic), app-icon variants, and accessibility support. This domain owns visual design and screen orchestration, not core VPN business logic.

## Requirements

### Requirement: Semantic Color Tokens

The presentation layer SHALL expose semantic color tokens (primary, error, success, warning, info, link, surface, border, text variants) that resolve per appearance.

#### Scenario: Color resolves per appearance
- **GIVEN** a view rendered in dark mode
- **WHEN** it uses a semantic text/primary token
- **THEN** the dark-appearance color value is applied

### Requirement: Typographic System

The presentation layer SHALL provide a typed typography system with custom font families and named text styles, applied via view modifiers and respecting dynamic type.

#### Scenario: Apply a named text style
- **GIVEN** a heading element
- **WHEN** a named heading text style is applied
- **THEN** the corresponding font, size, and tracking are used

### Requirement: Spacing System

The presentation layer SHALL enforce consistent spacing via named spacing tokens applied to padding, margins, and layout.

#### Scenario: Consistent component spacing
- **GIVEN** a button group
- **WHEN** it is laid out
- **THEN** the named spacing tokens determine the padding and inter-element spacing

### Requirement: Reusable Component Library

The presentation layer SHALL provide a library of themed, stateful reusable components (buttons, connect button, snackbar, action dialog) with hover/disabled/loading states.

#### Scenario: Primary button states
- **GIVEN** a primary button
- **WHEN** it becomes disabled
- **THEN** it renders a disabled appearance and stops responding to interaction

#### Scenario: Critical snackbar with action
- **GIVEN** a snackbar styled critical with an action
- **WHEN** the user taps the action
- **THEN** the action callback fires and the snackbar dismisses

### Requirement: Appearance Switching

The presentation layer SHALL support dark/light/automatic appearance selected from settings, persisted in app storage, and applied via the preferred color scheme.

#### Scenario: Select dark mode
- **GIVEN** the user selects dark mode in display settings
- **WHEN** the appearance is updated
- **THEN** it is persisted and the dark color scheme is applied immediately

#### Scenario: Automatic follows system
- **GIVEN** the appearance is set to automatic
- **WHEN** no explicit scheme is forced
- **THEN** the system color scheme is followed

### Requirement: App Icon Variants

The presentation layer SHALL support alternate app icons selectable in settings, mapping each variant to its alternate icon name and preview.

#### Scenario: Select an alternate icon
- **GIVEN** the app-icon settings screen
- **WHEN** the user selects an alternate icon
- **THEN** the alternate icon name is applied and the selection persists

### Requirement: Screen Navigation

The presentation layer SHALL orchestrate multi-screen navigation across the home/connection flow and the settings hierarchy, including modal overlays for blocking decisions.

#### Scenario: Navigate to settings
- **GIVEN** the home screen
- **WHEN** the user opens settings
- **THEN** the settings sub-graph is presented via its flow coordinator

#### Scenario: Blocking modal for connection failure
- **GIVEN** a connection error that requires explicit user action
- **WHEN** the failure is surfaced
- **THEN** a blocking modal overlay is presented instead of a transient snackbar

### Requirement: Reactive State Management

The presentation layer SHALL drive view updates from observable view models and shared environment managers, with persistent settings via app storage.

#### Scenario: Cascade state update
- **GIVEN** an observable view model bound to a shared manager
- **WHEN** the underlying state changes
- **THEN** dependent views re-render reactively

### Requirement: Accessibility Support

The presentation layer SHALL provide accessibility labels/hints, VoiceOver-aware focusability, and focus-effect handling for custom controls.

#### Scenario: VoiceOver focus
- **GIVEN** a custom button
- **WHEN** VoiceOver is enabled
- **THEN** the button becomes focusable and its label is announced

### Requirement: Two-Generation Component Coexistence

The presentation layer SHALL maintain two coexisting component generations (legacy "25" and modern "26") to allow gradual migration while preserving visual consistency.

#### Scenario: Mixed-generation screens
- **GIVEN** a screen built with legacy components
- **WHEN** content is ported to modern components
- **THEN** visual consistency is preserved while newer primitives are used
