> Generated by openlore on 2026-06-26

## Purpose

Describes the structural composition of the Apple client: the multi-module Swift Package workspace, the iOS/macOS/mutual platform split, the manager-based service layer exposed through observable view models, the dual tunnel backends behind a unified API, and the app-group sharing used between the app, the tunnel extension, and the widgets.

## Requirements

### Requirement: Modular Package Layout

The system SHALL be organized as multiple Swift Package modules with separated concerns (UI design system, components, screens, routes, and service layers), composed in an Xcode workspace.

#### Scenario: Add functionality in the right module
- **GIVEN** a new capability is added
- **WHEN** it is implemented
- **THEN** it is placed in the module matching its concern (UI vs services vs routing) rather than in a monolith

### Requirement: Platform Module Separation

The system SHALL separate platform-specific code into iOS and macOS service modules and share cross-platform types in a mutual module.

#### Scenario: Shared types in mutual module
- **GIVEN** a type used by both platforms (e.g. tunnel status, connection types)
- **WHEN** it is defined
- **THEN** it lives in the mutual module while platform-only code lives in the platform modules

### Requirement: Manager-Based Service Layer

The system SHALL implement business logic as observable manager objects (connection, gateway, credentials, configuration, etc.) consumed by SwiftUI views through view models and the environment.

#### Scenario: View observes a manager
- **GIVEN** a screen needs domain state
- **WHEN** it renders
- **THEN** it observes the relevant manager via a view model or the environment and updates reactively

### Requirement: Unified Connection API Over Dual Backends

The system SHALL expose a single connection-management API whose implementation diverges into a NetworkExtension path (iOS) and a gRPC daemon path (macOS).

#### Scenario: Same API, platform backend
- **GIVEN** a caller invokes the connection API
- **WHEN** it runs on iOS versus macOS
- **THEN** the unified API delegates to the NetworkExtension or the gRPC daemon respectively

### Requirement: App Group Sharing

The system SHALL share state across the app, the tunnel extension, and the widgets via an app-group container (shared defaults and filesystem paths).

#### Scenario: Share status with widgets
- **GIVEN** the app updates VPN status
- **WHEN** a widget reads its data
- **THEN** it reads the shared app-group values written by the app

### Requirement: Core Library Integration

The system SHALL integrate the Nym mixnet core as an external dependency — a bundled mixnet library on iOS and the daemon binary plus generated gRPC bindings on macOS — updated through repository scripts.

#### Scenario: Core update workflow
- **GIVEN** a new core/daemon version
- **WHEN** the update script is run
- **THEN** the bundled library/checksum (iOS) and daemon/proto bindings (macOS) are updated together
