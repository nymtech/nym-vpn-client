## Purpose

Collects anonymous VPN usage statistics by observing the tunnel state machine, deriving per-connection "session" records (connection time, session duration bucket, retries, exit gateway, errors), persisting them to a local SQLite database, and asynchronously reporting them to a backend via the statistics API client. It maintains an anonymous, seed-derived client identity and enforces collection/sending policies (enable/disable, direct-sending-while-disconnected) at runtime.

## Requirements

### Requirement: SessionStateMachine

The system SHALL maintain an internal session state machine that consumes tunnel usage events (connect/disconnect requests and Connecting/Connected/Disconnecting/Disconnected/Error/Offline state transitions) and SHALL produce a finished session record only once a session terminates, capturing connection duration, session duration, disconnection duration, retry attempt, tunnel type, exit gateway id/country code, and any error string.

#### Scenario: Successful session lifecycle is recorded
- **GIVEN** the usage handler is in `NoSession`
- **WHEN** it receives `ConnectRequest`, then `Connecting`, then `Connected`, then `DisconnectRequest`, then `Disconnecting`, then `Disconnected`
- **THEN** a `SessionReport` is stored containing the measured connection time, bucketized session duration, disconnection time, retry attempt, tunnel type and exit gateway, with no error, and the state returns to `NoSession`

#### Scenario: Connection that never establishes
- **GIVEN** the handler is in `Connecting` (no `Connected` was received)
- **WHEN** a `DisconnectRequest` followed by `Disconnected` is received
- **THEN** a session is stored with `session_duration_min` of 0 and the captured connecting-time metadata

### Requirement: ErrorAndRecoverableFailureCapture

The system SHALL persist a session report annotated with an error marker when the tunnel reports an error, goes offline, or experiences a connecting hiccup, using the constants `RECOVERABLE_ERROR_<id>` for connection hiccups (a new session is linked to the previous via a generated `follow_up_id`), `OFFLINE_ENDING` for offline transitions, and `SHUTDOWN_REQUESTED` for sessions still active at shutdown.

#### Scenario: Irrecoverable error during an ongoing session
- **GIVEN** the handler is in `OnGoing`
- **WHEN** an `Error` event is received
- **THEN** a session report is stored with the error string set and the state returns to `NoSession`

#### Scenario: Connecting hiccup links sessions
- **GIVEN** the handler is in `OnGoing`
- **WHEN** a new `Connecting` event arrives (a reconnect hiccup)
- **THEN** the current session is stored with a `RECOVERABLE_ERROR_<id>` error and the next `Connecting` session carries that id as its `follow_up_id`

### Requirement: SessionDurationBucketization

The system SHALL bucketize raw session duration into coarse minute buckets before reporting, returning 0 for a zero-length session, mapping durations under the defined thresholds (1, 3, 5, 7, 9, 11, 15, 20, 30, 45, 60 minutes) to the next threshold, and rounding longer sessions up to the next multiple of 60 minutes.

#### Scenario: Sub-minute session bucketized
- **GIVEN** a session shorter than 60 seconds
- **WHEN** the report is built
- **THEN** `session_duration_min` is 1

#### Scenario: Zero-length session bucketized
- **GIVEN** a session of 0 seconds (e.g. a connection that never established)
- **WHEN** the report is built
- **THEN** `session_duration_min` is 0

### Requirement: PersistentSessionStorage

The system SHALL persist pending session reports in a local SQLite database (`stats.db`), running migrations on init, restricting the database file to owner read/write (mode 0600) on Unix, and SHALL provide insert, paged read (LIMIT 5), per-id delete, and delete-all operations for pending reports.

#### Scenario: Pending report stored and later deleted
- **GIVEN** storage initialized successfully
- **WHEN** a finished session is inserted and then successfully sent
- **THEN** the report is inserted into `pending_session_report` and removed by id after successful sending

#### Scenario: Storage init failure disables collection
- **GIVEN** storage initialization fails
- **WHEN** the controller is constructed
- **THEN** no `StatisticsHandler` is created and statistics collection is disabled

### Requirement: AnonymousClientIdentity

The system SHALL maintain an anonymous client identity derived from a randomly generated 20-character alphanumeric seed stored in the database, lazily creating the seed on first access, exposing it as a `NetworkStatisticsIdentity` (seed plus derived id from `generate_vpn_client_stats_id`), and SHALL support resetting the seed.

#### Scenario: Seed lazily created on first read
- **GIVEN** no seed exists in storage
- **WHEN** `get_seed` is requested
- **THEN** a new random seed is generated, persisted, and returned together with its derived id

#### Scenario: Seed reset
- **GIVEN** a seed exists
- **WHEN** `reset_seed` is called
- **THEN** the existing seed is removed and a new (or provided custom) seed is initialized

### Requirement: ReportSendingPolicyAndCadence

The system SHALL only send reports when the tunnel is `Connected`, or when it is `Disconnected` and direct sending is allowed, and SHALL schedule sending using a randomized small delay (0–30s) for imminent attempts and a randomized big delay (15–120 min) between successful cycles, retrying up to 5 times on send failure before backing off to the big delay.

#### Scenario: Successful send schedules long backoff
- **GIVEN** the sending task sent all pending reports successfully
- **WHEN** the cycle completes
- **THEN** the retry counter is reset and the next attempt is scheduled after a randomized big delay (15–120 minutes)

#### Scenario: Send failures retried then backed off
- **GIVEN** report sending fails
- **WHEN** failures occur fewer than 5 consecutive times
- **THEN** sending is retried after a small delay, and once 5 retries are exhausted the next attempt is deferred to a big delay and the counter resets

#### Scenario: Active-device ping when nothing pending
- **GIVEN** there are no pending reports and the tunnel is `Connected`
- **WHEN** a sending cycle runs
- **THEN** an `ActiveDeviceReport` is posted instead of session reports

### Requirement: RuntimeCollectionControl

The system SHALL accept runtime commands to enable/disable collection and toggle direct sending while disconnected; disabling collection SHALL stop the sending task and delete all stored statistics, while enabling mid-session SHALL place the usage handler into a `Standby` state until a new session starts.

#### Scenario: Disabling collection wipes storage
- **GIVEN** collection is enabled with stored statistics
- **WHEN** a `DisableCollection` command is handled
- **THEN** the sending task is cancelled, the usage state resets to `NoSession`, and all stored statistics are deleted

#### Scenario: Enabling mid-session enters standby
- **GIVEN** the handler is in an active session and collection was disabled
- **WHEN** `EnableCollection` is handled
- **THEN** the usage handler transitions to `Standby` and does not fabricate a session until a fresh one begins

### Requirement: GracefulShutdownPersistence

The system SHALL, on cancellation, flush any in-flight session as a finished report marked `SHUTDOWN_REQUESTED`, allowing up to a bounded (2 second) window for the handler to wrap up before closing storage.

#### Scenario: In-flight session flushed at shutdown
- **GIVEN** a session is active (Connecting, OnGoing, or Disconnecting)
- **WHEN** the controller receives a cancellation signal
- **THEN** the active session is stored with the `SHUTDOWN_REQUESTED` error marker before the controller exits

## Technical Notes

- **Implementation**: `src/controller.rs` (event/command loop, identity), `src/handler/usage.rs` (session state machine + bucketization), `src/handler/report_sending.rs` (sending cadence, retries, policy), `src/storage/sqlite.rs` and `src/storage/mod.rs` (SQLite persistence, seed, 0600 permissions), `src/events.rs` and `src/commands.rs` (public senders), `src/error.rs`.
- **Dependencies**: `nym-statistics-api-client` (HTTP reporting), `nym-statistics-common` (report DTOs `VpnClientStatsReportV2`, `ActiveDeviceReport`, `StaticInformationReport`, `generate_vpn_client_stats_id`), `nym-vpn-lib-types` (`TunnelState`, `NetworkStatisticsConfig`, `NetworkStatisticsIdentity`), `nym-sqlx-pool-guard`, `nym-bin-common` (build version), plus `sqlx` (sqlite), `sysinfo` (OS/arch info), `tokio`, `tokio-util`, `rand`, `time`, `strum`. In the workspace this crate is the central usage-telemetry collector driven by the VPN tunnel state machine.
