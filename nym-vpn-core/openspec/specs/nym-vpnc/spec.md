# nym-vpnc Specification

> Generated by openlore on 2026-06-26
> Source files: Cargo.toml, src/main.rs, src/commands/mod.rs, src/commands/session.rs, src/table_style.rs

## Purpose

nym-vpnc is the NymVPN command-line client. It is a thin clap-based CLI that connects to the running nym-vpnd daemon through a gRPC `RpcClient` (over the local IPC transport) and exposes subcommands to connect/disconnect/reconnect the tunnel, inspect status and info, and manage gateways, DNS, LAN policy, ad-blocking, tunnel options, accounts, devices, network selection, sentry, SOCKS5, geo-exclusion, network statistics, diagnostics, and split tunneling. It can also run an interactive REPL session that authenticates once and reuses the connection for subsequent commands.

## Requirements

### Requirement: RpcClientConnection

The client SHALL create a single gRPC `RpcClient` to the daemon at startup and SHALL dispatch the parsed subcommand against it.

#### Scenario: ConnectAtStartup
- **GIVEN** the user invokes any nym-vpnc subcommand
- **WHEN** `main` runs `RpcClient::new().await`
- **THEN** an RPC connection to the daemon is established (via `nym-ipc`), and on failure the client returns a "Failed to create RPC client" error

### Requirement: TunnelControlCommands

The client SHALL provide `connect`, `disconnect`, and `reconnect` subcommands that invoke the corresponding daemon RPCs, with optional `--wait` blocking until a terminal tunnel state is observed.

#### Scenario: ConnectAndWait
- **GIVEN** the user runs `connect --wait`
- **WHEN** the client calls `connect_tunnel` then streams events via `listen_to_events`
- **THEN** it prints each new state and returns when `TunnelState::Connected` is reached, or errors on `TunnelState::Error`

#### Scenario: DisconnectAndWait
- **GIVEN** the user runs `disconnect --wait`
- **WHEN** the client subscribes to events, reads the current state, and calls `disconnect_tunnel`
- **THEN** it returns once a `Disconnected` or `Offline` state is observed (returning immediately if already in such a state), or errors on `TunnelState::Error`

### Requirement: StatusAndInfoReporting

The client SHALL report the current tunnel state and daemon/network info, with an optional continuous listen mode for status.

#### Scenario: StatusListen
- **GIVEN** the user runs `status --listen`
- **WHEN** the client prints the current state and then consumes the event stream
- **THEN** it prints each `NewState` and pretty-prints JSON for each `ConfigChanged` event until interrupted

#### Scenario: InfoOutput
- **GIVEN** the user runs `info`
- **WHEN** the client calls `get_info`
- **THEN** it prints daemon version/build details and the resolved Nym network, contract addresses, and API URLs

### Requirement: ConfigurationSubcommandTree

The client SHALL expose a structured subcommand tree delegating to per-feature modules, each of which executes against the shared `RpcClient`.

#### Scenario: DelegateToFeatureModule
- **GIVEN** the user runs a subcommand such as `gateway`, `dns`, `tunnel`, `account`, `device`, `network`, `sentry`, `socks5`, `geo-exclusion`, or `network-stats`
- **WHEN** `Command::execute` matches the variant
- **THEN** the matching `commands::<feature>` handler runs its corresponding daemon RPC

#### Scenario: SplitTunnelOnlyOnDesktop
- **GIVEN** the client is built for Linux, macOS, or Windows
- **WHEN** the `split-tunnel` subcommand is available
- **THEN** it delegates to `commands::split_tunnel`; the subcommand is compiled out on other platforms

### Requirement: InteractiveSession

The client SHALL provide a `start-session` REPL that parses each input line as a subcommand (multicall) and reuses the same `RpcClient` until the user exits.

#### Scenario: ReplLoop
- **GIVEN** the user runs `start-session`
- **WHEN** the user types a command line at the `$ ` prompt
- **THEN** the line is split with `shlex`, parsed via the multicall `SessionCli`, and executed against the cloned `RpcClient`

#### Scenario: ExitSession
- **GIVEN** an interactive session is running
- **WHEN** the user enters `exit-session` (or `exit`)
- **THEN** the REPL prints "Exiting ..." and the loop terminates; nested `start-session` is rejected with a message

### Requirement: OutputFormatting

The client SHALL accept a global `--table-style` option to control tabular output rendering.

#### Scenario: TableStyleOption
- **GIVEN** the user passes `--table-style <style>` to any subcommand
- **WHEN** clap parses `ProgramArgs`
- **THEN** the selected `TableStyle` (default applied if omitted) governs `tabled`-rendered output

## Technical Notes

- **Implementation**: `src/main.rs` (`ProgramArgs`, `Command` enum and `execute`, tunnel control/status/info helpers), `src/commands/mod.rs` (feature module declarations), `src/commands/session.rs` (REPL), per-feature modules under `src/commands/` (gateway, dns, account, device, network, sentry, socks5, geo_exclusion, network_stats, split_tunnel, tunnel, lan, ad_block, diagnostic).
- **Dependencies**: Talks to nym-vpnd exclusively through `nym-vpn-proto`'s `RpcClient` (features `rpc_client`, `conversions`), which uses `nym-ipc` under the hood for the local socket/pipe transport. Uses `nym-vpn-lib-types` for shared `TunnelEvent`/`TunnelState`/`VpnServiceInfo` domain types, `nym-diagnostic` for the diagnostic subcommand, `clap` for parsing, `tabled` for table output, `shlex` for REPL line splitting, and `tokio`/`tokio-stream` for async streaming. Within the workspace it is the terminal counterpart to the GUI app (nym-vpn-app), both clients of nym-vpnd.
