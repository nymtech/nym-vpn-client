## Purpose

`nym-ifconfig` provides low-level, platform-specific configuration of network interfaces (tun/utun devices) for the Nym VPN client. It exposes operations to create and destroy interfaces, assign and remove IPv4/IPv6 addresses (including point-to-point destinations), read and set MTU, query and toggle interface flags (up/down), and on macOS manage IPv6 neighbour-discovery (ND6) settings. It abstracts over Apple (macOS/iOS) BSD `ioctl`/control-socket APIs and Linux/Android netlink (`rtnetlink`) and `/dev/net/tun`, presenting a `Session` and `Tun`/`Utun` API per platform.

## Requirements

### Requirement: TunDeviceCreation

The system MUST be able to create or wrap a tunnel device file descriptor on each supported platform, exposing its kernel-assigned interface name.

On Linux/Android, `Tun::new` opens `/dev/net/tun` with `O_RDWR` and issues the `TUNSETIFF` ioctl with `IFF_TUN`; `new_with_parameters` allows a caller-provided name and flags, rejecting names longer than `IFNAMSIZ - 1`. On macOS, `Utun::new` opens a `System`/`KextControl` datagram socket and connects to the `com.apple.net.utun_control` kernel control. Both platforms also support wrapping an externally owned descriptor via `new_from_borrowed_fd`.

#### Scenario: CreateLinuxTunInterface
- **GIVEN** a Linux/Android host with `/dev/net/tun` available
- **WHEN** the caller invokes `Tun::new()`
- **THEN** the device is opened with `IFF_TUN` flags and `name()` returns the kernel-assigned interface name

#### Scenario: RejectOverlongInterfaceName
- **GIVEN** a requested interface name longer than `IFNAMSIZ - 1` bytes
- **WHEN** the caller invokes `Tun::new_with_parameters`
- **THEN** the call fails with `TunErrorKind::InterfaceNameTooLong`

#### Scenario: CreateMacosUtun
- **GIVEN** a macOS host
- **WHEN** the caller invokes `Utun::new()`
- **THEN** a socket connected to `com.apple.net.utun_control` is returned and `name()` reads the interface name via the `UtunIfname` socket option

### Requirement: InterfaceLifecycleManagement

On macOS the system SHALL be able to create and destroy named network interfaces through control sockets.

`Session::create_interface` issues `SIOCIFCREATE2` for a given name (e.g. `feth`/`utun`) and returns the actual interface name assigned by the kernel; `Session::destroy_interface` issues `SIOCIFDESTROY` for the named interface.

#### Scenario: CreateAndDestroyInterface
- **GIVEN** a macOS `Session`
- **WHEN** `create_interface("feth")` is called and later `destroy_interface` with the returned name
- **THEN** the interface is created (name starting with `feth`) and subsequently removed

### Requirement: IpAddressAssignment

The system MUST assign and remove IPv4 and IPv6 addresses on a named interface, supporting point-to-point destination addresses.

On Linux, `Session::add_address` resolves the interface index via netlink, adds the address with prefix, and when a `destination` is given rewrites the address attribute to set a peer (equivalent to `ip address add <addr> peer <dest> dev <if>`); `remove_address` deletes the address. On macOS, `add_address` takes an `AddAddressRequest::V4`/`V6` and issues `SIOCAIFADDR`/`SIOCAIFADDR_IN6` with address, netmask/prefix mask, optional destination/broadcast, and (for IPv6) lifetime and flags; `remove_address` issues `SIOCDIFADDR`/`SIOCDIFADDR_IN6`.

#### Scenario: AddPointToPointIpv4
- **GIVEN** an existing tun interface
- **WHEN** `add_address` is called with an IPv4 network and a destination address
- **THEN** the address is present in `addresses()` with the destination recorded as the peer

#### Scenario: RemoveIpv6Address
- **GIVEN** an interface with an assigned IPv6 address
- **WHEN** `remove_address` is called with that IP
- **THEN** the address no longer appears in `addresses()`

#### Scenario: MacosIpv6PrefixNotUpdatedInPlace
- **GIVEN** an existing IPv6 address with prefix /128 on a macOS interface
- **WHEN** `add_address` is called again with the same IP but prefix /64
- **THEN** the prefix remains /128 (macOS 14.7+ does not update an existing IPv6 prefix; the address must be removed first), per documented platform behavior

### Requirement: AddressEnumeration

The system MUST enumerate the IP addresses currently assigned to a named interface, including any point-to-point destination (and on macOS, broadcast) address.

On Linux, `addresses` reads address messages filtered by link index and reconciles `Address`/`Local` attributes into an `InterfaceIpAddrEntry { address, destination }`. On macOS, `addresses` iterates `getifaddrs()` filtered by interface name, converting `SockaddrStorage` to addresses and building `InterfaceIpAddrEntry { address (with netmask-derived prefix), broadcast, destination }`.

#### Scenario: ListAssignedAddresses
- **GIVEN** an interface with one or more assigned addresses
- **WHEN** `addresses(interface)` is called
- **THEN** a vector of `InterfaceIpAddrEntry` reflecting the assigned addresses (and destinations) is returned

### Requirement: MtuConfiguration

The system MUST read and set the MTU of a named interface.

On Linux, `mtu` reads the `Mtu` link attribute via netlink (returning `MtuNotFound` if absent) and `set_mtu` issues a link-set with the new MTU. On macOS, `mtu`/`set_mtu` use `SIOCGIFMTU`/`SIOCSIFMTU` ioctls on a control socket.

#### Scenario: SetThenReadMtu
- **GIVEN** an existing interface
- **WHEN** `set_mtu(interface, value)` is called followed by `mtu(interface)`
- **THEN** the returned MTU equals the value that was set

### Requirement: InterfaceFlagsControl

The system MUST query interface flags and bring interfaces administratively up or down.

On Linux, `interface_flags` reads the link header flags, while `up`/`down` issue link-set with the up/down state. On macOS, `interface_flags`/`set_interface_flags` use `SIOCGIFFLAGS`/`SIOCSIFFLAGS` ioctls.

#### Scenario: BringInterfaceUpThenDown
- **GIVEN** an interface that is administratively down
- **WHEN** `up(interface)` is called, then `down(interface)`
- **THEN** the `Up` flag is observed set after `up` and cleared after `down`

### Requirement: Ipv6NeighborDiscoveryControl

On macOS the system SHALL read IPv6 neighbour-discovery (ND6) info and set ND6 flags for an interface.

`Session::nd6_info` issues `SIOCGIFINFO_IN6` and returns `Nd6Info` (link/max MTU, reachability timers, flags, etc.); `Session::set_nd6_flags` issues `SIOCSIFINFO_FLAGS` with the chosen `Nd6Flags` (e.g. `ND6_IFF_PERFORMNUD`, `ND6_IFF_DAD`).

#### Scenario: ToggleNd6Flag
- **GIVEN** a macOS interface with current ND6 flags
- **WHEN** `set_nd6_flags` is called with a modified flag set and `nd6_info` is read back
- **THEN** the read-back flags equal the flags that were set

## Technical Notes

- **Implementation**: Platform split via `cfg`: `src/linux/{session.rs,tun.rs,sys.rs}` (Linux/Android) and `src/apple/{session.rs,utun.rs,ctl_sockets.rs,sys.rs}` (macOS/iOS). `src/copy_into.rs` provides safe truncation of interface names into `[c_char; IFNAMSIZ]` buffers. `src/error.rs` defines the shared `Error`/`ErrorKind`/`Result` (non-Windows); `Tun` has its own `TunError`/`TunErrorKind`. On macOS `CtlSockets` caches one datagram control socket per address family (Inet/Inet6).
- **Dependencies**: `nix` (ioctl/socket/net/fs syscalls, `ifaddrs`), `ipnetwork` (address/prefix types), and on Linux `rtnetlink` + `futures` + `tokio` + `tokio-util` (async netlink session with a cancellation `DropGuard`), on macOS `bitflags` (Ipv6/ND6 flag sets). No dependencies on other `nym-*` crates. Within the workspace it is the low-level interface-configuration primitive consumed by higher-level tunnel/routing code (alongside `nym-wg-go` which runs the WireGuard data plane over the configured tun device).
