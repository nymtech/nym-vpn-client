# nym-dns Specification

> Generated by openlore on 2026-06-26
> Source files: src/lib.rs, src/macos.rs, src/android.rs, src/linux/mod.rs, src/linux/resolvconf.rs, src/linux/systemd_resolved.rs, src/linux/network_manager.rs, src/linux/static_resolv_conf.rs, src/windows/mod.rs, src/windows/dnsapi.rs

## Purpose

Sets and continuously enforces the system DNS configuration so that the VPN's desired DNS servers are used while connected, and restores the previous configuration on reset. It abstracts wildly different OS DNS mechanisms (macOS SCDynamicStore, Linux systemd-resolved/NetworkManager/resolvconf/static `/etc/resolv.conf`, Windows iphlpapi/netsh/TCP-IP registry) behind a single `DnsMonitor` API. On Android/iOS it is a no-op stub because DNS is handled by the platform tunnel APIs.

## Requirements

### Requirement: UnifiedDnsMonitorApi

The system SHALL expose a platform-agnostic `DnsMonitor` whose `set(interface, DnsConfig)` applies the desired DNS servers/port and begins enforcing them, and whose `reset` / `reset_before_interface_removal` restore the prior configuration. The concrete backend is selected at compile time via `#[cfg(target_os = ...)]`.

#### Scenario: SetDesiredDns
- **GIVEN** a constructed `DnsMonitor` and a `DnsConfig` with one or more addresses
- **WHEN** `set` is called with a tunnel interface name and that config
- **THEN** the platform backend applies the addresses (and non-standard port where supported) and starts enforcing them

#### Scenario: ResetRestoresPreviousDns
- **GIVEN** a `DnsMonitor` that previously applied DNS settings
- **WHEN** `reset` is called
- **THEN** the system DNS configuration is restored to what it was before this instance set it, succeeding even if the interface no longer exists

#### Scenario: EmptyServerListIsReset
- **GIVEN** a `DnsConfig` whose `addresses` list is empty (on Linux)
- **WHEN** `set` is called
- **THEN** the monitor performs a reset and does not install a new backend (no DNS is enforced)

### Requirement: LinuxDnsBackendSelection

On Linux the system SHALL select the DNS management backend from the `NYM_DNS_MODULE` environment variable, accepting `static-file` (static `/etc/resolv.conf`), `resolvconf`, `systemd`, or `network-manager`; for any other value or when unset it SHALL auto-detect by trying systemd-resolved, then NetworkManager, then resolvconf, then static `/etc/resolv.conf`, returning `NoDnsMonitor` if none is usable.

#### Scenario: ExplicitModuleSelected
- **GIVEN** `NYM_DNS_MODULE=resolvconf` in the environment
- **WHEN** the Linux `DnsMonitorHolder` is constructed
- **THEN** the resolvconf backend is used (or construction fails if resolvconf is unavailable)

#### Scenario: AutoDetectionFallbackChain
- **GIVEN** `NYM_DNS_MODULE` is unset and systemd-resolved is not available
- **WHEN** the backend is auto-detected
- **THEN** it falls back to NetworkManager, then resolvconf, then static `/etc/resolv.conf`, erroring with `NoDnsMonitor` only if all fail

#### Scenario: FreshBackendPerSet
- **GIVEN** a previously applied DNS configuration
- **WHEN** `set` is called again
- **THEN** the monitor first resets, then constructs a new backend (so a changed system DNS-management mechanism is re-detected)

### Requirement: LinuxStaticResolvConfManagement

The static `/etc/resolv.conf` backend SHALL back up the existing `/etc/resolv.conf` to `/etc/resolv.conf.nymbackup`, write the desired nameservers, watch the file for external changes via inotify and re-apply the desired config, and on reset restore the backup and remove the backup file.

#### Scenario: BackupAndWrite
- **GIVEN** the static-file backend
- **WHEN** `set_dns` is called with desired servers
- **THEN** the current `/etc/resolv.conf` is backed up and replaced with the desired nameservers

#### Scenario: RestoreOnReset
- **GIVEN** the static-file backend has written DNS settings
- **WHEN** `reset` is called
- **THEN** `/etc/resolv.conf` is restored from `/etc/resolv.conf.nymbackup` and the backup file is removed

### Requirement: LinuxResolvconfPreconditions

The resolvconf backend SHALL fail construction when no `resolvconf` binary exists (`NoResolvconf`), when resolvconf is backed by systemd-resolved (`ResolvconfUsesResolved`), when resolvconf is not actually in use (`ResolvconfNotInUse`), or when dnsmasq is misconfigured (`DnsmasqMisconfiguration`), so an unsuitable mechanism is not silently used.

#### Scenario: NoResolvconfBinary
- **GIVEN** `resolvconf` is not on `PATH`
- **WHEN** the resolvconf backend is constructed
- **THEN** construction returns `NoResolvconf`

### Requirement: WindowsDnsBackendSelection

On Windows the system SHALL select the DNS backend from `NYM_DNS_MODULE`, accepting `iphlpapi`, `netsh`, or `tcpip`; for any other value or when unset it SHALL use the `Auto` backend, which tries iphlpapi, then netsh, then the TCP/IP registry parameter. It SHALL also expose `flush_resolver_cache` to flush the Windows resolver cache.

#### Scenario: AutoBackendOrder
- **GIVEN** `NYM_DNS_MODULE` is unset on Windows
- **WHEN** the `DnsMonitor` is constructed
- **THEN** the `Auto` backend is used, attempting iphlpapi, then netsh, then the TCP/IP registry parameter

#### Scenario: FlushResolverCache
- **GIVEN** the Windows platform
- **WHEN** `flush_resolver_cache` is called
- **THEN** the Windows DNS resolver cache is flushed via `DnsFlushResolverCache`

### Requirement: MacosDnsEnforcement

On macOS the system SHALL apply the desired DNS settings to all network services via `SCDynamicStore`, spawn a background CoreFoundation run loop that watches `State:`/`Setup:` DNS keys, and re-apply the desired settings whenever an external change is detected (debounced via a burst guard), backing up overwritten settings for restoration on reset. A non-standard DNS port SHALL be written only when it differs from port 53.

#### Scenario: ReapplyOnExternalChange
- **GIVEN** macOS DNS settings have been applied for the desired servers
- **WHEN** the OS (e.g. DHCP) changes DNS for a network service
- **THEN** the background monitor detects the change and re-applies the desired DNS settings to that service

#### Scenario: NonStandardPort
- **GIVEN** a `DnsConfig` whose port differs from 53
- **WHEN** macOS DNS settings are constructed
- **THEN** the `ServerPort` key is written into the service's DNS dictionary

#### Scenario: RestoreBackedUpSettings
- **GIVEN** macOS DNS settings have been applied and prior per-service settings backed up
- **WHEN** `reset` is called
- **THEN** the backed-up settings are restored, and entries that previously had none are removed from the dynamic store

### Requirement: MobileNoOpDnsMonitor

On Android and iOS the system SHALL provide a stub `DnsMonitor` whose `new`, `set`, and `reset` always succeed without modifying any system state, because DNS is configured through the platform tunnel APIs.

#### Scenario: AndroidSetIsNoOp
- **GIVEN** the crate is compiled for Android or iOS
- **WHEN** `set` or `reset` is called on the `DnsMonitor`
- **THEN** the call returns `Ok(())` and no system DNS is changed

## Technical Notes

- **Implementation**: `src/lib.rs` (`DnsMonitor`, `DnsConfig`, `DnsMonitorT` trait); `src/macos.rs` (`SCDynamicStore` monitor with `State`/`DnsSettings` and `BurstGuard`); `src/linux/mod.rs` (`DnsMonitorHolder`, `NYM_DNS_MODULE` selection, `will_use_nm`); `src/linux/{resolvconf,systemd_resolved,network_manager,static_resolv_conf}.rs`; `src/windows/mod.rs` (`Auto`/`iphlpapi`/`netsh`/`tcpip`) and `src/windows/dnsapi.rs` (`flush_resolver_cache`); `src/android.rs` (Android + iOS stub).
- **Dependencies**: Workspace crates `nym-routing` (Linux/macOS — `RouteManagerHandle` passed into systemd-resolved DNS routing and `debounce::BurstGuard` on macOS), `nym-dbus` (Linux D-Bus to systemd-resolved/NetworkManager), `nym-common` (flood detection), `nym-windows` (Windows). External: `system-configuration` (macOS), `resolv-conf`/`inotify`/`which`/`duct` (Linux), `winreg`/`windows` (Windows). Role in workspace: the DNS half of the VPN tunnel's leak-protection, complementing `nym-firewall`; both are driven by the tunnel state machine.
