## Purpose

A command-line diagnostic harness (binary, with a `DiagnosticHandler` library entry point) that black-box tests the Nym VPN client stack end to end. It exercises DNS resolution, HTTP/API reachability, gateway connectivity (TCP/WebSocket/Lewes-Protocol handshake), the CTAP 2.2 hybrid-transport relay, and full WireGuard registration over either the mixnet or the Lewes Protocol (LP) path — emitting a structured JSON report for each category so users and developers can pinpoint where connectivity breaks.

## Requirements

### Requirement: CommandLineInterface

The system SHALL provide a CLI with global options `--verbose`/`-v` (repeatable: 0→INFO, 1→DEBUG, 2+→TRACE), `--no-log` (suppress logging), and `--network`/`-n` (`mainnet` default, `sandbox`, `canary`), and two subcommands: `run` (network diagnostics, no registration) and `register` (full registration diagnostic). Each subcommand SHALL serialize its report to pretty-printed JSON on stdout.

#### Scenario: RunSubcommandEmitsJsonReport
- **GIVEN** the binary invoked as `run` for a selected network
- **WHEN** the diagnostics complete
- **THEN** a `DiagnosticReport` is printed to stdout as pretty JSON

#### Scenario: NetworkSelection
- **GIVEN** `--network sandbox` (or `canary`)
- **WHEN** the tool starts
- **THEN** the network config is loaded via discovery; `mainnet` instead loads built-in defaults directly

### Requirement: RunDiagnosticComposition

The `run` subcommand SHALL perform DNS, HTTP/API, and hybrid-transport checks by default, perform the gateway check only when `--gateway <ID>` is supplied, and SHALL allow each section to be skipped via `--skip-dns`, `--skip-http`, `--skip-hybrid-transport`. Every individual check result SHALL be wrapped as a `DiagnosticResult<T>` capturing either the success value or an error string.

#### Scenario: GatewayCheckRequiresGatewayId
- **GIVEN** a `run` invocation without `--gateway`
- **WHEN** diagnostics execute
- **THEN** the gateway diagnostic is skipped and the other sections still run

#### Scenario: SectionSkipped
- **GIVEN** `run --skip-dns`
- **WHEN** diagnostics execute
- **THEN** the DNS section is omitted from the report

### Requirement: DnsDiagnostic

The system SHALL resolve the hostnames derived from the network config's API URLs (Nym API, VPN API, Nyxd) using both the system resolver and a fixed set of public resolvers (Quad9 and Cloudflare, each over TLS, plain UDP/TCP, and HTTPS). Resolvers SHALL be configured with no cache, dual-stack (IPv4 and IPv6), a 2-second per-query timeout, and no retries, and SHALL record the resolved IPs and resolution duration or the failure.

#### Scenario: SystemAndPerNameserverResolution
- **GIVEN** hostnames extracted from the network config
- **WHEN** the DNS diagnostic runs
- **THEN** the report contains a `system` result and a `by_nameserver` result for each public resolver/protocol variant

### Requirement: HttpApiDiagnostic

The system SHALL check Nym API and VPN API reachability: counting described nodes via the Nym API, fetching VPN API health, deriving remote time skew, and probing both plain and CDN-fronted variants of each endpoint (front policy `Off` for plain, `Always` for fronted), recording per-endpoint status and any front hosts used.

#### Scenario: FrontedAndPlainEndpointsProbed
- **GIVEN** a network config whose API URLs declare fronting hosts
- **WHEN** the HTTP diagnostic runs
- **THEN** the report includes a `by_endpoint` entry for both the plain and the fronted variant of each API

#### Scenario: TimeSkewReported
- **GIVEN** the VPN API responds with a server time
- **WHEN** the HTTP diagnostic runs
- **THEN** the report includes the remote time skew alongside the health response and node count

### Requirement: GatewayDiagnostic

When given a gateway identity (base58 ed25519 key), the system SHALL validate the key, look the gateway up in the directory, attempt a raw TCP connection to its WebSocket port, upgrade to a WebSocket and issue a `SupportedProtocol` control request, and perform an LP handshake against the gateway's LP control port (selecting the ciphersuite from the gateway version and validating the LP data signature against the gateway key). Each step SHALL short-circuit downstream steps on failure.

#### Scenario: GatewayWebsocketProbe
- **GIVEN** a reachable gateway and a valid identity
- **WHEN** the gateway diagnostic runs
- **THEN** the report records TCP, WebSocket-upgrade, and `SupportedProtocol` response results

#### Scenario: TcpFailureSkipsWebsocket
- **GIVEN** a gateway whose WebSocket port is unreachable
- **WHEN** the TCP step fails
- **THEN** the WebSocket and control-request steps are skipped and reported as not attempted

### Requirement: HybridTransportDiagnostic

The system SHALL verify reachability of the CTAP 2.2 hybrid-transport relay at `cable.ua5v.com:443` by performing a TLS handshake (rustls with webpki-roots) and a WebSocket upgrade (`Sec-WebSocket-Protocol: fido.cable`, path `/cable/new/<random-tunnel-id>`, 10-second timeout). The probe SHALL be considered successful only if the response carries an `X-Cable-Routing-Id` header (HTTP 101 alone is insufficient), and SHALL record the routing id and handshake duration.

#### Scenario: RoutingIdHeaderRequired
- **GIVEN** the relay returns HTTP 101 without `X-Cable-Routing-Id`
- **WHEN** the hybrid-transport diagnostic evaluates the response
- **THEN** it is treated as a failure rather than a success

### Requirement: RegistrationDiagnostic

The `register` subcommand SHALL require `--gateway <ID>`, accept an optional `--storage-path` for the credential database, run in `--mixnet` (default) or `--lp` mode (mutually exclusive), and optionally skip the WireGuard ping stage via `--skip-wireguard`. A successful registration SHALL spend a `V1WireguardEntry` bandwidth ticket from the gateway, and the flow SHALL emit a `RegistrationReport` with each stage's result.

#### Scenario: MixnetRegistrationFlow
- **GIVEN** `register --gateway <ID> --mixnet`
- **WHEN** the flow runs
- **THEN** the report records mixnet client build, mixnet client start (10-second connect timeout), IPR connect, and the WireGuard dVPN registration result

#### Scenario: LpRegistrationFlow
- **GIVEN** `register --gateway <ID> --lp`
- **WHEN** the flow runs
- **THEN** the report records the LP handshake and the LP-based dVPN registration result

#### Scenario: RegistrationSpendsTicket
- **GIVEN** a credential database at `<storage-path>/credentials.db` with available tickets
- **WHEN** registration succeeds
- **THEN** a `V1WireguardEntry` entry ticket is consumed

### Requirement: WireguardPingDiagnostic

After a successful registration (unless `--skip-wireguard` is set), the system SHALL build a `boringtun` WireGuard tunnel from the returned `WireguardConfiguration`, choosing IPv4 or IPv6 by the endpoint address type, and SHALL send up to 10 ICMP/ICMPv6 echo requests (100 ms apart, 10-second total timeout) to Cloudflare DNS (`1.1.1.1` or `2606:4700:4700::1111`), verifying each reply by identifier (`0x4242`) and sequence number and recording per-ping round-trip delay.

#### Scenario: PingOverTunnel
- **GIVEN** an established WireGuard tunnel from registration
- **WHEN** the ping diagnostic runs
- **THEN** echo requests are encapsulated through the tunnel and each `PingReport` records the target and either the delay or an error

### Requirement: Logging

The system SHALL configure `tracing-subscriber` in compact form with file/line and without the module target, honoring `--no-log` and the `--verbose` count (overridable by `RUST_LOG`), and SHALL force `hickory_proto`, `hickory_resolver`, `h2`, and `rustls` to `info` level to suppress DNS/TLS noise.

#### Scenario: VerbosityControlsLevel
- **GIVEN** the binary invoked with `-vv`
- **WHEN** logging is initialized
- **THEN** the base level is TRACE while the noisy DNS/TLS crates remain at `info`

## Technical Notes

- **Implementation**: `src/main.rs` (arg parse, network config load, dispatch to `run`/`register`, JSON output); `src/cli.rs` (`clap` definitions: global flags, `RunParams`, `RegisterParams`); `src/lib.rs` + `src/diagnostic/mod.rs` (`DiagnosticHandler`, `build_api_client`); `src/diagnostic/dns.rs` (system + per-nameserver `hickory-resolver` checks); `src/diagnostic/http.rs` (health, node count, time skew, fronting); `src/diagnostic/gateway.rs` (key validation, TCP/WS/`SupportedProtocol`, LP handshake); `src/diagnostic/hybrid_transport.rs` (`cable.ua5v.com` probe, `X-Cable-Routing-Id` check); `src/diagnostic/registration/{mod,mixnet_client,lp_client,wireguard}.rs` (registration flows, bandwidth provider, `boringtun` ping); `src/error.rs` (`Error::{WsStreamClosed, MissingApiUrl, BuildApiClient, Websocket}`); `src/logging.rs`.
- **Dependencies**: Report/param types (`DiagnosticReport`, `RegistrationReport`, `DiagnosticResult<T>`, `PingReport`, etc.) come from workspace crate `nym-vpn-lib-types`; gateway lookup from `nym-gateway-directory`; network config from `nym-vpn-network-config`; API access via `nym-vpn-api-client`/`nym-http-api-client`; registration via `nym-authenticator-client`, `nym-registration-client`/`-common`, `nym-ip-packet-client`, `nym-bandwidth-controller`, `nym-credentials-interface`; mixnet via `nym-sdk`/`nym-client-core`/`nym-topology`; LP via `nym-lp`/`nym-lp-data`; chain via `nym-validator-client`; crypto via `nym-crypto`; build/user-agent metadata via `nym-bin-common`/`nym-platform-metadata`. External: `clap`, `tokio`, `tokio-tungstenite`, `tokio-rustls`/`rustls`/`webpki-roots`, `boringtun`, `pnet_packet`, `hickory-resolver`, `serde_json`, `semver`, `time`, `tracing(-subscriber)`. Role in workspace: a standalone troubleshooting binary that reuses the same gateway/registration/API building blocks as `nym-vpn-lib` to validate connectivity without bringing up the full tunnel engine.
