## Purpose

nym-vpn-account-controller owns the account/credential lifecycle of the VPN client.
It runs an async, command-driven state machine that manages account login,
device key management and registration, zk-nym credential (ticketbook) acquisition,
and account/subscription synchronization against the Nym VPN API and the nyxd
chain. It persists account/device keys and credentials in SQLite and broadcasts
account state and events to the rest of the engine.

## Requirements

### Requirement: CommandDrivenController

The controller SHALL process `AccountCommand`s received over a command channel and
return results to callers through per-command return senders.

#### Scenario: Execute an account command
- **GIVEN** a running `AccountController` with a command sender
- **WHEN** a caller sends an `AccountCommand` carrying a `ReturnSender`
- **THEN** the controller handles it and delivers the result (or `AccountCommandError`) back through the return sender

### Requirement: AccountStateMachine

The controller SHALL model account status as a state machine with states including
Offline, Syncing, LoggedOut, ReadyToConnect, Decentralised, UpgradeMode,
PendingSubscription, RequestingZkNyms, and Error.

#### Scenario: Transition on synchronization
- **GIVEN** the controller is in the Syncing state
- **WHEN** account synchronization completes and credentials are valid
- **THEN** the state transitions to ReadyToConnect and is broadcast to subscribers

#### Scenario: Enter offline state
- **GIVEN** the controller cannot reach the VPN API
- **WHEN** it detects the host is offline
- **THEN** it transitions to the Offline state

### Requirement: AccountLifecycleManagement

The controller SHALL support storing, linking, registering, and forgetting an
account.

#### Scenario: Store and register an account
- **GIVEN** a `StorableAccount` from a user mnemonic
- **WHEN** `StoreAccount` then `RegisterAccount` commands are processed
- **THEN** the account is persisted and the device is registered with the VPN API

#### Scenario: Forget an account
- **GIVEN** a stored account
- **WHEN** a `ForgetAccount` command is processed
- **THEN** the stored account/device data is removed and the state returns to LoggedOut

### Requirement: DeviceKeyManagement

The controller SHALL manage device identity keys, including loading, rotating, and
resetting them.

#### Scenario: Rotate device keys
- **GIVEN** an account with stored device keys
- **WHEN** a `RotateKeys` command is processed
- **THEN** new device keys are generated/stored and the device registration is updated

### Requirement: TicketbookAcquisition

The controller SHALL obtain and store zk-nym ticketbooks (credentials) used to pay
for gateway bandwidth, tracking pending credential requests.

#### Scenario: Obtain ticketbooks
- **GIVEN** an account in a ready state with insufficient tickets
- **WHEN** an `ObtainTicketbooks` command is processed
- **THEN** ticketbooks are requested, persisted in credential storage, and made available for connections

### Requirement: AccountQueries

The controller SHALL answer read-only queries about the account, device, usage,
balance, available tickets, and deeplinks via `CommonCommand`.

#### Scenario: Query available tickets
- **GIVEN** a controller with stored credentials
- **WHEN** a `GetAvailableTickets` common command is processed
- **THEN** it returns the current `AvailableTicketbooks` summary

### Requirement: StatePersistence

The controller SHALL persist account/device keys and credentials in a SQLite-backed
store guarded by a connection pool.

#### Scenario: Reload state on startup
- **GIVEN** previously stored account and device keys
- **WHEN** the controller is constructed
- **THEN** it loads the stored account, device keys, and WireGuard keys from storage before serving commands

### Requirement: EventBroadcasting

The controller SHALL broadcast account controller events and expose a state
receiver so other subsystems can observe account changes.

#### Scenario: Observe account events
- **GIVEN** a subscriber that called `subscribe_to_events()`
- **WHEN** the account state changes
- **THEN** the subscriber receives the corresponding event/state update
