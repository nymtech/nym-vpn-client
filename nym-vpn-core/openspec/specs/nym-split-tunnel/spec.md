## Purpose

The `nym-split-tunnel` crate excludes selected applications (and their traffic) from the Nym VPN tunnel so they route through the host's normal default interface. Exclusions are configured by filesystem path and applied per-process. Each platform uses a different mechanism: Linux moves PIDs into a dedicated cgroup; macOS runs a userspace packet classifier driven by Endpoint Security process monitoring and a pktap/BPF datapath; Windows talks to a kernel-mode WFP driver over IOCTLs. The crate exposes a shared `VpnInterface` type and `SplitTunnelErrorCause` classification across platforms.

## Requirements

### Requirement: PathBasedExclusionConfiguration

The system SHALL accept exclusion configuration as sets of filesystem paths and apply them so that matching processes route outside the VPN tunnel until the configuration is changed or cleared.

On macOS and Windows the entry point is `SplitTunnelHandle::set_exclude_paths(paths: HashSet<PathBuf>, hybrid_paths: HashSet<PathBuf>)`. On macOS this initializes/updates the `ProcessMonitor` and checks each process's executable path against the lists. On Windows the paths are converted from DOS paths to NT device paths, serialized into a binary configuration buffer, and pushed to the driver via the `SetConfiguration` IOCTL.

#### Scenario: Set excluded paths
- **GIVEN** a running split tunnel
- **WHEN** `set_exclude_paths` is called with a set of application paths
- **THEN** processes whose executable matches a path are routed via the default (non-tunnel) interface, and `Ok(())` is returned (macOS/Windows)

#### Scenario: Windows device-path conversion
- **GIVEN** excluded DOS paths such as `C:\app.exe` on Windows
- **WHEN** the configuration is applied
- **THEN** each path is converted to an NT device path (`\Device\HarddiskVolume...`); paths on unmounted volumes are skipped and logged

### Requirement: HybridSourceIpRouting

The system SHALL support a "hybrid" exclusion mode in which a process's packets are routed based on the source IP it binds to: traffic bound to the VPN tunnel address goes through the VPN, and other traffic goes through the default interface.

On macOS, hybrid processes are tracked with `ExclusionStatus::Hybrid` and the datapath uses `RoutingDecision::RouteBySourceIp`, comparing the packet source against the fixed VPN tunnel addresses. On Windows, hybrid paths carry `ST_CONFIGURATION_ENTRY_FLAG_HYBRID` so the driver routes by bound source IP without bind/connect rewriting. When a path appears in both the exclude and hybrid sets, hybrid takes precedence.

#### Scenario: Hybrid routing by source IP
- **GIVEN** a process configured as hybrid
- **WHEN** it sends a packet bound to the VPN tunnel address
- **THEN** the packet is routed through the VPN tunnel; packets bound to other source IPs are routed through the default interface

### Requirement: SplitTunnelInterfaceLifecycle

The system SHALL be informed of the active VPN tunnel interface via `set_tunnel`, and SHALL be able to forget it via `reset_tunnel`, tearing down any split-tunnel datapath created for it.

On macOS, `set_tunnel(vpn_interface)` creates the utun/pktap datapath when a process monitor exists (otherwise caches the interface), and `reset_tunnel()` destroys the split-tunnel interface while keeping the process monitor. On Windows, `set_tunnel` registers the tunnel IPv4/IPv6 addresses with the driver (`RegisterIpAddresses`) and `reset_tunnel` clears them.

#### Scenario: Set tunnel activates datapath
- **GIVEN** exclusion paths already configured on macOS
- **WHEN** `set_tunnel(vpn_interface)` is called
- **THEN** the split-tunnel utun device and pktap/BPF datapath are created and traffic begins to be classified

#### Scenario: Reset tunnel on disconnect
- **GIVEN** an active split tunnel
- **WHEN** `reset_tunnel()` is called (e.g. on entering the disconnected state)
- **THEN** the VPN interface is forgotten and the split-tunnel device is destroyed without removing the process monitor

### Requirement: ActorMessagingModel

The system SHALL run split tunneling (macOS/Windows) as a background actor controlled through a cloneable async handle over a message channel, shutting down when its shutdown token is cancelled or its channel closes.

On macOS, `SplitTunnel::spawn(route_manager, shutdown_token, error_handler)` returns `(SplitTunnelHandle, JoinHandle<()>)`; the actor `select!`s on incoming `Message`s and the `CancellationToken`. Handle methods (`interface`, `set_exclude_paths`, `set_tunnel`, `reset_tunnel`, `get_excluded_processes`) send a `Message` with a oneshot reply channel and map a dropped channel to an unavailable error.

#### Scenario: Shutdown via token
- **GIVEN** a spawned split tunnel actor
- **WHEN** the shutdown token is cancelled
- **THEN** the actor breaks its loop, runs cleanup/shutdown, and the join handle completes

### Requirement: ExcludedProcessObservability

The system SHALL expose the set of currently excluded processes for diagnostics.

`SplitTunnelHandle::get_excluded_processes()` returns a `SplitTunnelExcludedProcessList`. On macOS this derives from the `ProcessStates` map maintained by the Endpoint Security monitor; on Windows it derives from the in-memory `HashMap<PID, ExcludedProcess>` updated by driver start/stop splitting events.

#### Scenario: List excluded processes
- **GIVEN** a running split tunnel with excluded applications
- **WHEN** `get_excluded_processes()` is called
- **THEN** a `SplitTunnelExcludedProcessList` of the currently split processes is returned

### Requirement: ErrorCauseClassification

The system SHALL classify split-tunnel failures into a platform-agnostic `SplitTunnelErrorCause` so callers can react appropriately, distinguishing offline, missing-permission, and other causes.

`SplitTunnelErrorCause` has variants `IsOffline` and `NeedFullDiskPermissions` (macOS) and `Other`. On macOS, `From<&Error>` maps a `Default(_)` (missing default route) error to `IsOffline` and process-permission errors to `NeedFullDiskPermissions`; the actor invokes a caller-supplied `error_handler` with the cause.

#### Scenario: Offline classification
- **GIVEN** the macOS split tunnel cannot find a default route
- **WHEN** an operation fails with the `Default` error
- **THEN** the error is classified as `SplitTunnelErrorCause::IsOffline`

#### Scenario: Missing full-disk access
- **GIVEN** the macOS process monitor cannot start because full-disk access is not granted
- **WHEN** the error is classified
- **THEN** it maps to `SplitTunnelErrorCause::NeedFullDiskPermissions`

### Requirement: MacosProcessMonitoring

The system SHALL, on macOS, track process lifecycle via the Endpoint Security framework to determine each process's exclusion status, requiring macOS 11.0+ and full-disk access.

`ProcessMonitor` runs on a dedicated thread and subscribes to `ES_EVENT_TYPE_NOTIFY_EXEC`, `FORK`, and `EXIT`. On fork, a child inherits the parent's excluded/included status but not hybrid status. On exec, the process's executable path (and its responsible process path, via `responsibility_get_pid_responsible_for_pid`) is matched against the exclude/hybrid lists. Untracked processes have `ExclusionStatus::Unknown` and their packets are dropped. `has_full_disk_access` is exported for pre-checks.

#### Scenario: Exec match excludes process
- **GIVEN** the macOS process monitor is running with configured paths
- **WHEN** a process execs a binary whose path (or responsible process path) matches an exclude path
- **THEN** the process is marked `Excluded` and its traffic is routed via the default interface

#### Scenario: Unknown process dropped
- **GIVEN** a packet arrives for a PID not yet tracked
- **WHEN** the datapath classifies it
- **THEN** the packet is dropped

### Requirement: MacosPacketDatapath

The system SHALL, on macOS, run a userspace datapath that captures packets via pktap/BPF, classifies them per-PID, and forwards them to either the default interface or the VPN tunnel, rewriting addresses and recomputing checksums as needed.

The split-tunnel utun device uses fixed addresses (IPv4 `10.111.111.111/32`, IPv6 `fd11:1111:fefe:fefe::/64`). The egress task reads outbound packets, extracts the PID from the pktap header, and applies a `RoutingDecision` (`DefaultInterface`, `VpnTunnel`, `RouteBySourceIp`, or `Drop`). For default-interface egress the source IP is rewritten and IPv4/IPv6 and TCP/UDP checksums recalculated; for VPN egress the source IP is validated. The split-tunnel MTU is kept in sync with the VPN tunnel MTU via an interface change listener.

#### Scenario: Excluded packet to default interface
- **GIVEN** an outbound packet from an excluded process on macOS
- **WHEN** the egress task classifies it as `DefaultInterface`
- **THEN** the source IP is rewritten to the default interface address, checksums are recomputed, and it is forwarded to the default-interface BPF

### Requirement: LinuxCgroupExclusion

The system SHALL, on Linux, exclude traffic by moving process PIDs into a dedicated cgroup, preferring cgroup v2 (with an nftables `socket cgroupv2` rule) and falling back to deprecated cgroup v1 (`net_cls` classid).

`PidManager` initializes cgroup v2 first when the `cgroup2` feature is enabled and falls back to cgroup v1 on failure (logging the deprecation). It exposes `add(pid)`, `remove(pid)` (by moving the PID back to the root cgroup), `list()`, `clear()`, `is_supported()`, `excluded_cgroup()` (for the nftables integration), and `net_cls_classid()`. Errors include `AddCGroup2Rule`, `CGroup`, and `Unavailable`.

#### Scenario: Exclude a PID
- **GIVEN** a Linux `PidManager` with a working cgroup
- **WHEN** `add(pid)` is called
- **THEN** the PID is moved into the excluded cgroup whose traffic is steered outside the tunnel

#### Scenario: cgroup v2 fallback to v1
- **GIVEN** a kernel that does not support cgroup v2 split tunneling
- **WHEN** `PidManager` initializes
- **THEN** cgroup v2 setup fails and it falls back to cgroup v1, logging the deprecation warning

### Requirement: WindowsDriverService

The system SHALL, on Windows, manage a kernel-mode driver service and communicate with the driver over IOCTLs, resetting the driver before the service is stopped to avoid leaving the driver in an unsafe state.

`install_driver_service()` registers the `nymvpn-split-tunnel` service (kernel driver, on-demand, requires `nymvpn-split-tunnel.sys` next to the executable) if absent; `uninstall_driver_service()` stops then deletes it. `DeviceHandle` opens `\\.\NYMVPNSPLITTUNNEL` and drives a state machine (None → Started → Initialized → Ready → Engaged). The driver `reset()` must be called before unloading.

#### Scenario: Install driver service
- **GIVEN** the driver `.sys` file present beside the executable and the service not yet installed
- **WHEN** `install_driver_service()` is called
- **THEN** a kernel-driver Windows service is registered, or a service error is returned if creation fails

#### Scenario: Reset before stop
- **GIVEN** an engaged Windows split-tunnel driver
- **WHEN** the service is to be stopped
- **THEN** the driver is reset first so it does not unload while still filtering (avoiding resource leaks/instability)

### Requirement: WindowsPathAndVolumeMonitoring

The system SHALL, on Windows, keep driver path configuration consistent as symlinks and volumes change by monitoring path and volume events and re-resolving and re-applying configuration when affected.

`PathMonitor` watches volume roots via `ReadDirectoryChangesW` and re-resolves symlinks/junctions (`resolve_all_links_multiple`) when monitored paths change. `VolumeMonitor` creates a hidden window receiving `WM_DEVICECHANGE` (`DBT_DEVICEARRIVAL`/`DBT_DEVICEREMOVECOMPLETE`); when an excluded path's volume is affected it triggers a config re-apply and `path_monitor.refresh()`.

#### Scenario: Symlink change re-applies config
- **GIVEN** an excluded path that traverses a symlink on Windows
- **WHEN** the symlink target changes
- **THEN** the path monitor re-resolves the path and the driver configuration is re-applied

#### Scenario: Volume mount triggers refresh
- **GIVEN** an excluded path on a volume
- **WHEN** that volume mounts or unmounts
- **THEN** the volume monitor signals a config re-apply and refreshes path resolution

### Requirement: GracefulDegradationWhenUnavailable

The system SHALL degrade gracefully when split tunneling cannot be initialized or used, accepting operations as no-ops rather than failing the VPN connection.

On Windows, a failed initialization leaves the actor in `State::Failed`, where commands return `Ok(())`. The shared `InnerError::Unavailable`/`Error::Unavailable` variant and `SplitTunnelErrorCause::Other` represent the unavailable case; on Linux a failed `PidManager` reports `is_supported() == false`.

#### Scenario: Operations no-op when failed
- **GIVEN** a Windows split tunnel whose driver could not initialize (Failed state)
- **WHEN** `set_exclude_paths` or `set_tunnel` is called
- **THEN** the call returns `Ok(())` without affecting tunnel connectivity

## Technical Notes

- **Implementation**: `src/lib.rs` (shared `VpnInterface`, `SplitTunnelErrorCause`, platform re-exports); `src/linux/mod.rs` (`PidManager`, cgroup v1/v2); `src/macos/mod.rs` (`SplitTunnel`/`SplitTunnelHandle` actor, `State` machine), `src/macos/process.rs` (Endpoint Security `ProcessMonitor`, `ExclusionStatus`), `src/macos/tun.rs` + `src/macos/bpf.rs` + `src/macos/default.rs` (pktap/BPF datapath, `RoutingDecision`, default-route resolution); `src/windows/mod.rs` (`SplitTunnelHandle` actor), `src/windows/driver.rs` (`DeviceHandle`, IOCTLs), `src/windows/service.rs` (driver service), `src/windows/path_monitor.rs` + `src/windows/volume_monitor.rs` (config consistency).
- **Dependencies**: Internal — `nym-routing` (default route/gateway lookup and interface monitoring used to steer excluded traffic), `nym-cgroup` (Linux cgroups), `nym-firewall`/`nym-firewall-config` (nftables cgroup rule, behind `cgroup2` feature), `nym-macos`, `nym-dbus`, `nym-ifconfig`, `nym-platform-metadata`, `nym-windows`, `nym-vpn-lib-types` (`SplitTunnelExcludedProcessList`). External — `tun`, `pnet_packet`, `nix`, `libc` (all), `endpoint-sec`/`pcap` (macOS), `nftnl`/`mnl`/`netlink-sys` (Linux), `windows`/`windows-sys`/`windows-service` (Windows). In the workspace this crate is the user-facing split-tunneling feature, consumed by the VPN tunnel/state-machine layer, which feeds it the active `VpnInterface` and exclusion paths. The code derives from Mullvad VPN's split-tunnel implementation, adapted by Nym.
