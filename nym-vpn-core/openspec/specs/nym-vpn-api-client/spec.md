## Purpose

This crate is the typed HTTP client for the NymVPN public API (`public/v1/...`). It exposes `VpnApiClient`, which authenticates requests with short-lived JWTs signed by an account's secp256k1 wallet key (`VpnAccount`) and/or a device's ed25519 key (`Device`), serializes typed request bodies, and parses typed responses. It also owns clock-skew management between the device and the API server so that JWTs remain valid under time drift, and it builds a domain-fronted HTTP client with DNS-resolution fallbacks.

## Requirements

### Requirement: AccountAndDeviceJwtAuthentication

The system SHALL authenticate API requests with short-lived JWTs: an account JWT signed with the account's secp256k1 wallet key carried in the `Authorization: Bearer` header, and, where a device context is required, a device JWT signed with the device's ed25519 key carried in the `x-device-authorization: Bearer` header. JWT payloads SHALL set `exp` to 30 seconds and `iat` to the (possibly skew-corrected) issuance time.

#### Scenario: AccountScopedRequest
- **GIVEN** a `VpnApiClient` and a `VpnAccount`
- **WHEN** an account-scoped endpoint such as `get_account` or `get_devices` is called
- **THEN** the request carries a `Bearer` account JWT (header `alg: ES256K`, `sub` = Cosmos account id, `pubkey` = base58 secp256k1 key) and no device header

#### Scenario: DeviceScopedRequest
- **GIVEN** a `VpnApiClient`, a `VpnAccount`, and a `Device`
- **WHEN** a device-scoped endpoint such as `get_account_summary_with_device` or `request_zk_nym` is called
- **THEN** the request additionally carries an `x-device-authorization: Bearer` device JWT (header `alg: ECDSA`, `sub` = base58 ed25519 public key)

### Requirement: ClockSkewManagementAndJwtRetry

The system SHALL track clock skew between device and API server via a `SkewManager` that caches a measured skew for 4 hours (`SKEW_CACHE_TTL`) and estimates remote time. When a request fails with a JWT-related error, the system SHALL re-synchronise with remote time and retry the request once, returning the retried result only if it succeeds and otherwise returning the original error.

#### Scenario: ExpiredSkewRefresh
- **GIVEN** no cached skew or a skew cache older than 4 hours
- **WHEN** an authorized request needs a JWT issuance time
- **THEN** the system refreshes remote time before signing the JWT, but only substitutes remote time when the measured skew exceeds the acceptable threshold (`MAX_ACCEPTABLE_SKEW_SECONDS` = 60)

#### Scenario: JwtErrorTriggersRetry
- **GIVEN** an authorized GET/POST/DELETE/PATCH that returns an `EndpointFailure` whose message contains "jwt"
- **WHEN** the client detects the JWT error
- **THEN** it calls `sync_with_remote_time`, re-signs the JWT with remote time, retries once, and returns the retry result on success or the original error on failure

### Requirement: RemoteTimeTimeTravelDetection

The system SHALL measure remote API time by bracketing the request with local timestamps and estimating remote-now using half the round-trip time. It SHALL detect device sleep or backwards time travel and retry up to `REMOTE_TIME_MAX_RETRIES` (2) times with a 1-second delay, failing with `TimeTravelTooMuch` if every attempt is unreliable.

#### Scenario: NegativeRequestTime
- **GIVEN** the device clock moves backwards during a remote-time request (negative measured request duration)
- **WHEN** `get_remote_time` evaluates the sample
- **THEN** it discards the sample, waits 1 second, and retries up to 2 additional times before returning `TimeTravelTooMuch`

#### Scenario: RequestExceedsTimeout
- **GIVEN** the measured request time exceeds `NYM_VPN_API_TIMEOUT` (30s), suggesting the device slept
- **WHEN** `get_remote_time` evaluates the sample
- **THEN** it discards the sample and retries before failing with `TimeTravelTooMuch`

### Requirement: AccountIdentityAndKeyDerivation

The system SHALL derive a `VpnAccount` from a 24-word BIP-39 mnemonic via a secp256k1 HD wallet (prefix `"n"`), exposing the Cosmos account id, base58 public key, a base64 signature over the account id, and an account `mode` (`Api`, `Decentralised`, or `Privy`). It SHALL also derive a compact-ecash user keypair seed from the same wallet for ticketbook/zk-nym operations.

#### Scenario: GenerateNewAccount
- **GIVEN** a request to create a fresh account
- **WHEN** `VpnAccount::generate_new` is called
- **THEN** it generates a 24-word mnemonic, derives the wallet in `Api` mode, and returns the account plus mnemonic

#### Scenario: EcashKeypairDerivation
- **GIVEN** an existing `VpnAccount`
- **WHEN** `create_ecash_keypair` is called
- **THEN** the ecash keypair is seeded from the wallet's extended private key over the Cosmos derivation path, with the seed wrapped in `Zeroizing`

### Requirement: AccountAndDeviceLifecycleEndpoints

The system SHALL provide endpoints for account registration and device lifecycle under `public/v1/account/{id}`: create account (`register_account` POST to platform paths `android`/`apple` with `CreateAndroidAccountRequestBody`/`CreateAppleAccountRequestBody`), get account/summary/canonical-identity, register a device (`register_device` POSTing `device/{...}` with `RegisterDeviceRequestBody { device_identity_key, signature }` where the signature is the device's ed25519 signature over its own base58 identity key), list active devices, get a device by id, and update device status (`Active`/`Inactive`/`DeleteMe`).

#### Scenario: RegisterDevice
- **GIVEN** an account and a device keypair
- **WHEN** `register_device` is called
- **THEN** the request body carries the base58 device identity key and the device's base64 signature over that identity key, POSTed to the account's `device` route

#### Scenario: AccountSummaryFlags
- **GIVEN** a `NymVpnAccountSummaryWithDeviceResponse`
- **WHEN** the caller inspects subscription/bandwidth/device fields
- **THEN** helpers report `account_active`, `subscription_active`, `subscription_pending`, `bandwidth_limit`, `used_bandwidth`, and `remaining_devices`

### Requirement: ZkNymAndTicketbookEndpoints

The system SHALL provide zk-nym (ticketbook) endpoints under `account/{id}/device/{id}/zknym`: request a zk-nym (`request_zk_nym` POSTing `RequestZkNymRequestBody { withdrawal_request, ecash_pubkey, expiration_date, ticketbook_type }`), list zk-nyms available for download, get a zk-nym by id, and confirm a zk-nym download by id. It SHALL also expose the directory ticketbook partial verification keys endpoint and recognise the fair-usage-depleted backend error code.

#### Scenario: RequestZkNym
- **GIVEN** an account, a device, and a prepared ecash withdrawal request
- **WHEN** `request_zk_nym` is called
- **THEN** the withdrawal request, ecash public key, expiration date, and ticketbook type are POSTed to the device's `zknym` route and a `NymVpnZkNymPost` is returned

#### Scenario: ConfirmDownload
- **GIVEN** a zk-nym whose blinded shares have been downloaded
- **WHEN** `confirm_zk_nym_download_by_id` is called
- **THEN** the client POSTs the download confirmation for that zk-nym id

### Requirement: DirectoryGatewayAndDiscoveryEndpoints

The system SHALL expose unauthenticated directory and discovery endpoints: gateways (all/entry/exit/vpn, plus per-type and country variants under `directory/gateways`), health, geo-IP, well-known environments/discovery/current-env files (`envs.json`, `discovery.json`, `current-env.json`), and usage. Gateway queries SHALL support the `show_vpn_only`, `vpn_min_performance`, and `mixnet_min_performance` parameters.

#### Scenario: ListEntryGateways
- **GIVEN** a configured client
- **WHEN** `get_entry_gateways` is called
- **THEN** the client GETs `directory/gateways/entry` and returns a `NymDirectoryGatewaysResponse`

#### Scenario: HealthCheck
- **GIVEN** a configured client
- **WHEN** `get_health` is called
- **THEN** the client GETs `health` and returns a `NymVpnHealthResponse`

### Requirement: FrontedHttpClientAndDnsResolution

The system SHALL construct the underlying HTTP client via `fronted_http_client`/`fronted_http_client_builder` from a set of API URLs, an optional user agent, and a 30-second timeout (`NYM_VPN_API_TIMEOUT`), and SHALL support DNS resolution helpers and `ResolverOverrides`. Constructing from network details SHALL fail with `CreateVpnApiClient` when no VPN API URLs are configured.

#### Scenario: FromNetworkWithoutUrls
- **GIVEN** `NymNetworkDetails` whose `nym_vpn_api_urls` is absent
- **WHEN** `VpnApiClient::from_network` is called
- **THEN** it returns `VpnApiClientError::CreateVpnApiClient`

#### Scenario: HostnameResolution
- **GIVEN** an API URL that cannot be resolved
- **WHEN** the client attempts resolution
- **THEN** it surfaces `DnsResolutionFailure` / `HostnamesResolutionError`

### Requirement: TypedErrorSurface

The system SHALL represent every endpoint failure as a distinct `VpnApiClientError` variant wrapping a boxed `HttpClientError`, and SHALL allow extracting the backend `NymErrorResponse` (with documented error code ids such as `UNREGISTER_NON_EXISTENT_DEVICE_CODE_ID` and `FAIR_USAGE_DEPLETED_CODE_ID`) from an error.

#### Scenario: ExtractBackendError
- **GIVEN** a `VpnApiClientError` carrying an endpoint failure with a JSON error body
- **WHEN** `TryFrom<VpnApiClientError> for NymErrorResponse` or `extract_error_response` is invoked
- **THEN** the structured backend error (message and unique code id) is returned when present

## Technical Notes

- **Implementation**: `src/client.rs` (the `VpnApiClient` and all endpoint methods), `src/jwt.rs` (secp256k1/ECDSA JWT construction), `src/skew_manager.rs` (skew caching + remote-time sync), `src/types/account.rs` (`VpnAccount`, `VpnApiTime`, `VpnAccountMode`), `src/types/device.rs` (`Device`, `DeviceStatus`, `DeviceSignature`), `src/request.rs` and `src/response.rs` (typed request/response bodies), `src/routes.rs` (path segment constants), `src/error.rs`, `src/fronted_http_client.rs`, `src/resolve_host.rs`.
- **Dependencies**: builds on `nym-http-api-client` (`ApiClient`, `HttpClientError`, request builders) for transport; `nym-validator-client` for the secp256k1 HD wallet and signing; `nym-crypto` for ed25519 device keys; `nym-compact-ecash` for the ecash user keypair; `nym-network-defaults` for `from_network`; `nym-credential-proxy-requests` for shared request types. Within the workspace it is the network-facing layer consumed by `nym-vpn-account-controller`, which drives account/device/zk-nym lifecycle on top of these endpoints; the controller supplies the `VpnAccount`/`Device` and persists state, while this crate is stateless apart from its cached time skew.
