# nym-vpn-lib-types Specification

> Generated by openlore on 2026-06-26
> Source files: src/lib.rs, src/tunnel_state.rs, src/tunnel_event.rs, src/connection_data.rs, src/service.rs, src/account/controller_error.rs, src/account/controller_state.rs, src/account/mod.rs, Cargo.toml

## Purpose

`nym-vpn-lib-types` is the shared domain-type crate of the nym-vpn-core workspace. It defines the canonical connection/tunnel state machine, tunnel events, connection data, account controller state and errors, and service configuration types that flow between `nym-vpn-lib`, the daemon, the gRPC layer, and FFI bindings. Types are intentionally simple and self-contained so they can cross uniffi (mobile) and TypeScript/Tauri (desktop) binding boundaries, with `From` conversions to mirror external `nym-*` crate types gated behind the `nym-type-conversions` feature.

## Requirements

### Requirement: TunnelStateMachine

The system SHALL model the tunnel lifecycle as a closed enum `TunnelState` with the variants `Disconnected`, `Connecting`, `Connected`, `Disconnecting`, `Error`, and `Offline`, carrying the data each phase needs (retry attempt and establishment sub-state while connecting, `ConnectionData` while connected, an `ActionAfterDisconnect` while disconnecting, an `ErrorStateReason` on failure, and a reconnect flag while offline).

#### Scenario: ConnectingCarriesProgress
- **GIVEN** a tunnel that is being established
- **WHEN** a `TunnelState::Connecting` value is produced
- **THEN** it carries `retry_attempt`, an `EstablishConnectionState`, the `TunnelType`, and optional `EstablishConnectionData`, and its `Display` impl renders entry/exit gateways and the attempt number

#### Scenario: ErrorStateDetection
- **GIVEN** any `TunnelState` value
- **WHEN** `is_error_state()` is called
- **THEN** it returns `true` only for the `Error(_)` variant

### Requirement: ErrorStateReasonTaxonomy

The system SHALL enumerate every terminal failure cause as `ErrorStateReason` (firewall/routing/DNS/tun-device/tunnel-provider failures, IPv6 unavailability, gateway selection and identity/country validation failures, credential-waste, bandwidth exceeded, account/subscription/device problems, split-tunnel and full-disk-permission issues, relaxed-independence prompts, and an `Internal(String)` catch-all) and SHALL provide a stable `Display` representation for each.

#### Scenario: DnsFailurePreventsFilteringResolver
- **GIVEN** an `ErrorStateReason::SetDns` value on macOS or Windows
- **WHEN** `prevents_filtering_resolver()` is called
- **THEN** it returns `true`, signalling the filtering resolver cannot be configured

#### Scenario: StableDisplayNames
- **GIVEN** any `ErrorStateReason` variant
- **WHEN** it is formatted via `Display`
- **THEN** it produces a fixed PascalCase name (e.g. `MaxDevicesReached`), with `Internal` rendered as `Internal(<message>)`

### Requirement: TunnelEventModel

The system SHALL represent runtime tunnel notifications as `TunnelEvent` with variants `NewState(TunnelState)`, `MixnetState(MixnetEvent)`, `ConfigChanged(Box<VpnServiceConfig>)`, and `AccountState(AccountControllerState)`, where `MixnetEvent` further distinguishes bandwidth, connection-health, and packet-statistics events.

#### Scenario: BandwidthEventFromController
- **GIVEN** the `nym-type-conversions` feature is enabled and a `BandwidthStatusMessage`
- **WHEN** it is converted via `From<&BandwidthStatusMessage>`
- **THEN** `NoBandwidth` maps to `BandwidthEvent::NoBandwidth` and a remaining value maps to `BandwidthEvent::RemainingBandwidth(i64)`

#### Scenario: PacketRatesSummary
- **GIVEN** a populated `SphinxPacketRates`
- **WHEN** `summary()` is called
- **THEN** it returns a human-readable down/up plus cover-traffic throughput string using SI-scaled byte units

### Requirement: ConnectionDataContract

The system SHALL describe an active or forming tunnel via `ConnectionData` (entry/exit `GatewayLightInfo`, ISO-8601 `connected_at` timestamp, and a `TunnelConnectionData`), where `TunnelConnectionData` is either `Mixnet(MixnetConnectionData)` or `Wireguard(WireguardConnectionData)` and reports its `TunnelType` via `tunnel_type()`.

#### Scenario: TunnelTypeDiscriminant
- **GIVEN** a `TunnelConnectionData` value
- **WHEN** `tunnel_type()` is called
- **THEN** it returns `TunnelType::Mixnet` for the mixnet variant and `TunnelType::Wireguard` for the wireguard variant

#### Scenario: GatewayIdentityFromDirectory
- **GIVEN** the `nym-type-conversions` feature and a `nym_gateway_directory::Gateway`
- **WHEN** it is converted to `GatewayId` / `GatewayLightInfo`
- **THEN** the gateway identity is rendered as a base58 string and country code is taken from the gateway location when present

### Requirement: AccountControllerStateAndErrors

The system SHALL expose account-controller status as `AccountControllerState` and `AccountControllerErrorStateReason` (covering storage, API failure, internal errors, bandwidth exceeded, inactive account/subscription, max devices, and device-time desync), and SHALL surface command failures via `AccountControllerError` and `AccountCommandError`/`VpnApiError`.

#### Scenario: RetryableApiFailure
- **GIVEN** an `AccountControllerErrorStateReason`
- **WHEN** `is_retryable()` is called
- **THEN** it returns `true` only for the `ApiFailure { .. }` variant

#### Scenario: NyxdErrorMapping
- **GIVEN** a `nym_validator_client::nyxd::error::NyxdError`
- **WHEN** it is converted via `From` into `AccountCommandError`
- **THEN** it produces the corresponding account command error variant

### Requirement: VpnServiceConfigValidation

The system SHALL define `VpnServiceConfig` (with a `Default`, available via `default_vpn_service_config()` under uniffi) holding the user-facing VPN settings, and SHALL validate mixnet traffic settings through `MixnetTrafficConfig::validate()` returning `MixnetTrafficConfigValidationError` on invalid input.

#### Scenario: InvalidMixnetTrafficRejected
- **GIVEN** a `MixnetTrafficConfig` with out-of-range values
- **WHEN** `validate()` is called
- **THEN** it returns `Err(MixnetTrafficConfigValidationError)` describing the offending field

### Requirement: BindingSafeRepresentations

The system SHALL feature-gate binding attributes so the same Rust types export to uniffi (`uniffi-bindings`) and TypeScript via ts-rs (`typescript-bindings`), with serde camelCase serialization for TypeScript/Tauri compatibility, and SHALL keep exported types simple (unique names, no namespaces) per uniffi limitations.

#### Scenario: CamelCaseTypeScriptExport
- **GIVEN** the `typescript-bindings` feature is enabled
- **WHEN** TypeScript bindings are generated (`cargo test -p nym-vpn-lib-types -F typescript-bindings`)
- **THEN** exported types are written to `bindings.ts` with camelCase field names

## Technical Notes

- **Implementation**: `crates/nym-vpn-lib-types/src/lib.rs` (module/re-export surface), `tunnel_state.rs`, `tunnel_event.rs`, `connection_data.rs`, `service.rs`, `account/` (controller_error.rs, controller_state.rs, mod.rs, request_zknym.rs, storage.rs, ticketbooks.rs, deeplink.rs).
- **Dependencies**: Builds as both `cdylib` and `lib`. Optional `nym-*` deps (`nym-gateway-directory`, `nym-bandwidth-controller`, `nym-statistics-common`, `nym-vpn-api-client`, `nym-validator-client`, `nym-sdk`, `nym-registration-common`, `nym-vpn-network-config`, `nym-network-defaults`) are pulled in only under `nym-type-conversions` to provide `From` impls from internal nym types. Core deps: `strum`, `thiserror`, `time`, `si-scale`, `bip39`, `zeroize`; binding deps `uniffi` and `ts-rs` are optional. This crate is the single source of truth for shared domain types — other crates (including `nym-vpn-proto`) depend on it rather than re-exporting external types.
