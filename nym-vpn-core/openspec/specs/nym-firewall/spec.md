# nym-firewall Specification

> Generated by openlore on 2026-06-26
> Source files: src/lib.rs, src/net.rs, src/linux.rs, src/macos.rs, src/windows/mod.rs, src/windows/hyperv.rs, src/windows/ffi.rs, src/android.rs, src/ios.rs

## Purpose

Enforces network security for the VPN by applying OS-level firewall policies that prevent traffic from leaking outside the tunnel. It exposes a single `Firewall` type and a `FirewallPolicy` enum (`Connecting`, `Connected`, `Blocked`) that each platform backend translates into concrete rules: nftables on Linux, pf (packet filter) on macOS, and WFP (via a `WinFw` FFI module) on Windows. Android and iOS are no-op stubs because filtering is done by the platform tunnel/VPN service.

## Requirements

### Requirement: FirewallPolicyStates

The system SHALL support exactly three firewall policy states. `Connecting` allows traffic only to peer/relay endpoints, configured allowed endpoints, allowed in-tunnel traffic, and (optionally) LAN while connecting. `Connected` allows traffic only to peers and over the tunnel interface(s) plus (optionally) LAN. `Blocked` blocks all traffic in and out except configured allowed endpoints and (optionally) LAN.

#### Scenario: ApplyBlockedPolicy
- **GIVEN** a `Firewall` instance
- **WHEN** `apply_policy(FirewallPolicy::Blocked { allow_lan, allowed_endpoints })` is called
- **THEN** all traffic is blocked except the listed allowed endpoints (and LAN when `allow_lan` is true)

#### Scenario: ApplyConnectedPolicy
- **GIVEN** an established tunnel described by `TunnelInterface`
- **WHEN** `apply_policy(FirewallPolicy::Connected { .. })` is called
- **THEN** traffic is permitted to the peer endpoints and over the tunnel interface(s), and other traffic is rejected

#### Scenario: ResetReturnsToPriorState
- **GIVEN** a policy previously applied via this `Firewall` instance
- **WHEN** `reset_policy` is called
- **THEN** the system is returned to the state it had before any policy was applied through this instance

### Requirement: DnsLeakPrevention

The system SHALL block all outbound DNS (UDP and TCP port 53) by default in every active policy, and SHALL only permit DNS to the explicitly allowed tunnel-DNS endpoints (over the tunnel interface) and non-tunnel-DNS endpoints (off-tunnel). The DNS drop rule SHALL be ordered after relay-allow rules (so a relay may use port 53) but before LAN-allow rules (so DNS cannot leak to the LAN).

#### Scenario: DnsBlockedByDefault
- **GIVEN** any active policy with no allowed DNS endpoints for a given destination
- **WHEN** the policy rules are built
- **THEN** outbound UDP/53 is rejected (ICMP port-unreachable) and TCP/53 is rejected (TCP RST) on Linux

#### Scenario: TunnelDnsAllowed
- **GIVEN** a `Connected` policy whose `AllowedDns` contains a tunnel DNS endpoint
- **WHEN** rules are built
- **THEN** DNS to that endpoint is allowed over the exit tunnel interface while all other DNS remains blocked

#### Scenario: DnsNotLeakedToLan
- **GIVEN** a policy with `allow_lan = true`
- **WHEN** rules are built
- **THEN** the DNS drop rule precedes the LAN-allow rules so DNS does not leak onto the LAN

### Requirement: LanTrafficControl

The system SHALL permit traffic to/from the predefined private LAN networks and LAN multicast networks (from `nym-firewall-config`), plus DHCP server traffic, only when `allow_lan` is enabled in the policy; otherwise LAN traffic SHALL be subject to the default block/reject.

#### Scenario: LanAllowedWhenEnabled
- **GIVEN** a policy with `allow_lan = true`
- **WHEN** rules are built
- **THEN** traffic to `ALLOWED_LAN_NETS` and `ALLOWED_LAN_MULTICAST_NETS` is accepted

#### Scenario: LanBlockedWhenDisabled
- **GIVEN** a policy with `allow_lan = false`
- **WHEN** rules are built
- **THEN** no LAN-allow rules are added and LAN traffic falls through to the default reject

### Requirement: NetworkBootstrapTrafficAllowed

The system SHALL always allow the network bootstrap and neighbor-discovery traffic required for connectivity regardless of policy: loopback traffic, DHCPv4/DHCPv6 client exchanges, and IPv6 NDP messages (router solicitation/advertisement, neighbor solicitation/advertisement, redirect).

#### Scenario: LoopbackAlwaysAllowed
- **GIVEN** any active Linux policy
- **WHEN** rules are built
- **THEN** inbound and outbound traffic on the `lo` interface is accepted

#### Scenario: DhcpAndNdpAllowed
- **GIVEN** any active Linux policy
- **WHEN** rules are built
- **THEN** DHCPv4 (ports 67/68), DHCPv6 (ports 546/547 to the DHCPv6 multicast servers), and ICMPv6 NDP messages are accepted

### Requirement: AllowedEndpointAndClientScoping

The system SHALL allow traffic to configured `AllowedEndpoint`s, scoping who may use them via `AllowedClients`. On Unix, `AllowedClients::Root` restricts the leak to processes running as root (matched on Linux via `meta skuid == 0`), while `AllowedClients::All` permits any client (used for local proxies that do not run as root). On Windows, `AllowedClients` is a set of executable paths (empty meaning "any executable").

#### Scenario: RootOnlyEndpoint
- **GIVEN** an `AllowedEndpoint` with `AllowedClients::Root` on Linux
- **WHEN** rules are built
- **THEN** the allow rule additionally matches `meta skuid == ROOT_UID` so only root processes may reach the endpoint

#### Scenario: AnyClientEndpoint
- **GIVEN** an `AllowedEndpoint` with `AllowedClients::All`
- **WHEN** rules are built
- **THEN** the endpoint is reachable without a UID restriction

### Requirement: LinuxSplitTunneling

On Linux the system SHALL mark traffic from split-tunneled processes (matched by cgroup v2 inode when the `cgroup2` feature is enabled, or by the cgroup v1 `net_cls` classid as a fallback) and from `SO_MARK`-marked sockets, tagging them with the split-tunnel connection mark and the firewall mark so they bypass the tunnel, with masquerade applied to rerouted packets (except on loopback). It SHALL apply kernel sysctls when connecting/connected: setting `src_valid_mark` to 1 and locking down `arp_ignore` to 2 (each suppressible via env var).

#### Scenario: SplitTunnelTrafficBypasses
- **GIVEN** the `cgroup2` feature is enabled and an `excluded_cgroup2` is configured
- **WHEN** a process in that cgroup sends traffic
- **THEN** its packets are marked with `SPLIT_TUNNEL_MARK` (ct mark) and `fwmark` (meta mark), accepted in input/output/forward chains, and masqueraded outside loopback

#### Scenario: ArpIgnoreLockedDown
- **GIVEN** a `Connecting` or `Connected` policy and `NYM_FIREWALL_DONT_SET_ARP_IGNORE` not set
- **WHEN** the policy is applied
- **THEN** `net.ipv4.conf.all.arp_ignore` is raised to 2 if currently 0 or 1

### Requirement: LinuxNftablesEnforcement

On Linux the system SHALL implement the policy as a single `inet` nftables table named `nym` with input/output/forward chains defaulting to drop and dedicated prerouting/mangle/nat chains, ending unmatched outbound/forward traffic with an ICMP-port-unreachable reject. After applying, it SHALL verify the table is actually present, returning `NetfilterTableNotSetError` otherwise. It SHALL also include rules mitigating CVE-2019-14899 when LAN is allowed.

#### Scenario: TableVerifiedAfterApply
- **GIVEN** a policy applied on Linux
- **WHEN** `apply_policy` finishes sending the batch
- **THEN** the `nym` table is queried back and an error is returned if it is missing

#### Scenario: Cve201914899Mitigated
- **GIVEN** a tunnel with configured IPs and `allow_lan = true`
- **WHEN** rules are built
- **THEN** inbound packets destined to the tunnel IPs are dropped (after the allow-tunnel rule)

### Requirement: MacosPfEnforcement

On macOS the system SHALL enforce the policy through pf under the `nym` anchor, building scrub, NAT/redirect, and filter rules; ending with a drop-all filter rule; and clearing stale pf states for remote addresses that are no longer permitted by the policy (preserving states for allowed tunnel traffic and allowed endpoints). Rule logging level SHALL be controlled by `NYM_FIREWALL_DEBUG` (`pass`/`drop`/`all`).

#### Scenario: DropAllTrailingRule
- **GIVEN** a policy applied on macOS
- **WHEN** the pf filter rules are constructed
- **THEN** a final drop-all rule is appended so unmatched traffic is blocked

#### Scenario: StaleStatesCleared
- **GIVEN** a policy change on macOS
- **WHEN** rules are set
- **THEN** pf states for remote addresses no longer allowed are flushed, while states for allowed tunnel traffic and allowed endpoints are retained

### Requirement: WindowsWfpEnforcement

On Windows the system SHALL apply policy through the `WinFw` FFI module, supporting atomic entry into a blocked state at initialization (`WinFw_InitializeBlocked`) and policy application for connecting/connected/blocked states. It SHALL additionally manage Hyper-V (e.g. WSL) leak-blocking rules via WMI when entering blocked states (suppressible via `NYM_FIREWALL_BLOCK_HYPERV`), and SHALL surface `FirewallPolicyError::Locked` with an optional `BlockingApplication` when another application prevents the policy.

#### Scenario: AtomicBlockedInit
- **GIVEN** `FirewallArguments` with `InitialFirewallState::Blocked(endpoints)`
- **WHEN** the Windows `Firewall` is constructed via `from_args`
- **THEN** the firewall is initialized directly into the blocked state allowing only the given endpoints

#### Scenario: HypervLeakBlocking
- **GIVEN** a state where Hyper-V traffic should be blocked and `NYM_FIREWALL_BLOCK_HYPERV` is not disabling it
- **WHEN** the blocked policy is applied
- **THEN** Hyper-V blocking firewall rules are added via WMI (and removed when leaving that state)

### Requirement: MobileNoOpFirewall

On Android and iOS the system SHALL provide a stub `Firewall` whose `from_args`, `apply_policy`, and `reset_policy` always succeed without modifying any OS firewall, because filtering is performed by the platform VPN/tunnel service.

#### Scenario: ApplyPolicyIsNoOp
- **GIVEN** the crate compiled for Android or iOS
- **WHEN** `apply_policy` is called with any policy
- **THEN** it returns `Ok(())` and no OS firewall state is changed

## Technical Notes

- **Implementation**: `src/lib.rs` (`Firewall`, `FirewallPolicy`, `FirewallArguments`, `InitialFirewallState`, `FirewallPolicyError`, DHCP/NDP/ICMPv6 constants, policy `Display`); `src/net.rs` (`AllowedEndpoint`, `AllowedClients`, `AllowedTunnelTraffic`, `Endpoint`, `TransportProtocol`, `TunnelInterface`/`TunnelMetadata`, `AllowedDns` with `new_with_tunnel_dns` partitioning by local address); `src/linux.rs` (nftnl `PolicyBatch`, chains, split tunneling, kernel sysctls, table verification); `src/macos.rs` (pfctl anchor `nym`, state clearing, `RuleLogging`); `src/windows/mod.rs` + `ffi.rs` + `hyperv.rs` (`WinFw` FFI, WMI Hyper-V rules); `src/android.rs`, `src/ios.rs` (stubs).
- **Dependencies**: Workspace crates `nym-firewall-config` (LAN/multicast nets, `SPLIT_TUNNEL_MARK`, `is_local_address`), `nym-common`, `nym-cgroup` (Linux split-tunnel cgroup2), `nym-platform-metadata` (macOS). External: `nftnl`/`mnl`/`nix` (Linux nftables), `pfctl` (macOS), `windows`/`wmi`/`widestring` (Windows), `ipnetwork`/`libc`. Env vars: `NYM_FIREWALL_DEBUG` (rule counters/logging), `NYM_FIREWALL_DONT_SET_SRC_VALID_MARK`, `NYM_FIREWALL_DONT_SET_ARP_IGNORE` (Linux), `NYM_FIREWALL_BLOCK_HYPERV` (Windows). Role in workspace: the packet-filtering half of leak protection, paired with `nym-dns`, driven by the tunnel state machine which feeds it `FirewallPolicy` values.
