# nym-vpnd Specification

## Purpose

nym-vpnd is the NymVPN daemon. It runs as a privileged background process (standalone or as an OS service), owns the lifetime of the VPN tunnel via `nym_vpn_lib::service::NymVpnService`, and exposes a gRPC (tonic) `NymVpnService` over a local IPC transport (`nym-ipc`) so that CLI and GUI clients can drive connection, configuration, account, diagnostic, SOCKS5, and split-tunnel operations. It also broadcasts tunnel events to subscribers and manages logging, network environment setup, and graceful shutdown.

## Requirements

### Requirement: DaemonStartupModes

The daemon SHALL select its run mode from a clap subcommand, defaulting to standalone, and SHALL support Windows service install/uninstall/start commands when built for Windows.

#### Scenario: RunStandaloneByDefault
- **GIVEN** the daemon binary is invoked with no subcommand
- **WHEN** `CliArgs::parse()` resolves `command.unwrap_or_default()`
- **THEN** the default `Command::RunStandalone` is selected and `run_vpn_service` runs the daemon as a standalone process

#### Scenario: RunAsServiceOnWindows
- **GIVEN** the daemon is invoked with `RunAsService` on Windows
- **WHEN** `cli_args.is_run_as_service()` returns true
- **THEN** logging is configured for file output (not stdout) and `windows_service::start` registers the Windows service dispatcher

### Requirement: GrpcCommandInterface

The daemon SHALL host the `NymVpnService` gRPC service over a `nym-ipc` incoming stream and SHALL translate each RPC into a `VpnServiceCommand` dispatched to the VPN service over an unbounded channel, awaiting a oneshot reply.

#### Scenario: DispatchRpcToVpnService
- **GIVEN** a connected, authenticated gRPC client issues `connect_tunnel`
- **WHEN** the handler calls `send_and_wait(VpnServiceCommand::SetTargetState, TargetState::Secured)`
- **THEN** the command is sent to `NymVpnService`, the oneshot response is awaited, and the acceptance boolean is returned to the client

#### Scenario: ChannelClosedReturnsInternalError
- **GIVEN** the VPN command channel or response channel is closed
- **WHEN** a handler invokes `send_and_wait`
- **THEN** a `tonic::Status::internal` error ("Command channel is closed" / "Response channel is closed") is returned to the client

### Requirement: TunnelEventStreaming

The daemon SHALL expose a server-streaming `listen_to_events` RPC that forwards `TunnelEvent`s from an internal broadcast channel to all subscribed clients.

#### Scenario: SubscribeToTunnelEvents
- **GIVEN** a client calls `listen_to_events`
- **WHEN** the handler resubscribes to the `tunnel_event_rx` broadcast receiver
- **THEN** a boxed stream of `proto::TunnelEvent` items is returned, mapping receive errors to `tonic::Status::internal`

### Requirement: PlatformGatedRpcs

The daemon SHALL gate platform-specific RPCs at compile time and SHALL return an "Unsupported platform" internal error for RPCs invoked on platforms where the feature is unavailable.

#### Scenario: SplitTunnelProcessOnNonLinux
- **GIVEN** the daemon is not built for Linux
- **WHEN** a client calls `add_split_tunnel_process`
- **THEN** the handler returns `tonic::Status::internal("Unsupported platform")`

#### Scenario: SplitTunnelAppOnMacosOrWindows
- **GIVEN** the daemon is built for macOS or Windows
- **WHEN** a client calls `add_split_tunnel_app`
- **THEN** the request is converted to a `SplitApp` and dispatched via `VpnServiceCommand::AddSplitTunnelApp`

### Requirement: NetworkEnvironmentSetup

The daemon SHALL initialize the Nym network environment from a configured network name before spawning the VPN service, fetching the network config if the local cache is stale and exporting it to the process environment.

#### Scenario: FetchStaleNetworkCache
- **GIVEN** the local `NetworkCache` for the configured network has no valid network entry
- **WHEN** `setup_environment` runs
- **THEN** `fetch_if_stale` is awaited and the resolved network is exported to env via `export_to_env`

#### Scenario: WindowsServiceFetchFailureExitCode
- **GIVEN** the daemon runs as a Windows service and network environment setup fails
- **WHEN** `run_service` handles the error
- **THEN** the service is marked stopped with `ServiceSpecificExitCode::FetchNetworkEnvironment`

### Requirement: ConfigurablePaths

The daemon SHALL resolve its config, data, and log directories from environment variables with platform-specific defaults, allowing operators to override locations.

#### Scenario: OverrideConfigDir
- **GIVEN** the `NYM_VPND_CONFIG_DIR` environment variable is set
- **WHEN** `config_dir()` is called
- **THEN** the env-var value is used instead of the platform default (`/etc/nym` on non-Windows, `%ProgramData%\nym-vpnd\config` on Windows)

### Requirement: GracefulShutdown

The daemon SHALL install signal handlers that cancel a shared `CancellationToken`, propagating shutdown to the command interface and VPN service.

#### Scenario: CtrlCTriggersShutdown
- **GIVEN** the daemon is running standalone
- **WHEN** a Ctrl-C (and on Unix, SIGTERM or SIGQUIT) signal is received
- **THEN** the shutdown token is cancelled, the command interface shutdown token is cancelled, and the VPN service and command interface tasks are joined

#### Scenario: WindowsServiceStopEvent
- **GIVEN** the daemon runs as a Windows service
- **WHEN** the service control handler receives `ServiceControl::Stop`
- **THEN** the service status is set to pending-stop and the shutdown token is cancelled

### Requirement: ClientVerificationBypassFlag

The daemon SHALL accept an unsafe `--disable-client-verification` flag that is propagated into the IPC authentication material to skip client legitimacy checks for debugging.

#### Scenario: DisableClientVerification
- **GIVEN** the daemon is started with `RunWithArgs`/`RunAsService` and `disable_client_verification = true`
- **WHEN** `start_command_interface` builds `AuthenticationMaterial::new`
- **THEN** the flag is passed so the IPC layer skips client authentication checks

## Technical Notes

- **Implementation**: `src/main.rs` (startup, run modes, `spawn_vpn_service`), `src/command_interface.rs` (tonic `NymVpnService` impl, `start_command_interface`, `default_socket_path`), `src/environment.rs`, `src/paths.rs`, `src/shutdown_handler.rs`, `src/cli.rs`, `src/windows_service/mod.rs`.
- **Dependencies**: Wraps `nym-vpn-lib` (`NymVpnService`, `VpnServiceCommand`, config, logging, sentry, privy) — the daemon is a thin transport/lifecycle shell around that library. Uses `nym-ipc` (feature `daemon`) for the unix-socket / named-pipe / XPC transport, `nym-vpn-proto` for the gRPC `NymVpnService` definitions and type conversions, `nym-vpn-lib-types` for domain types, `nym-vpn-network-config` (`NetworkCache`) for environment setup, `tonic`/`tokio`/`tokio-util` for the async runtime and cancellation, and on Windows `windows-service`/`windows`/`eventlog`. Within the workspace, nym-vpnd is the privileged server that nym-vpnc and the GUI app (nym-vpn-app) connect to.
