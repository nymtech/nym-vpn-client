# nym-offline-monitor Specification

> Generated by openlore on 2026-06-26
> Source files: src/lib.rs, src/linux.rs, src/windows.rs, src/android.rs, src/apple/mod.rs, src/apple/macos.rs, src/apple/ios.rs, src/apple/path_monitor.rs

## Purpose

Detects the host's network connectivity (online/offline) and reports transitions to the rest of the VPN client so the tunnel and DNS subsystems can react — in particular to avoid getting stuck in a state that blocks all internet access. It exposes a single `ConnectivityHandle` and a `Connectivity` state model, backed by a per-platform monitor that watches OS routing/connectivity events (routing table on Linux/Windows/macOS, `Network.framework` path monitoring on Apple, a native callback adapter on Android). Several backends deliberately shape raw OS events (debouncing, synthetic offline) to work around platform-specific issues.

## Requirements

### Requirement: ConnectivityHandleApi

The system SHALL expose a cloneable `ConnectivityHandle`, constructed by an async `spawn_monitor` that takes platform-specific inputs (a `RouteManagerHandle` on Linux/Windows/macOS, a `NativeConnectivityAdapter` on Android, plus an optional `fwmark` on Linux) and returns immediately while the monitor task runs in the background. The handle SHALL expose `connectivity()` to read the current state and `next()` to await the next state change over an internal `watch` channel, and SHALL implement the `ConnectivityMonitor` async trait so it can be mocked.

#### Scenario: ReadCurrentState
- **GIVEN** a `ConnectivityHandle` returned by `spawn_monitor`
- **WHEN** `connectivity().await` is called
- **THEN** it returns the latest `Connectivity` value held in the watch channel

#### Scenario: AwaitNextChange
- **GIVEN** a `ConnectivityHandle`
- **WHEN** `next().await` is called and the underlying connectivity state subsequently changes
- **THEN** it resolves with the new `Connectivity` value (the call is cancel-safe)

### Requirement: ConnectivityStateModel

The system SHALL represent connectivity as a `Connectivity` enum. On non-Android platforms `Status { ipv4, ipv6 }` records whether IPv4 and IPv6 connectivity exist; on Android `Status { connected }` records a single boolean. `PresumeOnline` SHALL be used as the initial state and as the fallback whenever the real state cannot be determined. The system SHALL provide `is_online()`, `is_offline()`, and `has_ipv6()` helpers, where offline means no IP family is reachable.

#### Scenario: OfflineWhenNoFamilyReachable
- **GIVEN** a non-Android `Connectivity::Status { ipv4: false, ipv6: false }`
- **WHEN** `is_offline()` is evaluated
- **THEN** it returns true (and `is_online()` returns false)

#### Scenario: PresumeOnlineCountsAsOnline
- **GIVEN** a `Connectivity::PresumeOnline` state (the initial value or a fallback)
- **WHEN** `is_online()` is evaluated
- **THEN** it returns true so the client is never wrongly treated as offline when state is unknown

### Requirement: MonitorDisableSwitch

The system SHALL allow the monitor to be disabled via the `NYM_DISABLE_OFFLINE_MONITOR` environment variable, in which case `spawn_monitor` returns a handle whose state remains `PresumeOnline`.

#### Scenario: MonitorDisabledByEnv
- **GIVEN** `NYM_DISABLE_OFFLINE_MONITOR` is set
- **WHEN** `spawn_monitor` is called
- **THEN** no platform monitor task is started and the reported connectivity stays `PresumeOnline`

### Requirement: GracefulShutdown

The system SHALL stop the background monitor task when the `ConnectivityHandle` is dropped, by cancelling a `CancellationToken` via an internal `DropGuard` propagated to the spawned task.

#### Scenario: DropStopsMonitor
- **GIVEN** a running monitor owned by a `ConnectivityHandle`
- **WHEN** the last handle is dropped
- **THEN** the drop guard cancels the shutdown token and the spawned monitor task terminates

### Requirement: LinuxRouteProbing

On Linux the system SHALL subscribe to routing-table change events via `RouteManagerHandle`, and determine connectivity by probing for default routes to the public IPs `1.1.1.1` (IPv4) and `2606:4700:4700::1111` (IPv6), optionally constrained by the configured `fwmark`. A new state SHALL be published immediately whenever it differs from the previous one.

#### Scenario: RouteChangeUpdatesState
- **GIVEN** the Linux monitor listening on the route change stream
- **WHEN** a routing event removes the default route used to reach the probe IPs
- **THEN** the corresponding IP family is marked unreachable and, if the overall state changed, the new `Connectivity` is sent on the watch channel

### Requirement: WindowsRouteAndPowerMonitoring

On Windows the system SHALL track IPv4/IPv6 default routes via `RouteManagerHandle` default-route-change callbacks and observe sleep/resume through a `PowerManagementListener`. Offline transitions SHALL be published immediately, while offline→online transitions SHALL be delayed by `ONLINE_STABILIZATION_DELAY` (3 seconds) using a cancellable timer so a competing offline event cancels the pending online notification. On suspend the state SHALL be synthesized to offline and restored after resume (allowing time for tunnel re-initialization).

#### Scenario: OnlineTransitionStabilized
- **GIVEN** the Windows monitor currently reporting offline
- **WHEN** a default route appears
- **THEN** the online notification is scheduled after a 3-second delay, and is suppressed if an offline event arrives first

#### Scenario: SuspendForcesOffline
- **GIVEN** the Windows host enters sleep
- **WHEN** the power management listener reports suspend
- **THEN** the reported connectivity is set to offline and is restored after resume

### Requirement: AndroidNativeAdapter

On Android the system SHALL obtain connectivity from a consumer-provided `NativeConnectivityAdapter` async trait whose `next_connectivity()` yields a boolean, wrapping each distinct value as `Connectivity::Status { connected }`. If no initial value arrives within `INITIAL_STATE_TIMEOUT` (1 second), the state SHALL default to `PresumeOnline`.

#### Scenario: AdapterDrivesState
- **GIVEN** an Android monitor with a `NativeConnectivityAdapter`
- **WHEN** the adapter yields a connectivity boolean that differs from the current state
- **THEN** the monitor publishes `Connectivity::Status { connected }` on the watch channel

#### Scenario: InitialTimeoutPresumesOnline
- **GIVEN** the Android monitor has just started
- **WHEN** the adapter does not produce an initial value within 1 second
- **THEN** the state defaults to `PresumeOnline`

### Requirement: MacosRouteMonitorSyntheticOffline

On macOS the default backend SHALL listen to default-route add/remove events via `RouteManagerHandle`, and on every route event SHALL immediately publish a synthetic offline state (`ipv4: false, ipv6: false`) and then transition to the real state after `SYNTHETIC_OFFLINE_DURATION` (1 second). This deliberately forces an offline interval between network switches and before coming back online to work around macOS DNS blocking. The backend SHALL be switchable to the path monitor via the `NYM_USE_PATH_MONITOR` environment variable.

#### Scenario: SyntheticOfflineOnRouteChange
- **GIVEN** the macOS route monitor (default backend)
- **WHEN** a default-route change event occurs
- **THEN** an offline state is published immediately and the real state is published ~1 second later

#### Scenario: PathMonitorOptIn
- **GIVEN** `NYM_USE_PATH_MONITOR` is set on macOS
- **WHEN** `spawn_monitor` runs
- **THEN** the Apple path monitor backend is used instead of the route monitor

### Requirement: ApplePathMonitor

On macOS (opt-in) and iOS (always) the system SHALL monitor connectivity through Apple's `Network.framework` via `nym-apple-network`'s `PathMonitor` on a dedicated serial dispatch queue, mapping `NWPath` status to `Connectivity`: `Satisfied`/`Satisfiable` maps to `Status` reflecting `supports_ipv4()`/`supports_ipv6()`, `Unsatisfied` maps to offline, and `Unknown`/`Invalid` maps to `PresumeOnline` with a warning. Rapid path updates SHALL be coalesced with a `DEFAULT_PATH_DEBOUNCE` of 1 second, and the initial state SHALL default to `PresumeOnline` if none arrives within 1 second.

#### Scenario: PathStatusMapped
- **GIVEN** the Apple path monitor receives an `NWPath` update
- **WHEN** the path status is `Satisfied` with IPv4 support only
- **THEN** the published state is `Status { ipv4: true, ipv6: false }`

#### Scenario: PathUpdatesDebounced
- **GIVEN** the Apple path monitor receives several path updates in quick succession
- **WHEN** they arrive within the 1-second debounce window
- **THEN** they are coalesced into a single connectivity notification

#### Scenario: IosUsesPathMonitorOnly
- **GIVEN** the crate compiled for iOS
- **WHEN** `spawn_monitor` runs
- **THEN** it always uses the Apple path monitor (there is no route-monitor fallback)

## Technical Notes

- **Implementation**: `src/lib.rs` (`ConnectivityHandle`, `Connectivity` enum + `is_online`/`is_offline`/`has_ipv6`, `ConnectivityMonitor` async trait, `spawn_monitor`, watch channel seeded with `PresumeOnline`, `DropGuard` shutdown, `NYM_DISABLE_OFFLINE_MONITOR`); `src/linux.rs` (route listener probing `1.1.1.1`/`2606:4700:4700::1111`, `fwmark`); `src/windows.rs` (`BroadcastListener`, `SystemState`, `ONLINE_STABILIZATION_DELAY`, power/suspend handling); `src/android.rs` (`NativeConnectivityAdapter`, `INITIAL_STATE_TIMEOUT`); `src/apple/macos.rs` (route monitor with `SYNTHETIC_OFFLINE_DURATION`, `NYM_USE_PATH_MONITOR`); `src/apple/path_monitor.rs` (`Network.framework` `PathMonitor`, `DEFAULT_PATH_DEBOUNCE`, dispatch queue `net.nymtech.vpn.offline-monitor`); `src/apple/ios.rs` (path-monitor-only).
- **Dependencies**: Workspace crates `nym-routing` (`RouteManagerHandle` — the core route/connectivity source on Linux/Windows/macOS), `nym-windows` (`AddressFamily`, `PowerManagementListener`), `nym-common` (`ErrorExt`, flood detection), and on Apple `nym-apple-network` (`PathMonitor`/`NWPath`). External: `tokio` (watch/time/rt), `tokio-util` (`CancellationToken`/`DropGuard`), `tokio-stream`, `debounced` (Apple path debounce), `futures`, `dispatch2` (Apple GCD queue), `thiserror`, `tracing`, `async-trait`. Role in workspace: feeds online/offline transitions to the tunnel state machine in `nym-vpn-lib` and to DNS handling, complementing `nym-connection-monitor` (which watches in-tunnel data flow) — this crate watches host-level reachability.
