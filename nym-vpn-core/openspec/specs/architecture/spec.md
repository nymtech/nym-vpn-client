> Generated by openlore on 2026-06-26

## Purpose

This spec documents the structural organization of the nym-vpn-core workspace: how
the ~38 crates are layered, how the engine is consumed on desktop versus mobile,
and the dependency direction between layers. It describes the system as a whole;
each crate's behavior is documented in its own domain spec.

## Requirements

### Requirement: CargoWorkspaceComposition

The system SHALL be organized as a single Cargo workspace whose members are
single-responsibility crates declared in the root `Cargo.toml`.

#### Scenario: Adding a capability
- **GIVEN** a new platform or networking capability is needed
- **WHEN** it is implemented
- **THEN** it lives in its own crate registered under workspace `members`, keeping responsibilities isolated

### Requirement: LayeredDependencyDirection

The system SHALL be layered so that platform/utility crates and shared-type crates
are depended upon by the core library, which is in turn depended upon by the
daemon/clients and the FFI bindings — dependencies point downward, never up.

#### Scenario: Core orchestration consumes lower layers
- **GIVEN** `nym-vpn-lib` orchestrates a connection
- **WHEN** it needs DNS, routing, firewall, split-tunnel, gateway, account, or WireGuard functionality
- **THEN** it depends on the dedicated crates (`nym-dns`, `nym-routing`, `nym-firewall`, `nym-split-tunnel`, `nym-gateway-directory`, `nym-vpn-account-controller`, `nym-wg-go`, etc.) rather than reimplementing them

### Requirement: SharedTypeContract

The system SHALL centralize cross-cutting domain types (tunnel/connection states,
errors, status events) in `nym-vpn-lib-types` and the gRPC contract in
`nym-vpn-proto`, so the engine, daemon, clients, and FFI agree on one data model.

#### Scenario: Consistent state across boundaries
- **GIVEN** a tunnel state change occurs in the engine
- **WHEN** it is reported to a desktop client over gRPC and to a mobile host over UniFFI
- **THEN** both surfaces represent the state using the shared types/contract converted from `nym-vpn-lib-types`

### Requirement: DesktopControlPlane

The system SHALL deliver desktop functionality through the `nym-vpnd` daemon, which
embeds `nym-vpn-lib`, serves the `nym-vpn-proto` gRPC API over `nym-ipc` transport,
and is consumed by the `nym-vpnc` CLI and the GUI application.

#### Scenario: CLI controls the daemon
- **GIVEN** `nym-vpnd` is running
- **WHEN** `nym-vpnc` issues a command
- **THEN** the command travels over the IPC transport to the daemon's gRPC service, which drives `nym-vpn-lib`

### Requirement: MobileBindingLayer

The system SHALL deliver mobile functionality through UniFFI crates
(`nym-vpn-lib-uniffi`, `nym-vpn-rpc-uniffi`) that wrap `nym-vpn-lib` and generate
Swift/Kotlin bindings via `uniffi-bindgen`, without a separate daemon process.

#### Scenario: Generating bindings
- **GIVEN** the mobile build pipeline runs
- **WHEN** it invokes `uniffi-bindgen`
- **THEN** Swift/Kotlin bindings are generated from the UniFFI crate's exported interface

### Requirement: UpstreamNymDependencies

The system SHALL build on the broader Nym platform crates (e.g. `nym-sdk`,
`nym-client-core`, `nym-crypto`, `nym-validator-client`, `nym-credentials-interface`)
that are sourced from outside this workspace.

#### Scenario: Mixnet client functionality
- **GIVEN** the engine needs mixnet client primitives or chain access
- **WHEN** it establishes a mixnet path or validates credentials
- **THEN** it relies on the upstream Nym crates rather than reimplementing mixnet/crypto/chain logic

### Requirement: TestHarnessSeparation

The system SHALL keep end-to-end test infrastructure in dedicated crates under
`crates/test/` (`test-manager`, `test-rpc`, `test-runner`), separate from shipping crates.

#### Scenario: Running integration tests
- **GIVEN** an integration test run is started
- **WHEN** the test-manager orchestrates a target
- **THEN** it drives the test-runner over the test-rpc contract, isolated from production crates

## Technical Notes

- **Implementation**: root `Cargo.toml` (workspace members); layering visible in `crates/nym-vpn-lib/Cargo.toml` (depends on platform + shared-type crates), `crates/nym-vpnd/Cargo.toml` (depends on `nym-vpn-lib`, `nym-vpn-proto`, `nym-ipc`), `crates/nym-vpn-lib-uniffi/Cargo.toml` (depends on `nym-vpn-lib`)
- **Dependencies**: internal layering — platform/utility crates → `nym-vpn-lib` → {`nym-vpnd` + `nym-vpnc`} / {`nym-vpn-lib-uniffi` + `nym-vpn-rpc-uniffi`}; shared types via `nym-vpn-lib-types` and `nym-vpn-proto`; external upstream Nym platform crates (`nym-sdk`, `nym-client-core`, `nym-crypto`, etc.)
