## Purpose

This crate generates the UniFFI bindings that expose the Nym VPN library (`nym-vpn-lib`) to Swift (iOS) and Kotlin (Android) frontends. It is compiled only for `target_os = "android"` or `target_os = "ios"` and presents a platform-agnostic, async, object-oriented FFI surface for library/environment initialization, gateway lookup, account management, deeplink handling, and full tunnel lifecycle control. It bridges foreign callbacks (tun providers, connectivity monitors, tunnel status listeners) back into the native Rust async runtime.

## Requirements

### Requirement: PlatformGatedScaffolding

The crate MUST compile its FFI scaffolding only on mobile targets and MUST register the UniFFI scaffolding before exporting any object, record, enum, or callback.

#### Scenario: Building for a non-mobile target
- **GIVEN** the crate is compiled with a target that is neither `android` nor `ios`
- **WHEN** the compiler evaluates the crate-level `#![cfg(any(target_os = "android", target_os = "ios"))]` attribute
- **THEN** the crate body is empty and no FFI symbols are produced

#### Scenario: Building for a mobile target
- **GIVEN** the crate is compiled for `ios` or `android`
- **WHEN** `uniffi::setup_scaffolding!()` runs at crate root
- **THEN** the UniFFI runtime scaffolding is initialized and all `#[uniffi::export]` items become part of the generated bindings

### Requirement: AsyncRuntimeBridging

The system MUST bridge exported `async` methods onto a Tokio runtime and MUST run resource-heavy VPN service construction on a dedicated multi-threaded runtime separate from the UniFFI async adapter.

#### Scenario: Exported async object methods
- **GIVEN** an exported impl block annotated `#[uniffi::export(async_runtime = "tokio")]`
- **WHEN** a foreign caller invokes an `async fn` such as `NymGatewayCache::get_gateways` or `NymVpnServiceCommandSender::connect_tunnel`
- **THEN** the future is driven on the Tokio runtime provided by the `uniffi` `tokio` feature

#### Scenario: Constructing the VPN service
- **GIVEN** the UniFFI async adapter runs on a single-threaded runtime
- **WHEN** `NymVpnService::new_service` is called
- **THEN** the service is spawned on the crate's static multi-threaded `TOKIO_RUNTIME` (10 worker threads) and a join failure is mapped to `VpnError::InternalError`

### Requirement: EnvironmentInitialization

The system SHALL expose `NymEnvironment` for resolving network configuration either from a cache directory (with network fetch fallback) or from built-in mainnet defaults, and MUST export it to the process environment before the VPN service starts.

#### Scenario: Cache-directory environment with network fetch
- **GIVEN** a cache directory, a network name, and a `UserAgent`
- **WHEN** `NymEnvironment::new_with_cache_dir` is called and the cached network is unavailable
- **THEN** the network is fetched if stale, and on fetch failure `VpnError::FetchEnvironment` is returned

#### Scenario: Offline mainnet fallback
- **GIVEN** no network connectivity is desired
- **WHEN** `NymEnvironment::new_with_mainnet_fallback` is called
- **THEN** mainnet defaults are loaded without network calls, so no system messages or account links are populated

### Requirement: LoggingAndSentryInitialization

The system SHALL provide a one-time `initLogger` entry point that configures tracing verbosity, optional file logging, and optional Sentry monitoring before any other FFI object is created.

#### Scenario: Initializing logging once
- **GIVEN** the library has just been loaded
- **WHEN** `initLogger(log_dir, log_level, sentry_monitoring)` is called
- **THEN** logging is configured exactly once via a `OnceLock`, Sentry is initialized only when `sentry_monitoring` is true, and software/OS version are logged

#### Scenario: Querying Sentry state during service construction
- **GIVEN** `initLogger` may or may not have enabled Sentry
- **WHEN** `NymVpnService::new_service` reads `logging::is_sentry_enabled()`
- **THEN** the resulting `sentry_enabled` flag is propagated into the spawned VPN service parameters

### Requirement: TunnelLifecycleControl

The system MUST expose tunnel control through a command-sender object that serializes foreign requests into `VpnServiceCommand` messages over an mpsc channel and awaits a oneshot reply, and MUST forward tunnel events to a foreign listener.

#### Scenario: Sending a control command
- **GIVEN** an active `NymVpnServiceCommandSender`
- **WHEN** a method such as `connect_tunnel`, `disconnect_tunnel`, `reconnect_tunnel`, or `set_enable_two_hop` is awaited
- **THEN** the corresponding `VpnServiceCommand` is sent with a oneshot reply channel, and a closed command or response channel yields `NymVpnServiceCommandError` with an `"Command channel is closed"` / `"Response channel is closed"` internal message

#### Scenario: Delivering tunnel events to the foreign listener
- **GIVEN** a foreign `TunnelStatusListener` passed to `NymVpnService::new_service`
- **WHEN** the spawned event handler receives a `TunnelEvent` from the broadcast channel
- **THEN** `TunnelEvent::NewState` updates the internal tunnel-state watch channel and every event is forwarded via `on_event`

#### Scenario: Graceful shutdown
- **GIVEN** a running `NymVpnService`
- **WHEN** `shutdown_and_wait` is called
- **THEN** a disconnect is requested, the service waits up to `DISCONNECT_TIMEOUT` (5s) for a `Disconnected` or `Offline` state, then drops the shutdown guard and joins the event handler and service tasks

### Requirement: ForeignCallbackTraits

The system MUST expose platform-specific behavior to native code through foreign-implementable trait objects registered with `with_foreign`, adapting them to the `nym-vpn-lib` provider interfaces.

#### Scenario: iOS tunnel provider
- **GIVEN** an iOS app implementing `OSTunProvider`
- **WHEN** the library needs to apply tunnel settings
- **THEN** `OSTunProviderImpl` forwards `set_tunnel_network_settings` to the foreign object and maps `VpnError` into a `std::io::Error`

#### Scenario: Android tunnel provider
- **GIVEN** an Android app implementing `AndroidTunProvider`
- **WHEN** the library needs to bypass a socket or configure the tunnel
- **THEN** `AndroidTunProviderImpl` forwards `bypass`/`configure_tunnel`, returning a `RawFd` on success and mapping `VpnError` to a `std::io::Error`

#### Scenario: Android connectivity monitoring
- **GIVEN** an Android app implementing `AndroidConnectivityMonitor` and `ConnectivityObserver`
- **WHEN** `register_connectivity_observer` wires a `ConnectivitySender` into the foreign monitor
- **THEN** connectivity changes are delivered over an unbounded channel and consumed by `NymOfflineMonitor`

### Requirement: AccountManagementSurface

The system SHALL expose account, device, deeplink, and gateway-cache management both through a controller-backed object and through a direct storage object usable when no controller is running.

#### Scenario: Controller-backed account management
- **GIVEN** an initialized `NymAccountController`
- **WHEN** the caller logs in, registers, creates, forgets, rotates keys, or queries identities/summary
- **THEN** the request is dispatched to the account controller via `AccountCommandSender` and errors are mapped to `VpnError`

#### Scenario: Direct storage when controller is absent (iOS)
- **GIVEN** the account controller is not running
- **WHEN** the caller uses `NymVpnAccountStorage` (e.g. `login`, `forget_account`, `register_account`, `get_account_summary`)
- **THEN** storage and VPN API calls are performed directly, and `get_account_summary` falls back to cached summary when the network sync fails

#### Scenario: Gateway lookup without a running service
- **GIVEN** a `UserAgent`, `NymEnvironment`, and `NymOfflineMonitor`
- **WHEN** `NymGatewayCache::get_gateways(gw_type)` is awaited
- **THEN** gateways are looked up via the directory client and network failures are mapped to `VpnError::NetworkConnectionError`

### Requirement: ErrorMappingToForeignType

The system MUST map all internal error types into the single flat `VpnError` enum exported across the FFI boundary so foreign code observes a stable, exhaustive error surface.

#### Scenario: Mapping account command errors
- **GIVEN** an `AccountCommandError` produced by the account controller
- **WHEN** it is converted via `From<AccountCommandError> for VpnError`
- **THEN** each variant maps to a specific `VpnError` case (e.g. `NoAccountStored`, `InvalidMnemonic`, `InsufficientFunds`, `Offline` -> `NetworkConnectionError`)

#### Scenario: Mapping infrastructure errors
- **GIVEN** an HTTP client, tunnel state machine, on-disk key/mnemonic storage, or account controller error
- **WHEN** the corresponding `From` impl runs
- **THEN** it collapses into a `VpnError` variant such as `HttpClient`, `Storage`, or `InternalError`

## Technical Notes

- **Implementation**: `src/lib.rs` (scaffolding, `VPNConfig`, `TOKIO_RUNTIME`, Android JNI `initContext`, Android webpki TLS), `src/vpn_service.rs`, `src/vpn_service_command_sender.rs`, `src/account.rs`, `src/vpn_account_storage.rs`, `src/gateway_cache.rs`, `src/environment.rs`, `src/logging.rs`, `src/offline_monitor.rs`, `src/deeplink.rs`, `src/error.rs`, `src/tunnel_provider/*`.

Built on `uniffi` (`tokio` feature), `tokio`, `tokio-util`, `sentry`, plus Android-only `jni`/`ndk-context`/`rustls`/`inventory`. In the workspace this crate is the mobile (iOS/Android) FFI front door to the core VPN library, parallel to `nym-vpn-rpc-uniffi` which binds the daemon RPC client instead.
