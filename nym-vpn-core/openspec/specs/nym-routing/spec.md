## Purpose

The `nym-routing` crate manages OS routing tables across Linux, macOS, and Windows for the Nym VPN client. It applies a set of required routes to the system, optionally binding them to a symbolic "default node" that is re-resolved whenever the host's default route changes, and it monitors the network for default-route and interface changes. All operations run through an asynchronous actor (`RouteManagerImpl`) driven by commands sent over a channel from a cloneable `RouteManagerHandle`.

## Requirements

### Requirement: RouteManagerHandleLifecycle

The system SHALL provide a cloneable `RouteManagerHandle` that spawns an asynchronous route manager actor and tears it down on `stop()`, reverting all routing changes it applied.

The handle is constructed with `RouteManagerHandle::spawn()` (taking `fwmark` and `table_id` on Linux), which creates a `RouteManagerImpl` and spawns it on a tokio task, returning a handle wrapping an `Arc<mpsc::UnboundedSender<RouteManagerCommand>>`. `stop()` sends `RouteManagerCommand::Shutdown` and awaits a oneshot acknowledgement.

#### Scenario: Spawn route manager
- **GIVEN** a tokio runtime
- **WHEN** `RouteManagerHandle::spawn(...)` is called
- **THEN** a `RouteManagerImpl` is created, spawned on a task, and a `RouteManagerHandle` is returned, or `Error::PlatformError` if platform initialization fails

#### Scenario: Stop reverts routes
- **GIVEN** a running route manager that has applied routes
- **WHEN** `stop()` is called
- **THEN** a `Shutdown` command is sent, the actor cleans up all applied routes, and the call awaits the acknowledgement

### Requirement: ApplyAndClearRoutes

The system SHALL apply a set of `RequiredRoute` entries via `add_routes` until they are explicitly cleared, and SHALL remove all previously applied routes via `clear_routes`.

`add_routes(routes: HashSet<RequiredRoute>)` is async and sends `RouteManagerCommand::AddRoutes`, returning the platform result. `clear_routes()` is synchronous (fire-and-forget) and sends `RouteManagerCommand::ClearRoutes`. On the actor side, applied routes are tracked (Linux: `added_routes: HashSet<Route>`; macOS: `applied_routes: BTreeMap`; Windows: route records) so they can be removed later.

#### Scenario: Add routes
- **GIVEN** a set of `RequiredRoute` entries
- **WHEN** `add_routes` is called
- **THEN** the routes are inserted into the system routing table and tracked, and `Ok(())` is returned, or `Error::PlatformError` if a route fails

#### Scenario: Clear routes
- **GIVEN** routes previously applied via `add_routes`
- **WHEN** `clear_routes` is called
- **THEN** all tracked routes are deleted from the routing table; failures during individual deletions are logged but cleanup continues

### Requirement: SymbolicDefaultNodeResolution

The system SHALL support routing through a symbolic `NetNode::DefaultNode` on macOS and Windows that resolves to the host's current best default route, and SHALL re-resolve such routes when the default route changes. On Linux, `NetNode::DefaultNode` is not available.

On Windows, `resolve_node` calls `get_best_default_route()` for `DefaultNode`, returning `Error::NoDefaultRoute` when none exists; when the default route changes, the affected routes are deleted, their LUID and next-hop updated, and re-added. On macOS, `DefaultNode` routes are stored in `non_tunnel_routes` and resolved against `best_default_route` in `apply_non_tunnel_routes`. On Linux, `add_required_routes` filters to `NetNode::RealNode` only.

#### Scenario: Default node resolves at apply time
- **GIVEN** a `RequiredRoute` whose node is `NetNode::DefaultNode` (macOS/Windows)
- **WHEN** the route is applied
- **THEN** it is resolved to the current best default route's interface and gateway

#### Scenario: Default node re-resolves on change
- **GIVEN** an applied route bound to `DefaultNode`
- **WHEN** the host's default route changes
- **THEN** the monitor detects the change and the affected route is deleted and re-added through the new default route

### Requirement: DefaultRouteMonitoring

The system SHALL monitor the host for changes to the best non-tunnel default route and notify registered listeners, coalescing bursts of low-level notifications.

On macOS, `default_route_listener()` returns a receiver of `DefaultRouteEvent` (`AddedOrChangedV4`/`V6`, `RemovedV4`/`V6`); `DefaultRouteMonitor` tracks the primary interface and applies a 5-second grace period (`NO_ROUTE_GRACE_TIME`) before reporting route loss. On Windows, `DefaultRouteMonitor` registers `NotifyRouteChange2`, `NotifyIpInterfaceChange`, and `NotifyUnicastIpAddressChange` callbacks and emits `EventType::Updated`, `UpdatedDetails`, or `Removed`. Both platforms debounce via `BurstGuard` (200ms buffer, 2s max).

#### Scenario: Default route removed (macOS grace)
- **GIVEN** the macOS default route monitor is running
- **WHEN** the best default route disappears
- **THEN** the `None` notification is delayed by the 5-second grace time before being delivered to listeners, unless a new route appears first

#### Scenario: Burst coalescing
- **GIVEN** rapid low-level routing notifications on macOS or Windows
- **WHEN** they arrive within the buffer period
- **THEN** the `BurstGuard` waits up to 200ms of silence (or 2s total) before invoking the callback once

### Requirement: BestDefaultRouteSelection

The system SHALL select the best default route by choosing the route with destination prefix length 0 that has a gateway and resides on a physical interface, ordered by lowest effective metric.

On Windows, `get_best_default_route(family)` reads the IP forward table, filters for prefix length 0, `route_has_gateway()`, and `is_route_on_physical_interface()` (excluding loopback, tunnel, and adapters described as "WireGuard"/"Wintun"/"Tunnel"), annotates each with route-metric + interface-metric, and returns the lowest-metric entry or `None`.

#### Scenario: Pick lowest-metric physical default route
- **GIVEN** multiple default routes on the host
- **WHEN** `get_best_default_route` is called
- **THEN** virtual/tunnel/loopback interfaces are excluded and the remaining default route with the lowest effective metric is returned, or `None` if there is none

### Requirement: PlatformSpecificRouteBackends

The system SHALL implement routing through the platform-native mechanism: rtnetlink on Linux, the BSD `PF_ROUTE` routing socket on macOS, and the IP Helper API (`CreateIpForwardEntry2`/`DeleteIpForwardEntry2`) on Windows.

On Linux, `RouteManagerImpl` uses netlink and supports per-table routing via `fwmark`/`table_id`. On macOS, routes are applied via `RoutingTable` over a routing socket and require a device (gateway-by-IP-only is logged as unimplemented and skipped). On Windows, `add_into_routing_table` uses `CreateIpForwardEntry2`, falling back to `SetIpForwardEntry2` when `ERROR_OBJECT_ALREADY_EXISTS`, and deletion ignores `ERROR_NOT_FOUND`.

#### Scenario: Existing route overwrite on Windows
- **GIVEN** a route to add on Windows that already exists in the table
- **WHEN** `CreateIpForwardEntry2` returns `ERROR_OBJECT_ALREADY_EXISTS`
- **THEN** the route is overwritten via `SetIpForwardEntry2`

#### Scenario: macOS requires device
- **GIVEN** a macOS `RealNode` route specifying only a gateway IP and no device
- **WHEN** `add_required_routes` processes it
- **THEN** an error is logged that gateway-by-IP is unimplemented and the route is skipped

### Requirement: AtomicBatchAddWithRollback

The system SHALL, on Windows, roll back routes added earlier in a batch if a later route in the same `add_routes` call fails, leaving the routing table unchanged from before the batch.

`RouteManagerInternal::add_routes` maintains an event log and, on failure, calls `undo_events()` to process events in reverse and delete the routes it added.

#### Scenario: Batch failure rollback
- **GIVEN** a batch of routes being added on Windows
- **WHEN** one route in the batch fails to add
- **THEN** all routes already added in that batch are deleted via `undo_events` and an error is returned

### Requirement: LinuxRoutingRulesAndTables

The system SHALL, on Linux, create and clear policy routing rules that direct packets to the configured routing table, and SHALL support adding routes either to the main table or to a dedicated table.

`create_routing_rules(enable_ipv6)` and `clear_routing_rules()` send the corresponding commands; `RequiredRoute::use_main_table(bool)` selects `RT_TABLE_MAIN` versus the dedicated `table_id`. Rules route unmarked packets to the custom table and suppress prefix-0 routes.

#### Scenario: Route into dedicated table
- **GIVEN** a `RequiredRoute` configured with `use_main_table(false)` on Linux
- **WHEN** it is applied
- **THEN** the route is installed in the configured `table_id` rather than the main table

#### Scenario: Create routing rules
- **GIVEN** a running Linux route manager
- **WHEN** `create_routing_rules(enable_ipv6)` is called
- **THEN** policy rules are installed so unmarked traffic uses the custom table

### Requirement: LinuxRouteQueriesAndMtu

The system SHALL, on Linux, answer route-lookup and MTU queries for a destination, following gateway hops recursively to discover the MTU.

`get_destination_route(destination, mark)` returns the route for a destination (with optional firewall mark). `get_mtu_for_route(ip)` follows routes up to 10 times: it returns a device's MTU when the route has a device, recurses on the gateway IP otherwise, and defaults to 1500 when no custom MTU is found.

#### Scenario: Recursive MTU discovery
- **GIVEN** a destination IP whose route resolves only to a gateway
- **WHEN** `get_mtu_for_route` is called
- **THEN** the resolver follows the gateway hops (up to 10 iterations) until it finds a device, returning that device's MTU or defaulting to 1500

### Requirement: RouteChangeEventStreams

The system SHALL expose platform-appropriate event streams for route and interface changes to subscribers.

On Linux, `change_listener()` returns a receiver of `CallbackMessage::NewRoute`/`DelRoute` derived from netlink multicast (`RTMGRP_IPV4_ROUTE`/`RTMGRP_IPV6_ROUTE`). On macOS, `interface_change_listener()` returns `InterfaceEvent { interface_index, mtu }` parsed from `PF_ROUTE` link messages, and `get_default_gateway()` resolves the best default routes to gateway MAC addresses.

#### Scenario: Linux route change broadcast
- **GIVEN** a subscriber registered via `change_listener`
- **WHEN** the kernel reports a new or deleted route over netlink
- **THEN** a `CallbackMessage::NewRoute` or `DelRoute` is delivered to the subscriber, and dropped subscribers are pruned

### Requirement: RecoverableErrorClassification

The system SHALL classify whether a failed routing operation is recoverable so callers can decide to retry.

`Error::is_recoverable()` returns `true` on macOS only for `PlatformError(RouteError::Unreachable)` (the case where the default route vanished before the offline monitor caught it), and `false` on all other platforms and errors.

#### Scenario: Retry on unreachable
- **GIVEN** a macOS `add_routes` call that fails with `RouteError::Unreachable`
- **WHEN** the caller inspects `error.is_recoverable()`
- **THEN** it returns `true`, indicating a retry is likely to succeed

## Technical Notes

- **Implementation**: `src/lib.rs` (public types `Route`, `RequiredRoute`, `NetNode`, `Node`, `MacAddress`, `Gateway`); `src/unix/mod.rs` (`RouteManagerHandle`, `Error`, `RouteManagerCommand`); `src/unix/linux.rs` (netlink backend); `src/unix/macos/mod.rs`, `src/unix/macos/default_routes.rs`, `src/unix/macos/watch.rs` (PF_ROUTE backend + monitors); `src/windows/route_manager.rs`, `src/windows/default_route_monitor.rs`, `src/windows/get_best_default_route.rs` (IP Helper backend); `src/debounce.rs` (`BurstGuard`).
- **Dependencies**: External — `rtnetlink`/`libc` (Linux), `nix`/`system-configuration`/`bitflags` (macOS), `windows`/`nym-windows`/`widestring` (Windows), `ipnetwork`, `tokio`, `futures`, `thiserror`, `tracing`; internal — `nym-common` (non-Android). In the workspace, `nym-routing` is the low-level OS routing primitive consumed by higher-level crates including `nym-split-tunnel`, which uses `RouteManagerHandle` to learn default routes/gateways while steering excluded traffic. The code derives from Mullvad VPN's routing manager, adapted by Nym.
