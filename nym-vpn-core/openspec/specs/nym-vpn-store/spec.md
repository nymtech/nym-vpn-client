## Purpose

Defines the persistent-storage abstraction for the VPN client's secrets and account state: the account mnemonic, device ed25519 keys, per-gateway WireGuard x25519 keys, and a cached account summary. It specifies storage traits and provides both on-disk (file/PEM/SQLite) and in-memory ephemeral backends, with secure file permissions, key zeroization, and key expiry.

## Requirements

### Requirement: VpnStorageTraitComposition

The system SHALL define a `VpnStorage` super-trait composing account information storage, device key storage, and account summary storage, so a single backend satisfies all three.

#### Scenario: BackendImplementsAllStorage
- **GIVEN** a type implementing `AccountInformationStorage`, `DeviceKeyStore`, and `AccountSummaryStorage`
- **WHEN** it is used where a `VpnStorage` is expected
- **THEN** it is accepted as a complete VPN storage backend

### Requirement: AccountMnemonicPersistence

The system SHALL store and load a `StorableAccount` (mnemonic plus account mode), returning `None` (not an error) when no account is stored, and the on-disk backend MUST refuse to overwrite an existing account file.

#### Scenario: LoadReturnsNoneWhenAbsent
- **GIVEN** no account file exists
- **WHEN** `load_account` is called on the on-disk store
- **THEN** `Ok(None)` is returned rather than an error

#### Scenario: StoreRefusesOverwrite
- **GIVEN** an account already stored at the path
- **WHEN** `store_account` is called again
- **THEN** `OnDiskMnemonicStorageError::MnemonicAlreadyStored` is returned

### Requirement: LegacyAccountCompatibility

The system SHALL deserialize legacy stored-mnemonic records that lack a `mode` field, defaulting the account mode, so existing installations keep working.

#### Scenario: LoadLegacyMnemonic
- **GIVEN** a previously written mnemonic file without a `mode` field
- **WHEN** `load_account` is called
- **THEN** a `StorableAccount` is returned with the default account mode

### Requirement: SecretFilePermissions

The system SHALL restrict on-disk secret storage to the owner on Unix, setting the containing directory to `0o700` and the mnemonic file to `0o600`, and enforcing `0o600` on load.

#### Scenario: RestrictMnemonicFilePermissions
- **GIVEN** a Unix host
- **WHEN** the mnemonic is stored and later loaded
- **THEN** the parent directory is `0o700` and the file is `0o600`

### Requirement: DeviceKeyLifecycle

The system SHALL manage ed25519 device keys via `DeviceKeyStore` with load/store/init/reset/remove operations, where `init_keys` is a no-op if keys already exist, `reset_keys` overwrites them, and key generation MAY be seeded deterministically.

#### Scenario: InitDoesNotOverwrite
- **GIVEN** device key files already exist on disk
- **WHEN** `init_keys` is called
- **THEN** existing keys are left unchanged

#### Scenario: SeededDeterministicGeneration
- **GIVEN** a 32-byte seed is provided to `reset_keys`
- **WHEN** keys are generated
- **THEN** a ChaCha20-seeded RNG produces the keypair deterministically; otherwise `OsRng` is used

### Requirement: KeyZeroization

The system SHALL store private key material in zeroize-on-drop key types so secrets are wiped from memory when dropped.

#### Scenario: KeysZeroizeOnDrop
- **GIVEN** device keys held in memory
- **WHEN** the keypair is dropped
- **THEN** the underlying ed25519 key material is zeroized (statically asserted via `ZeroizeOnDrop`)

### Requirement: WireguardKeyExpiry

The system SHALL persist per-gateway WireGuard x25519 entry/exit keypairs in SQLite with an expiration timestamp, returning existing keys only when unexpired and otherwise generating and storing fresh keys.

#### Scenario: RegenerateExpiredKeys
- **GIVEN** stored WireGuard keys for a gateway whose expiration time has passed
- **WHEN** `load_or_create_keys(gateway_id)` is called
- **THEN** new keypairs are generated, persisted with a new expiration, and returned

### Requirement: EphemeralStorageBackends

The system SHALL provide in-memory ephemeral implementations of the storage traits for testing and non-persistent use.

#### Scenario: UseInMemoryKeys
- **WHEN** an `InMemEphemeralKeys` (or ephemeral account/summary store) is used
- **THEN** data is kept only in memory and not written to disk
