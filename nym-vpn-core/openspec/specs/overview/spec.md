# nym-vpn-core Overview Specification

> Generated by openlore on 2026-06-26

## Purpose

nym-vpn-core is the Rust workspace that implements the cross-platform engine of the
Nym VPN client. It establishes privacy-preserving tunnels over the Nym mixnet (a
5-hop, anonymizing data path) and over WireGuard, manages the full tunnel
lifecycle and OS-level networking (DNS, routing, firewall, split tunneling),
handles account/credential management against the Nym VPN API, and exposes the
engine to host applications through a local control daemon (`nym-vpnd` + gRPC) on
desktop and through UniFFI bindings on iOS and Android. The workspace is composed
of ~38 single-responsibility crates plus an end-to-end test harness.

## Requirements

### Requirement: MixnetAndWireguardTunnels

The system SHALL support establishing a VPN connection over either the Nym mixnet
(5-hop anonymizing path) or WireGuard (2-hop), selectable per connection.

#### Scenario: Connect over the mixnet
- **GIVEN** a configured account and a selected entry/exit gateway
- **WHEN** the user requests a mixnet connection
- **THEN** the engine builds the mixnet data path and transitions the tunnel to Connected

#### Scenario: Connect over WireGuard
- **GIVEN** a configured account and WireGuard-capable gateways
- **WHEN** the user requests a WireGuard (dVPN) connection
- **THEN** the engine configures a WireGuard tunnel via the wireguard-go bridge and connects

### Requirement: CrossPlatformSupport

The system SHALL run on Linux, macOS, Windows, iOS, and Android, isolating
platform-specific behavior in dedicated crates.

#### Scenario: Platform-specific networking
- **GIVEN** the engine runs on a given operating system
- **WHEN** it configures DNS, routing, or the firewall
- **THEN** it dispatches to the platform-appropriate implementation (e.g. nftables/pf/WFP for firewall)

### Requirement: DaemonControlPlaneDesktop

The system SHALL provide a control daemon (`nym-vpnd`) that owns the tunnel and
exposes a gRPC API consumed by desktop clients (CLI `nym-vpnc` and the GUI app).

#### Scenario: Client commands the daemon
- **GIVEN** `nym-vpnd` is running as a privileged service
- **WHEN** a client sends a connect/disconnect/status request over the IPC gRPC channel
- **THEN** the daemon executes the command and streams status/state events back

### Requirement: MobileFfiBindings

The system SHALL expose its functionality to mobile hosts through UniFFI bindings
for Swift (iOS) and Kotlin (Android).

#### Scenario: Mobile app drives a connection
- **GIVEN** the iOS/Android app links the generated UniFFI bindings
- **WHEN** it calls the exported connect API
- **THEN** the Rust engine runs the tunnel and reports state changes through the FFI callback interface

### Requirement: AccountAndCredentialManagement

The system SHALL manage account login, device registration, and zk-nym
credentials required to use Nym gateways.

#### Scenario: Authorized usage
- **GIVEN** a user has logged in with an account mnemonic
- **WHEN** the engine needs to connect
- **THEN** it ensures the device is registered and valid credentials/ticketbooks are available

### Requirement: NetworkEnvironmentDiscovery

The system SHALL discover its network environment configuration (e.g. mainnet vs.
other environments, API/validator endpoints, feature flags) at runtime.

#### Scenario: Bootstrap configuration
- **GIVEN** a selected network environment
- **WHEN** the engine starts
- **THEN** it resolves the Nym VPN API and chain endpoints and applicable feature flags before connecting

## Technical Notes

- **Implementation**: workspace root `Cargo.toml`; orchestration in `crates/nym-vpn-lib`; daemon in `crates/nym-vpnd`; FFI in `crates/nym-vpn-lib-uniffi`
- **Dependencies**: tokio (async runtime), tonic/prost (gRPC), uniffi (mobile bindings), wireguard-go via `crates/nym-wg-go`; see the architecture spec for the crate layering
