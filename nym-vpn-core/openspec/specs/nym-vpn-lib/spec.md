## Purpose

`nym-vpn-lib` is the central orchestrator of the Nym mixnet VPN client. It owns the tunnel lifecycle (connect, disconnect, reconnect), the cross-platform tunnel state machine, and both the mixnet and WireGuard tunnel paths. It exposes a high-level service (`NymVpnService`) that translates user/IPC commands into tunnel control commands, manages account/credential/gateway/discovery subsystems, configures the OS (routing, DNS, firewall, split tunneling), and broadcasts tunnel and account state events back to callers.

## Requirements

### Requirement: TunnelStateMachine

The system SHALL drive the tunnel through a finite set of states (Disconnected, Connecting, Connected, Disconnecting, Error, Offline) by running an async event loop that consumes `TunnelCommand`s and produces `TunnelEvent`s.

#### Scenario: Spawning the state machine
- **GIVEN** valid `NymConfig`, `TunnelSettings`, a command receiver, and an event sender
- **WHEN** `TunnelStateMachine::spawn` is called
- **THEN** the machine initializes shared OS subsystems (firewall, DNS handler, route handler, adblocker, resolver), enters `OfflineState` if connectivity reports offline or otherwise `DisconnectedState`, and returns a `JoinHandle` to the running loop.

#### Scenario: Broadcasting a state change
- **GIVEN** the running state machine loop
- **WHEN** a state handler returns `NextTunnelState::NewState`
- **THEN** the machine converts the private state to a public `TunnelState`, reports it to the statistics sender, and sends `TunnelEvent::NewState` over the event channel.

### Requirement: ConnectionLifecycleCommands

The system SHALL accept `TunnelCommand::Connect`, `TunnelCommand::Disconnect`, `TunnelCommand::SetTunnelSettings`, and `TunnelCommand::Block` and react according to the current state.

#### Scenario: Connecting from disconnected
- **GIVEN** the machine is in `DisconnectedState`
- **WHEN** it receives `TunnelCommand::Connect`
- **THEN** it transitions to `ConnectingState` with retry attempt 0 and no preselected gateways.

#### Scenario: Disconnecting from connected
- **GIVEN** the machine is in `ConnectedState`
- **WHEN** it receives `TunnelCommand::Disconnect`
- **THEN** it transitions to `DisconnectingState` with `PrivateActionAfterDisconnect::Nothing`, tears down the tunnel monitor, and eventually returns to `DisconnectedState`.

### Requirement: ConnectingOrchestration

The system SHALL, while connecting, resolve API addresses, configure a connecting firewall policy, start a `TunnelMonitor`, and progress through `EstablishConnectionState` sub-states (ResolvingApiAddresses, AwaitingAccountReadiness, RefreshingGateways, SelectingGateways, RegisteringWithGateways, ConnectingTunnel) before reaching the Connected state.

#### Scenario: Tunnel reaches up
- **GIVEN** `ConnectingState` has started a tunnel monitor
- **WHEN** the monitor emits `TunnelMonitorEvent::Up` with tunnel interface and connection data
- **THEN** the machine transitions to `ConnectedState` carrying the selected gateways and the monitor handle.

#### Scenario: Retry with exponential backoff
- **GIVEN** a connection attempt fails and triggers a reconnect
- **WHEN** the retry attempt number increases
- **THEN** the wait delay follows fast retries (500ms) for the first 2 attempts and then exponential backoff capped at 15 seconds before re-entering `ConnectingState`.

### Requirement: GatewayBlacklistingOnFailure

The system SHALL blacklist a failing gateway and discard the current selection so a different gateway is chosen on the next attempt.

#### Scenario: Connection check fails
- **GIVEN** `ConnectingState` is monitoring a tunnel
- **WHEN** it receives `TunnelMonitorEvent::ConnectionFailed` or `TunnelMonitorEvent::RegistrationFailed`
- **THEN** the offending gateway id is added to the gateway provider blacklist, the selected gateways are cleared, and the state machine remains in connecting to retry with a fresh selection.

### Requirement: TunnelTypeSelection

The system SHALL choose between the mixnet and WireGuard tunnel paths based on configured `TunnelType` and the `GatewaySelectionAlgorithm`, defaulting to WireGuard when the algorithm is `Auto`.

#### Scenario: Auto algorithm forces WireGuard
- **GIVEN** `TunnelSettings` with `GatewaySelectionAlgorithm::Auto`
- **WHEN** `tunnel_type_used()` is evaluated
- **THEN** it returns `TunnelType::Wireguard` regardless of the configured `tunnel_type`.

#### Scenario: Explicit mixnet selection
- **GIVEN** a non-Auto algorithm and `tunnel_type` set to Mixnet
- **WHEN** the tunnel monitor establishes the connection
- **THEN** the mixnet tunnel path (mixnet client, IP packet router, processor) is used rather than the WireGuard path.

### Requirement: OfflineHandling

The system SHALL detect loss of network connectivity and transition to `OfflineState`, optionally reconnecting automatically once connectivity is restored.

#### Scenario: Going offline while connecting
- **GIVEN** `ConnectingState` is active
- **WHEN** the connectivity handle reports the device is offline
- **THEN** the machine disconnects with `PrivateActionAfterDisconnect::Offline { reconnect: true, gateways }` and enters `OfflineState`.

#### Scenario: Reconnecting on connectivity restore
- **GIVEN** the machine is in `OfflineState` with `reconnect` set
- **WHEN** connectivity is restored
- **THEN** the machine transitions to `ConnectingState` with the last known gateways; otherwise it transitions to `DisconnectedState`.

### Requirement: ErrorStateAndBlocking

The system SHALL transition to `ErrorState` on unrecoverable failures, applying a blocking firewall policy that denies network access, and SHALL map internal errors to a public `ErrorStateReason`.

#### Scenario: Mapping an error to a reason
- **GIVEN** a tunnel or account failure surfaces during connecting
- **WHEN** the error is converted via `error_state_reason()`
- **THEN** it yields a specific `ErrorStateReason` (e.g. `SetDns`, `TunDevice`, `SameEntryAndExitGateway`, `BandwidthExceeded`, `MaxDevicesReached`) or `None` when the failure does not warrant the error state.

#### Scenario: Blocking network access on command
- **GIVEN** the machine is in any active state
- **WHEN** it receives `TunnelCommand::Block(reason)`
- **THEN** it transitions toward `ErrorState`, applying a `FirewallPolicy::Blocked` policy that blocks traffic.

### Requirement: SettingsDiffReconnect

The system SHALL compute a diff between old and new `TunnelSettings` and reconnect only when changed fields require it, otherwise applying changes in place.

#### Scenario: Non-reconnecting setting change
- **GIVEN** a connected or connecting tunnel
- **WHEN** `SetTunnelSettings` changes only fields like `AllowLan` or `SplitTunnel`
- **THEN** the settings are applied without forcing a reconnect (`should_reconnect` returns false).

#### Scenario: Reconnecting setting change
- **GIVEN** a connected tunnel
- **WHEN** `SetTunnelSettings` changes the entry point, exit point, tunnel type, or DNS
- **THEN** `should_reconnect` returns true and the tunnel is reconnected with appropriately cleared or retained gateways.

### Requirement: TunnelMonitorEstablishment

The system SHALL run a `TunnelMonitor` task that awaits account readiness, refreshes and selects gateways, registers with gateways, brings up the tunnel interface, and reports lifecycle events back to the state machine, returning a `Tombstone` for resource cleanup.

#### Scenario: IPv6 unavailable
- **GIVEN** the tunnel settings enable IPv6
- **WHEN** the monitor starts and the OS does not have IPv6 enabled
- **THEN** the monitor returns `Error::Ipv6Unavailable` and the resulting `Down` event carries `ErrorStateReason::Ipv6Unavailable`.

#### Scenario: Tunnel teardown produces a tombstone
- **GIVEN** a running tunnel monitor
- **WHEN** the monitor exits (cleanly or with error)
- **THEN** it emits `TunnelMonitorEvent::Down` and returns a `Tombstone` whose drop closes the tunnel devices.

### Requirement: ServiceCommandInterface

The system SHALL expose `NymVpnService` which receives `VpnServiceCommand`s, translates connect/disconnect/reconnect and setting changes into `TunnelCommand`s, and answers account, gateway, diagnostics, and configuration queries.

#### Scenario: Translating a target-state command
- **GIVEN** a running `NymVpnService`
- **WHEN** it receives `VpnServiceCommand::SetTargetState(Connected)` (or `Reconnect`)
- **THEN** it reports a connection request to statistics and sends `TunnelCommand::Connect` to the state machine command channel.

#### Scenario: Querying tunnel state
- **GIVEN** a running `NymVpnService`
- **WHEN** it receives `VpnServiceCommand::GetTunnelState`
- **THEN** it replies on the provided oneshot channel with the current `TunnelState`.

### Requirement: EventBroadcasting

The system SHALL broadcast `TunnelEvent`s (state changes and account state) to subscribers via a `broadcast` channel, forwarding events emitted by the state machine.

#### Scenario: Forwarding a tunnel state event
- **GIVEN** subscribers to the service's `tunnel_event_tx` broadcast channel
- **WHEN** the state machine emits `TunnelEvent::NewState`
- **THEN** the service handles the event and re-broadcasts it to all subscribers.

### Requirement: OSIntegrationDuringConnect

The system SHALL configure operating-system networking (firewall exceptions, routing, DNS filtering resolver, split tunneling, SOCKS5 proxy) appropriately for each state to prevent leaks while permitting required control-plane traffic.

#### Scenario: Restricting networking while connecting
- **GIVEN** a desktop platform entering `ConnectingState`
- **WHEN** the state is entered
- **THEN** networking is disallowed (discovery and account API firewall raised, geo-location disabled) until the connecting firewall policy and resolver overrides are applied, after which networking is re-allowed.

## Technical Notes

- **Implementation**: Public API and shared types in `src/lib.rs`; state machine core, `SharedState`, `TunnelSettings`, `TunnelCommand`, `Error`/`ErrorStateReason` mapping in `src/tunnel_state_machine/mod.rs`; per-state handlers in `src/tunnel_state_machine/states/*`; connection establishment in `src/tunnel_state_machine/tunnel_monitor.rs`; tunnel error types and the mixnet/WireGuard paths under `src/tunnel_state_machine/tunnel/{mixnet,wireguard}/`; gateway selection in `src/tunnel_state_machine/tunnel/gateway_provider/`; mixnet topology/processor in `src/mixnet/`; high-level service and command interface in `src/service/vpn_service.rs`.
- **Dependencies**: Orchestrates many sibling crates — `nym-sdk`/`nym-client-core` (mixnet client), `nym-wg-go`/`nym-wireguard-types` (WireGuard), `nym-gateway-directory` (gateway discovery/selection), `nym-registration-client` (gateway registration), `nym-bandwidth-controller` and `nym-credentials-interface` (credentials/ticketbooks), `nym-vpn-account-controller`/`nym-vpn-store`/`nym-vpn-api-client` (account and credential management), `nym-vpn-network-config` (network discovery), `nym-routing`/`nym-dns`/`nym-firewall`/`nym-split-tunnel` (desktop OS integration), `nym-offline-monitor` (connectivity), `nym-connection-monitor` (ICMP/TCP probes), `nym-statistics` (telemetry), and `nym-vpn-lib-types` for the shared public type vocabulary (`TunnelState`, `TunnelEvent`, `ErrorStateReason`, `EntryPoint`/`ExitPoint`, etc.). Within the workspace it is the central library consumed by the daemon/clients (e.g. `nym-vpnd`) and platform FFI layers (iOS/Android tunnel providers).
