# nym-connection-monitor Specification

> Generated by openlore on 2026-06-26
> Source files: src/lib.rs, src/connection_monitor.rs, src/connection_probe.rs, src/icmp_probe.rs, src/tcp_probe.rs

## Purpose

Monitors tunnel connectivity health by periodically sending probes through the tunnel and observing whether replies arrive within a timeout. It abstracts the probe transport behind a `ConnectionProbe` trait with ICMP (ping) and TCP-handshake implementations, runs a two-phase (initial/monitoring) probing loop with retry-based failure detection, and emits `ConnectionEvent`s describing whether the connection is viable, intermittently failing, or failed.

## Requirements

### Requirement: TwoPhaseProbingLoop

The system SHALL run a probing loop that starts in an aggressive `Initial` phase to establish viability and, upon the first successful probe, switches to a less aggressive `Monitoring` phase that spaces successful probes by a configurable periodicity.

#### Scenario: Transition to monitoring after first success
- **GIVEN** the monitor is in the `Initial` phase
- **WHEN** a probe succeeds
- **THEN** the phase switches to `Monitoring`, a `Viable` event is emitted, and the next probe is scheduled after `probe_periodicity`

#### Scenario: Successful monitoring checks paced by periodicity
- **GIVEN** the monitor is in the `Monitoring` phase
- **WHEN** probes keep succeeding
- **THEN** each subsequent probe is sent `probe_periodicity` after the previous probe's reply

### Requirement: RetryBasedFailureDetection

The system SHALL treat probe failures as intermittent and retry them, emitting `IntermittentFailure { retry }` for each failed attempt up to the phase-specific retry count, and SHALL declare the connection `Failed` once the retry count is exceeded.

#### Scenario: Initial connection declared failed after exhausting retries
- **GIVEN** the monitor is in the `Initial` phase and every probe fails
- **WHEN** the number of consecutive failures exceeds `initial_probe_retry_count`
- **THEN** `IntermittentFailure` events are emitted per retry and a final `Failed` event is emitted

#### Scenario: Recovery resets retry counter
- **GIVEN** one or more probes have failed (retry counter > 0)
- **WHEN** a subsequent probe succeeds
- **THEN** a `Viable` event is emitted and the retry counter resets to 0

### Requirement: EvenlyPacedRetransmission

The system SHALL pace failed-probe retransmissions at fixed intervals equal to the phase timeout (measured from the last send time) so that fast-failing probes (e.g. socket errors) do not flood the network.

#### Scenario: Failed initial probes retransmitted at timeout interval
- **GIVEN** the initial probe keeps failing faster than the configured timeout
- **WHEN** retransmissions are scheduled
- **THEN** each subsequent probe starts exactly one `initial_probe_timeout` after the previous one

### Requirement: AbstractProbeInterface

The system SHALL define probing behind an async `ConnectionProbe` trait whose `send(timeout)` returns success or a `BoxedProbeError`, and probe error types SHALL expose `is_timeout()` so the monitor can distinguish timeouts from other failures.

#### Scenario: Probe reports a timeout
- **GIVEN** a probe whose underlying transport times out
- **WHEN** the probe's error is inspected
- **THEN** `is_timeout()` returns true for that error

### Requirement: IcmpProbeTransport

The system SHALL provide an ICMP (ping) probe that sends echo requests to a configurable target IP (default `1.1.1.1` for IPv4, `2606:4700:4700::1111` for IPv6) with a configurable identifier and incrementing sequence number, supporting binding to a local address and, on Linux/Android/iOS/macOS, to a named interface (resolved to an interface index on iOS/macOS).

#### Scenario: ICMP echo sent to probe target
- **GIVEN** an `IcmpProbe` configured for a target IP
- **WHEN** `send(timeout)` is called
- **THEN** an ICMP echo request is sent with an incremented sequence number and the call succeeds if a reply arrives before the timeout

#### Scenario: ICMP timeout classified
- **GIVEN** no ICMP reply arrives within the timeout
- **WHEN** the resulting error is examined
- **THEN** it is an `IcmpProbeError` whose `is_timeout()` is true

### Requirement: TcpProbeTransport

The system SHALL provide a TCP probe that determines viability by completing a TCP handshake to a configurable target address (default target IPs on port 80), creating a fresh non-blocking socket per probe, supporting binding to a local address and (on Linux/Android/iOS/macOS) a named interface, and classifying a connect that exceeds the timeout as a timeout error.

#### Scenario: TCP handshake succeeds
- **GIVEN** a `TcpProbe` targeting a reachable address
- **WHEN** `send(timeout)` completes the handshake before the timeout
- **THEN** the probe returns success

#### Scenario: TCP connect times out
- **GIVEN** the handshake does not complete within the timeout
- **WHEN** `send(timeout)` is called
- **THEN** a `TcpProbeError` with `is_timeout()` true is returned

## Technical Notes

- **Implementation**: `src/connection_monitor.rs` (state machine: `Phase`, `ConnectionStatus`, `TimingConfig`, event emission, retry pacing), `src/connection_probe.rs` (`ConnectionProbe`/`ProbeError`/`BoxedProbeError` traits), `src/icmp_probe.rs` (ICMP via `surge-ping`), `src/tcp_probe.rs` (TCP handshake via `socket2`/`tokio`), `src/mock_probe.rs` (test double). `TimingConfig::mixnet()` and `TimingConfig::two_hop()` provide preset timings.
- **Dependencies**: `surge-ping` (ICMP), `socket2` + `tokio` (TCP/async), `nix` (interface index resolution), `nym-common` (`trace_err_chain!`), `async-trait`, `tokio-util` (`CancellationToken`), `thiserror`. In the workspace it provides the health-check signal used by the VPN tunnel layer to detect whether traffic is actually flowing through the established mixnet/wireguard tunnel and to trigger reconnection on failure.
